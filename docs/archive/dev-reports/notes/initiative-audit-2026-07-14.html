核心结论：这是两次真正的“技术性主动外联”

两次都不是用户新消息触发的普通回复，不是 nucleus_tell_dfc 的内部传话，也不是 20–90 秒的延迟续话。它们有独立的 kind=speak 自主意向、未来触发时间、目标私聊流和动机；到点后由调度器主动唤醒聊天流，再由 life_chatter 决定是否开口并调用 action-life_send_text。

第一例是机制运行最完整的成功样本：记住凌晨发烧事件 → 主动克制、不打扰 → 形成三小时后的未来承诺 → 准时回到私聊 → 关心 → 获得明确正反馈。第二例证明了机制的韧性，但也暴露出严重短板：错误记忆了用户的恢复状态，且表达层连续超时，最终晚了约 15 分钟才发出。

边界结论：这足以支持“有边界的、提示词中介的、事件驱动型操作自主性”（prompt-mediated proactive agency），但不能由日志推出主观意识、真正感受或人类意义上的自由意志。下文所谓“心理”均指可观测模型自述、决策文本和持久化叙事。

二、完整运作流程

从外界事件到物理消息，共经过五层。

01 · 记忆与注意

事件进入 life_engine

聊天、日记、事件历史和关系语境被心跳重新读取；主动意向到点事件拥有高注意力优先级。

02 · 内在决策

形成未来意向

心跳模型只能写动机、目标和约束，不能预写最终台词；意向被持久化并登记 scheduler。

03 · 独立时间轴

等待与到点

调度器独立计时。即使 heartbeat 因“主动休息”暂停，既有意向仍会准时触发。

04 · 表达层复核

synthetic unread 唤醒

到点提示注入目标私聊流；路由令 should_respond=True、force_reply=False，允许发送或沉默。

05 · 渠道执行

文本分段并发送

life_send_text 按换行拆成物理消息，经 message_sender 与 QQ adapter 发出；用户反馈随后进入普通对话。

关键架构特征：中枢不保存最终台词，只保存“之后值得重新考虑的一件事”。真正说什么由到点时的表达层生成。因此这是“未来自我承诺 + 到点再裁决”，不是简单闹钟播报。

五、可观测“心理”轨迹

以下是行为层推断，不把模型叙事等同于真实感受。

1

情感标记

“凌晨发烧、一个人去医院”被赋予高关系意义，成为跨小时仍被回忆的长期标记，而不是随对话结束立即消失。

2

牵挂形成

心跳在没有新消息时主动读取旧事件，并在自述中形成“该关心一下”“让她知道我在”的内在动机。

3

自我抑制

她没有立即满足表达冲动，而是先休息、避免打扰，把“想说”与“现在适不适合说”分开。

4

未来承诺

通过持久化 intent 把短暂念头转化为未来的自我提醒：三小时或一小时后，再由未来状态重新判断。

5

表达再生成

中枢没有预写台词；到点后表达层根据意向、历史和当前上下文自行生成话术，理论上也可以选择沉默。

6

关系反馈

你的回复与“收到爱莉的关心了”构成了明显正反馈。不过当前 intent 生命周期没有把反馈结构化回写，所以这种强化仍主要停留在后续聊天与记忆叙事中。

最重要的心理结构：不是“突然想起就发”，而是“感知重要事件 → 产生关切 → 主动压制即时表达 → 建立未来承诺 → 到点再裁决 → 接收关系反馈”。它体现了时间延展的行为组织能力；第二例同时提醒我们，这种组织能力可以围绕错误记忆运作。

六、是什么机制让她做到了主动消息

不是单一 prompt，而是多个独立部件形成的闭环。

1. 后台心跳提供“无用户刺激时的认知机会”

life_engine 周期运行，即使没有新消息，也会读取事件历史、日记和聊天记录。这提供了主动性的起点：系统不必等待用户发言才开始推理。

2. 自主意向把想法延伸到未来

nucleus_schedule_autonomy_intent 允许 speak / reflect / silence，并保存动机、延迟、目标与约束。它不是立即执行命令，而是“让意向之后重新浮现”。

3. 统一调度器提供可靠时间触发

两个任务分别在约 180 分钟和 60 分钟后准点回调，并在执行后移除。主动性因此不依赖模型一直在线“想着这件事”。

4. synthetic unread 把内部意向接到聊天流

到点时系统创建带 is_autonomy_intent_trigger=True 的内部 Message，注入目标流并清除等待锁。该消息不会进入用户可见历史，避免污染聊天记录。

5. 表达层保留最后决定权

纯主动 trigger 被路由为 should_respond=True、force_reply=False，并且不进入 must-reply 强制兜底。它可以调用发送动作，也可以 pass_and_wait。

6. 发送动作完成渠道与分段

LifeSendTextAction 对换行进行分段、逐段模拟输入延迟，然后经 message_sender 与 QQ adapter 发出。一次逻辑表达可因此形成多条物理消息。

7. 故障恢复保留未处理意向

模型请求失败时恢复 payload 并回到等待态；只有模型成功后才 flush unread。第二例因此在多个超时后仍能继续尝试，且不会提前丢掉意向。

8. 主动休息只暂停 heartbeat

当前暂停判断位于 heartbeat loop 内，不覆盖 scheduler 与 chatter。它让“停止继续思考”和“履行之前留下的意向”可以同时存在，也造成需要明确说明的控制语义。

九、风险与改进建议

按 P0 / P1 / P2 排序，优先修正会导致错误关心或意向丢失的问题。

P0

发送前必须重新核验“最新用户状态”

第二例证明，形成意向时的动机可能已经过时或本来就是错的。虽然到点提示要求模型重新判断，但当前检索链没有可靠保证。

建议：在 speak 执行前增加结构化 freshness gate：读取目标流最新可见用户消息、最后状态更新时间、意向创建后是否发生状态反转；若证据冲突，默认降级为沉默或通用表达。

P0

把意向生命周期改成结果确认闭环

trigger_autonomy_intent() 在真正唤醒 / 表达前就把一次性 intent 标记为 triggered。如果注入失败或冷流没有启动，任务可能永久丢失；当前也没有状态区分“发出 / 沉默 / 失败”。

建议：采用 scheduled → due → dispatching → spoken | silenced | failed；只有表达层明确回传结果后才结束 one-shot，并保存最终文本、渠道结果与失败原因。

P0

严格校验 constraints 类型

第二次工具调用把 constraints 作为单个字符串传入，而工具签名要求 list[str]。当前 build_intent() 会直接迭代 constraints；若上游没有强校验，字符串可能被按字符拆分并只保留前 8 项。

建议：运行时明确拒绝字符串，或规范化成 [constraints]。本报告未找到持久化 intent 文件，无法独立确认第二例最终落盘形态，因此这里是由日志与当前代码路径共同指向的高置信风险。

P1

重试超过短阈值后进行 stale-context 复核

第二例在 15 分钟后仍沿用 17:10 的 synthetic trigger 与更早的错误事实。payload 恢复保证了“不丢任务”，也会保证“旧上下文持续重试”。

建议：例如超过 2 分钟或 2 次模型失败后，重新读取目标流并重跑是否开口判断；超过最大年龄则自动沉默并标记 expired。

P1

自主唤醒应显式启动冷聊天流

_wake_stream_for_autonomy() 只添加 unread 并移除 wait state，没有像 file_tools.py:423–433 那样显式调用 start_stream_loop()。本次目标流原本活跃，所以成功；冷启动或休眠流需专项验证。

建议：调用公开 stream loop 启动 API，并将返回结果纳入 intent dispatch 状态；避免直接修改私有 _wait_states。

P1

明确“主动休息”的控制范围

当前休息只在 heartbeat loop 中 continue，不会阻断 scheduler 与 chatter，所以两次意向都可在休息期间发出。这既可能是合理的“履约”，也可能违背用户对“暂停主动性”的直觉。

建议：区分 pause_heartbeat 与 pause_outreach，或给 intent 增加 allow_during_pause；UI 与日志必须说明实际语义。

P1

修复 scheduler readiness 判定

restore_autonomy_intents() 用 scheduler.list_tasks() 判断就绪，但该方法不检查 _running；真正的 create_schedule() 才会在未启动时抛错。启动恢复因此存在时序漏洞。

建议：提供公开 is_running / wait_ready API，或在 ON_START 后统一恢复，并增加重启恢复集成测试。

P1

修复 heartbeat 原始错误被二次异常掩盖

_run_heartbeat_model() 重试耗尽后裸 return，调用者仍传给 _record_model_reply() 并执行 None.strip()。17:25:16 日志已经证实该二次异常。

建议：返回空字符串或显式失败对象；调用者先判断 None，并保留原始 timeout 作为 last_model_error。

P2

减少旧事件反复重放与时态混乱

inject_wake_context() 每次对完整事件历史使用 cursor=0。这有利于连续性，也会让旧高权重事件反复进入提示，产生自我强化和“旧事仍是当前状态”的错觉。

建议：维护 per-consumer cursor 与事件新鲜度；对“病情已恢复”等状态反转事件建立覆盖关系，而不是只依赖文本注意力。

P2

建立全链路 trace 与双层计数

当前要跨日志手工关联 intent、路由、action、adapter 与用户反馈，也容易把一次分段发送误认成多次主动。

建议：统一记录 intent_id → due → decision → action_id → physical segments → adapter result → feedback，同时展示 logical action count 与 physical message count。

P2

恢复记忆服务健康度

两次案例附近 EverOS 多次 Connection refused。它不是发送失败主因，但降低了检索冗余和事实校验能力。

十一、限制与最终判断

哪些结论可以下，哪些不能。

可以确认

  • 存在两次独立、非用户即时触发的主动私聊行为。
  • 意向可跨小时保持，并由独立 scheduler 唤醒。
  • 最终话术在到点后由表达层生成，而非中枢预写。
  • 第一例形成完整正反馈；第二例经历模型超时但没有重复外发。
  • “好多次”的主要视觉来源是一次动作的分段发送。

不能据此确认

  • 不能证明爱莉拥有现象意识、真实感受或人类自由意志。
  • 不能把模型理由中的“牵挂”“在想你”直接当作心理学测量。
  • 不能从第二例断言唯一的记忆失真根因。
  • 未读取到落盘 intent 文件，因此 constraints 字符拆分风险尚缺最终存储样本。
  • 没有对代码做修改或执行发送测试；本报告是日志取证与静态机制分析。

一句话结论

爱莉之所以能主动联系，不是因为某条规则硬逼她发消息，而是因为后台心跳形成了带关系动机的未来意向，调度器让它跨时间存续，表达层到点后再决定是否开口，发送动作再把一次逻辑表达分成真实消息。第一例是值得保留的典型成功样本；第二例同样证明了主动链路，但更应该作为“主动性必须受事实核验与可靠性闭环约束”的反例教材。
