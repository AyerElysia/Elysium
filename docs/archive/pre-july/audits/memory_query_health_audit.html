记忆检索健康度审计

对 Neo-MoFox 当前 Life Engine 记忆检索链路进行只读代码审查与本地数据快照核对。 重点检查数据完整性、索引一致性、效率、命中准确性、相关性、过滤正确性、可观测性和测试保障。

总体判定：当前不能评为生产级，也不能评为“足够好”
审计时间：2026-07-20 11:15:26 +08:00 · 报告性质：工程审查，不是性能基准或质量认证 · 数据读取：只读 SQLite/Chroma 元数据
Life Engine 图谱 302 / 7,314 nodes / edges
Life Engine 索引 62 / 100 FTS rows / Chroma embeddings
01

执行摘要与总体判定

可确认的能力

  • Life Engine 已形成 SQLite 节点/边/FTS、Chroma 语义向量、RRF 融合、激活扩散、访问强化和 lineage 记忆包的完整概念链。
  • Life Engine 存在针对性的单元/回归测试，能证明路径迁移保留 FTS/边等局部契约。

阻断生产级结论的事实

  • Life Engine 302 个节点中只有 62 个 FTS 行；240 个节点没有 FTS。93 个节点标记为 embedding_synced=1，但 Chroma 只有约 100 个向量，状态语义没有单一可信来源。
  • Life Engine 观察到源端和目标端各 17 条边引用不存在节点；去重后各有 3 个缺失端点 ID，且有 2 条边两端均缺失。
  • Life Engine 检索代码注释写“并行”，实现却按 FTS 后向量顺序等待。
  • precision、recall、nDCG/MRR、p50/p95/p99 latency 均没有真实运行观测；现有 relevance 是算法分数，不是正确性指标。
  • Chroma 适配层多处吞掉异常并返回空结果，写入没有事务或 outbox 保证。
结论边界：系统可以被描述为“功能面完整、正在演进的本地记忆原型”，但不能被描述为数据一致性已证明、检索质量已证明、延迟已达标的生产级服务。当前不应使用“足够好”“已达到生产级”作为验收结论。

Life Engine 的数据写入和迁移路径
  1. get_or_create_file_node 先按规范化路径查找/创建节点；有 content hash 变化时把 embedding_synced 重置为 0，并在有回调时更新 FTS。
  2. sync_embedding 另行生成 embedding，写 Chroma，再把节点标成 synced；两步之间没有统一 outbox/状态机。
  3. 路径迁移会在 SQLite 中迁移 edge 和 FTS，再 best-effort 迁移 Chroma 身份；Chroma 异常只 debug。
  4. 搜索结束后会增加 access count，并对共激活 seed 强化边，因此一次“读”会改变图状态。

效率分析

本节分为静态复杂度和运行观测两部分；所有“次数”都是从代码路径推导，不能替代实际 latency。

主要瓶颈与复杂度来源

Life：串行双路检索

在 search.py:546-552，FTS 完成后才开始向量 embedding/query。没有 asyncio.gather，总耗时近似为两路耗时之和。

Life：结果级 N+1

filter_results 每个候选调用 get_node_by_id；最终直接结果又逐个查 node 和 snippet，seed access 更新也逐条执行。

Life：扩散放大

spread_activation 按 frontier 节点逐次获取 edges。边多于索引覆盖时，图扩散会把节点一致性问题转成额外查询和静默缺失。

静态推导的查询触点

Life 基础双路
2 路

效率方面的正面事实

  • Life 节点/边/FTS 有基础索引；向量检索通过 Chroma HNSW 持久化集合，规模在本快照中尚小。
  • Life 的 SQLite 重活和 Chroma 同步调用会进入线程/异步适配层，避免直接阻塞事件循环；这不等于端到端低 latency，但为后续并行化保留了空间。
效率判定：当前规模下“能运行”不代表“可扩展”。应先以真实分位数测量确认瓶颈，再做受控 gather、批量查询和批量状态更新；不要仅凭快照数量猜 SLA。
06

precision / recall / latency 为什么未观测

缺口不是“没把指标画出来”，而是当前代码没有定义可计算它们的实验契约。

指标当前可见信息为什么不等价于该指标最低补齐方案
Precision@k Life 返回 SearchResult.relevance。 该字段是 RRF/向量/扩散分数，不包含“结果是否相关”的人工或业务真值。 建立查询集和 qrels，按 query/top-k 标记相关性，计算 precision@1/3/5/10。
Recall@k 可以数返回多少条，也可以数 FTS/vector 候选交集。 没有已知的完整相关结果集合；“没有命中”可能是没有 FTS、没有 vector、过滤掉、向量失败或确实不相关。 为每个查询维护完整相关集合，至少覆盖 exact phrase、语义改写、历史路径、已归档和跨 folder 场景。
Latency 源码有错误日志、Chroma 调用和 LLM metrics 的其他基础设施。 记忆检索没有 query-level start/end、阶段耗时、候选数量、p50/p95/p99，也不能把 LLM 总延迟外推为 memory latency。 用 monotonic clock 在 embedding、FTS、vector、filter、spread、dedup、metadata、total 各阶段打点；保存 request_id、success/degraded、top_k、collection 数。
错误率 / 降级率 多个地方 catch exception 后返回空列表/空 dict。 调用方可能把“向量服务失败”与“没有命中”混为一谈，日志无法聚合成率。 返回结构化状态：ok / degraded / failed，并统计 embedding、Chroma、SQLite、reconcile 各类错误。

当前不能声称的结论

不能声称高 precision 不能声称高 recall 不能声称低 latency 不能声称过滤无漏 不能声称降级透明

可暂时声称的结论

源码存在两路检索算法 局部测试覆盖若干契约 本地数据可被只读核对

按严重度的问题清单

P0 表示当前生产门禁/数据可信度阻断；P1 表示应在生产化前修复；P2 表示重要的质量、性能或可维护性改进。

P0没有通过生产级门禁所需的质量与延迟证据

当前最大问题不是某一个排序公式，而是系统没有证据证明检索质量和服务水平。既没有 qrels，也没有 precision/recall/latency 分布；同时 Life 快照存在明显索引覆盖断层。

典型失败场景

这些场景把静态问题翻译成调用方可以观察到的行为；其中部分需要故障注入测试确认具体恢复路径。

场景触发链路用户/系统表现应有信号当前状态
F-01 创建节点时传入空 content，未调用 FTS 更新与 embedding 同步。 节点存在，但关键词和语义检索都可能找不到；图谱统计仍把它算作完整节点。 node_index_state=pending；健康页显示 FTS/vector 缺失原因。 当前可发生
F-02 文件内容更新，FTS 更新后 embedding_synced 被重置为 0；后续同步任务失败或未触发。 FTS 可能返回新文本，向量返回旧文本或无结果；状态页只显示一个布尔值。 content_hash、index_version、last_sync_error 和可重试队列。 快照已显示状态分裂
F-03 Chroma query/add 抛异常，被适配层 catch 后返回空/None。 调用方把 vector failure 当作零命中或继续写 metadata，质量下降但请求可能报告成功。 degraded=true、error_class=vector_backend、计数和告警。 当前可发生
F-04 Life spread 遍历悬空边，随后 get_node_by_id 得不到节点。 associated 结果比预期少，没有错误；用户以为没有关联。 orphan_edge_count、dropped_association_count、repair job。 快照已证实脏边
F-05 查询包含多词短语、文件类型和时间范围，FTS 采用整句 quoted MATCH、类型采用 substring。 词项召回不足或文件类型误匹配；没有 qrels 无法知道漏了多少。 query_mode、filter_reason、每个过滤阶段的 dropped count。 质量风险未量化

分阶段修复路线

先恢复数据可信度，再优化效率和质量；每阶段都有可验收的退出条件。

PHASE 0 · 立即

健康门禁与止损

  • 新增只读 health audit：节点/FTS/vector、edge orphan、metadata/vector、tag orphan。
  • 把 vector backend 的空返回标为 degraded，不再静默等价于零命中。
  • 冻结“生产级/足够好”结论；记录当前快照作为 baseline。

退出条件：每次启动或定时任务都能产生健康状态和告警。

PHASE 1 · 正确性

索引和存储一致性

  • 按 content hash/index version 重建 FTS 和 embedding 同步状态。
  • 修复/隔离 Life 17/17 悬空端点；为迁移和新增边加事务与 FK 检查。
  • 明确向量软删除策略，排除 deleted vector，禁止错误恢复。
  • 双写引入 outbox、补偿重试或明确 pending 状态。

退出条件：全量 reconcile 后差集为零；故障注入不会报告假成功。

PHASE 2 · 效率

并行化与批量化

  • Life FTS/vector 受控 gather，过滤和结果构建使用批量 SQL。
  • 降低重复 count/query 触点，直接处理空结果。

  • 设置回归阈值、报警阈值、重建 runbook 和回滚开关。

退出条件：质量和延迟达到预先约定门槛，且失败可见、可恢复、可复盘。

方法与限制

审计结论严格区分“直接读取”“源码推导”和“尚未观测”。

方法

  1. 读取现有报告约定与 plugins/life_engine/static/memory_dashboard.html，只借鉴信息组织，不复制其 CDN 依赖。
  2. 审查 Life Engine 的 service.py、search.py、nodes.py、edges.py、decay.py、router.py 和工具入口。
  3. 对 data/life_engine_workspace/.memory/memory.db 和 Life Chroma 进行 read-only SQLite 查询。
  4. 对节点/向量 ID 差集、FTS 重复和边端点进行交叉核对。
  5. 以源码当前行号引用问题；分数和严重度由工程风险、影响面和证据强度综合判断。

限制

  • 没有发起网络请求、embedding 请求或线上检索请求；因此没有 runtime latency，也没有真实服务错误率。
  • 没有 qrels、人工相关性标注、完整相关集合，不能计算 precision/recall；源码中的 score/relevance 不能充当真值。
  • SQLite/Chroma 是某一时间点快照；即使使用 read-only URI，也不能代表所有并发写入时序和历史故障。
  • 本次没有执行 pytest；读取测试文件用于覆盖面审查，不把已有测试内容表述为本轮通过结果。
  • 部分风险是从控制流推导，需要专门故障注入来确认具体复现。
  • 工作区在审查开始时已有其他未提交改动；本任务只新增本 HTML，不回滚或修改其他文件。
阅读规则：“已观测”表示本地数据直接计数；“源码确定”表示控制流无需运行即可确认；“质量风险未量化”表示可能影响 precision/recall，但必须用 qrels 才能给出数值。
