Life Engine 记忆查询健康审计

针对长期记忆的索引边界、SQLite 一致性、召回基础、关系图噪声和向量化准备状态的只读审查。报告仅使用聚合统计，不含记忆正文、原始检索词、用户身份信息或完整真实路径。

审计时间：2026-07-23 03:16 +08:00 · 审计方式：代码验证 + SQLite/Chroma 只读检查 · 报告版本：1

当前结论：索引处于“可恢复但明显降级”的状态。 SQLite 文件本身未损坏，但存在 34 项外键违规、32 条孤儿关系、242 份待重新索引的现存文档，以及尚未迁移到 chunk/outbox 新索引结构的历史库。实际库正被 5 个外部进程持有文件句柄；因此本次没有执行任何写入、重建、删边或向量操作。

一、审计范围与判断边界

已检查

  • 长期记忆 SQLite 的结构完整性、外键一致性、节点/边/FTS 计数。
  • 工作区文档与索引节点的覆盖率、哈希新鲜度、历史缺失节点和污染节点。
  • 关系图的孤儿边、自环和 associates 边占比。
  • Chroma SQLite 文件的只读完整性，以及空命中 FTS 的本地微基准。

没有声称验证的事项

  • 没有读取或展示任何记忆正文、查询文本、用户私密数据或文件清单。
  • 没有对在线服务执行停机、重建、删库、删边或向量写入。
  • 没有真实相关性标注集，因此不能宣称当前 recall、precision 或排序相关性已经达标。
  • 没有启动 embedding worker；向量集合的真实语义覆盖率仍待重建后测量。

外键违规数为 34，高于孤儿边行数 32，是因为一条边可能同时引用两个不存在的端点。修复工具会删除不存在 source/target 的边，并将不存在节点的 correction 关联置空；不会删除仍然合格但源文件已经消失的历史节点。

相关性风险：associates 边占比接近 85%，会把自动联想噪声放大到图扩展阶段。即使文本召回正确，过密关系图也可能把不相关的证据带入最终上下文。建议在修复后收紧自动建边阈值、限制每个节点的扩展数，并优先保留显式 lineage/corrects/refines 关系。

六、Chroma 与原生多模态边界

本轮只读结果

  • Chroma SQLite 文件完整性：ok。
  • 文件大小：4,583,424 bytes。
  • 本次审计、dry-run 和迁移工具均未打开向量集合进行写入；迁移工具设计上不会触碰 Chroma。

需要避免的误判

  • “Chroma 文件完整”不等于向量语义覆盖率或图片理解质量已经正确。
  • 当前真实库没有新 chunk/outbox 行，不能据此断言原生多模态向量链路已被新检索结构消费。
  • 重建 SQLite 后，应由既有 embedding worker 生成新 chunk 向量，再做向量集合 ID 覆盖审计。

七、已完成的工程性修复

  1. 统一长期记忆资格规则，并接入索引、检索、服务、文件工具、梦境残留、关系图和衰减链路。
  2. 工作区扫描仅递归允许的记忆目录；运行态、隐藏目录等只做聚合拒绝，不再扫描其内部垃圾文件。
  3. 索引写入改为正式 document upsert：同步节点、chunks、FTS 和 outbox；不存在的文件不会被误建空白节点。
  4. 新增健康快照：覆盖 SQLite 完整性、FK、FTS/chunk/outbox 孤儿、边噪声、资格污染、覆盖率和哈希失配。
  5. 新增 reconcile_life_memory.py：默认 dry-run；--apply --rebuild --prune-ineligible --repair-orphans 才会写 SQLite，且自动备份。
  6. 新增活跃持库保护：检测到外部进程打开记忆库时，apply 会在创建备份或写入前拒绝执行。
验证结果：相关完整测试集 115 passed（另有项目既有的 2 个 deprecation warnings）；目标文件 ruff check 与 git diff --check 均通过。

八、推荐执行顺序

优先级动作原因与验收
P0 在服务正常停机后执行 SQLite-only reconcile 修复 32 条孤儿边、清理 30 个污染节点、重写 242 份新/变更文档，并生成 chunks/FTS/outbox。验收：integrity_check=ok、foreign_key_check=0。
P0 启动既有 embedding worker 并等待 outbox 清空 SQLite rebuild 不触碰 Chroma；worker 才负责向量。验收：pending 任务归零、chunk 向量覆盖率可核验。
P1 收紧自动 associates 关系 降低近 85% 自动联想边对上下文的污染。优先限制扩展预算、阈值和每节点边数。
P1 建立脱敏标注检索集 建议 50–100 条人工问题，每条标注期望文件集合和时间范围；再测 recall@5、MRR、nDCG、p95 端到端时延。
P2 定期只读健康审计 每次服务升级或模型变更后检查覆盖率、FK、孤儿、outbox 和向量 ID 一致性。

停机后唯一建议的迁移命令

./.venv/bin/python scripts/reconcile_life_memory.py \
  --workspace data/life_engine_workspace \
  --apply --rebuild --prune-ineligible --repair-orphans

该命令会先备份 SQLite，只改 SQLite，不改 Chroma。当前服务仍持库时它会安全失败；本报告不建议绕过该保护或在线强行执行。

九、最终判断

当前不是“查询慢一点”的单点问题，而是旧索引状态、关系图污染和未落地 chunk 索引的组合问题。 代码层面的隔离与迁移工具已经准备好，下一步关键是一次受控停机后的 SQLite 重建、孤儿修复和 embedding worker 回填。完成后再基于标注集评估准确性，才有资格判断这套记忆查询是否真正可靠。

隐私说明：本报告没有记录记忆内容、文件原文、完整真实路径、原始查询、进程标识或用户身份数据；所有数字均为聚合观测值。
