# 生命引擎核心（Life Engine Core）

> 文档状态：权威文档；意识 Presence、World Projection、Perception Gateway、主体主动性权威与心跳机会总线已落地。
> 代码位置：`plugins/life_engine/core/`、`plugins/life_engine/service/`、`plugins/life_engine/initiative/` 与 `plugins/life_engine/opportunity/`。
> 本文是生命引擎运行态的权威文档；凡与本文冲突，以本文和当前代码为准。

## 0. 一句话定位

生命引擎核心是数字生命的**自主运行循环**：以固定间隔心跳驱动潜意识决策，以事件驱动的主意识表达层（LifeChatter）处理对外交互，两者共享同一主体的身份、记忆和认知，通过统一事件流保持时间连续性。

## 2. 心跳循环（潜意识层）

### 2.1 运行机制

心跳是生命引擎的自主运行脉搏，由 `LifeEngineService._heartbeat_loop()` 驱动：

```
start() → 初始化子系统 → 启动 _heartbeat_loop() + _memory_index_loop()
                              │
                              ▼ (每 N 秒)
                    ┌── 睡眠时段？──→ 跳过
                    │── 主动休息？──→ 跳过（检查点除外）
                    │
                    ▼
              _run_heartbeat_round()
                    │
                    ├── 收集记忆健康与到期复盘机会（只读，不改写）
                    ├── 收集后台智能体结果
                    ├── _prepare_heartbeat_context()  ← 装配 prompt
                    ├── _run_heartbeat_model()        ← LLM 调用 + 工具执行
                    ├── 记录模型回复
                    ├── 触发学习系统快环反思
                    └── 持久化状态
```

### 2.2 关键参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `heartbeat_interval_seconds` | 配置 | 心跳间隔 |
| `heartbeat_timeout_seconds` | 120 | 单次 LLM 调用超时 |
| LLM 总预算 | timeout×2+60 | 覆盖重试+降级 |
| `max_rounds_per_heartbeat` | 配置 | 单次心跳最大工具轮数 |
| `sleep_time` / `wake_time` | 配置 | 睡眠时段（HH:MM） |

### 2.3 心跳 Prompt 装配

`_prepare_heartbeat_context()` 构建注入 LLM 的上下文。下列段落是当前真实装配，不是愿望清单：

| 段落 | 来源 | 说明 |
| --- | --- | --- |
| 系统人设 | `SOUL.md` / `USER.md` / MEMORY 摘要 / 过滤后的 `TOOL.md` | 身份与主体权威；不在 16k 事件预算内 |
| 固定指令头 | `_build_prompt_header()` | 内在动作、主体权威边界、工作区文件树。不再复述已移出心跳的 bash/看屏/联网/子代理 |
| 工具 schema | `_get_nucleus_tools()` → `HEARTBEAT_TOOL_NAMES` → `ROLE.TOOL` | 约 19 个常驻 schema，内核 pinned。清单见 `plugins/life_engine/service/tool_manifests.py` |
| 世界感知 | Perception Gateway | `<transient_world_perception>` 在事件预算之外前置，默认硬顶 32 KiB |
| 潜意识事件投影 | 运行时 `_event_history`（从 pending/账本镜像进来后再折叠） | **仅当存在未消费 delta 时**才拼进 Prompt。有 delta 时：规范摘要 + 最近 5 个已确认因果组 + 本拍 delta，总预算 16000 字符。游标追上、本拍无新事件时，这段是空的，只剩下预算外的世界感知。单项 ≤4 KiB 时内联 `raw_content`。这 **不是**「每拍都带整个生命域近期事件、超预算再压缩」 |
| 日记普查 | `RecentHandwrittenDiariesSection` | 工作区目录事实，不是「请收拾」 |
| TODO 板 | `TodoBoardSection` | 她自己写下的开放条目。status+id 顺序，约 1 KiB。不是邀请，不按优先级排序，不进机会页 |
| 机会页 | `OpportunitySection` → `OpportunityBus` | **一个** 2–4 KiB 页。连续性栏是 open `AttentionThread` / `InitiativeSeed` 只读投影（「你留下的线索」）；邀请栏是到期工程事实（主体文档复盘、MEMORY 结构压力、file_care、长河、epistemic 候选）。忽略 ≠ 拒绝。动手说明书要么是 skill，要么是已常驻工具。学习邀请指向 `nucleus_learn` / `skills/learning`，不自动 `get_skill`。冷却只针对邀请栏，且必须等本页 exact receipt。技能目录 / 学习观察账本 / 学习进度仍是非 offer 短状态 |
| 能力目录 | `HeartbeatCapabilityCatalogSection` | 约 0.5–1 KiB。不重复 schema。指出未注入本拍的能力仍在聊天/场景窗口；没出现在本轮 schema ≠ 主体不想用 |
| 心跳状态 | runtime | 时间、间隔、外界是否安静 |

心跳 **不** 注入 ChatStream「最近聊天记录」；那是 `build_chatter_runtime_context()` 的表达层快照。workspace 变更需要追溯时，聊天窗口仍可用 `nucleus_trace`；心跳常驻池不再注册它。聊天滚动上下文里的 Attention 投影（`_format_chatter_attention_threads`）仍是表达层快照，不是心跳机会页。

机会页由 `plugins/life_engine/opportunity/` 装配。生产者只判断工程事实是否成立，不写长邀请诗，也不在 render 时写入冷却。整页一个 `delivery_id`；最终成功心跳 attempt 对本页声明投影给出 content-free exact receipt 后，才冷却 **邀请栏** 中未 omitted 的 offer。连续性栏可以出现在同一 `delivery_id` 的声明集合里，但 commit 不得调用 `ProactiveAuthority` 写路径，也不得给线索写 last_invited。展示顺序只用技术键 `kind + domain + offer_id`；分页是预算，不是重要性。超预算必须标 `omitted` 和 offer id，禁止静默丢。TODO 板是心跳里的状态段，不是机会页；`enqueue_proactive_opportunity` 仍走生命事件工作集。

对心跳来说，学习、文件收拾、长河、MEMORY 复盘是同一类邀请：页上只给到期事实。动手说明书要么是一份工程 skill，要么是已经常驻的工具。学习走 `skills/learning/SKILL.md` + 薄执行门 `nucleus_learn`；MEMORY 走 `nucleus_memory_continuity_review`；长河走 `nucleus_write_narrative`；文件收拾走 `nucleus_mkdir` / `nucleus_read_file`。收集/渲染/冷却不得自动 `get_skill`。

事件投影与世界感知仍可能把协议信封送进潜意识窗口；工具 schema 污染已由心跳白名单收缩。诊断当时的 49 工具快照见 [心跳潜意识上下文污染分析_2026-09-03](../report/心跳潜意识上下文污染分析_2026-09-03.md)；当前清单见 [心跳工具清单_2026-09-03](../report/心跳工具清单_2026-09-03.md)。权威 Life Event 仍须完整保留。

### 2.3.1 潜意识是账本的具名消费者

「接到」生命域事件不等于每拍把全文再塞进 Prompt。心跳是权威 Life Event 账本上的具名消费者 `life_engine_subconscious_ingest:v1`：

- 账本只追加。`_pending_events` 是派生缓冲，不是第二份权威。
- 每拍 `_prepare_heartbeat_context()` 在 drain 之前 catch-up；启动加载 runtime 后也会追赶。缺口（`RawEventGapError`）fail closed，禁止把 ingest 游标拨到 frontier。
- 两个游标不要混：ingest 游标用账本 `ingest_position`；`heartbeat_context_cursor` 仍用 `LifeEngineEvent.sequence`，只在成功心跳对本拍声明工作给出 exact receipt 后前进。
- 首次在已有运行历史上启用该 consumer 时，若 `heartbeat_context_cursor > 0` 且 consumer 尚未创建，ingest 游标 seed 到当前 frontier（`bootstrap=high_water`），禁止把全部历史重放为本拍新经历。历史改由 `nucleus_grep_events` / `nucleus_read_event` 可达。
- 进入工作集的是带 `metadata.legacy_event_type` 的活动/消息，以及没有 legacy 对偶的 `chat.message.delivery_failed` / `delivery_unknown`。`send_requested`、已确认投递、与 MESSAGE 重复的 received chat fact、provider notice 只推进 ingest，不进心跳工作集。
- 后台 agent/mission 结果先写账本再入 pending；收集或 persist 失败必须保留待处理，禁止 skip。
- `record_message` 同步路径先账本后队列；异步路径为 EventBus 5 秒截止仍可先入 pending，后台写账本失败会有界重试并保持脏状态。异步窗口里 pending 可能暂时超前账本，不是第二权威。

`nucleus_grep_events` 搜索账本（可加时间窗、instance、人、工具、因果等过滤），命中只给节选和 occurrence 引用；全文走 `nucleus_read_event`。扫描有硬顶，扫不全必须标 `scan_truncated` 并给出下一页 position。

### 2.4 潜意识是完整意识活动的有界视图

潜意识的权威来源不是某个临时 Prompt，也不是 `last_chatter_think_by_stream` 一类兼容快照，而是统一 Life Event 账本中属于同一主体的活动 occurrence。当前表达链按以下顺序落账：

1. 一次成功模型生成先写入 `life.conscious_activity.model_turn.v1`，完整保留 provider reasoning、同轮 assistant 独白（包括空值）、transport request 身份、actor instance、stream 和 turn occurrence；
2. 每个工具选择写入 `life.conscious_activity.tool_call.v1`，原样保留模型提交的参数。`action-life_send_text` 的 `mood/decision/expected_response/thought/content` 因此属于同一个工具选择事件，不再只存在于短截断的最近快照；
3. 实际执行、协议阻断、重复抑制、主动等待、失败或平台投递完成写入配对的 `life.conscious_activity.tool_result.v1`；发送事实再以 `conscious_activity_id`、`tool_call_id` 和 origin turn 回连；
4. 模型轮 → 工具选择 → 工具结果形成一个可重放因果组。完整原文留在权威账本；超过 4 KiB 的单项只在 Prompt 投影中提供 UTF-8 安全节选、SHA-256、原始字节数和 `life-event-occurrence:` 引用；`nucleus_read_event` 可按 occurrence 稳定分页读取完整内容；
5. 本轮最终 wake Text 以独立 delivery marker 注册到 LLM 内核。只有最终成功 attempt 对整份 Text 返回 exact receipt，且 World Perception 自身也通过既有 exact receipt，heartbeat 才确认已完整看见本页并推进消费游标。截断、缺失、重复 marker 或回执未知都 fail closed。

这里的“活动”描述发生过什么，不替主体判断其意义。Provider reasoning 被保留为该意识实例当轮生成的过程材料，但不会因此自动升级为事实、长期记忆、信念或人格结论。系统 prompt、他者输入和基础设施日志继续保留各自来源，不能冒充第一人称活动。

默认跨实例潜意识视图保留完整工具参数/结果（大项改为可续读 ref）。Memory Witness 本身是意识实例，而不是纯基础设施；它每次成功模型生成的 provider reasoning、assistant message 和稳定 window/stream/request 归因也必须先进入同一活动账本。与此同时，Witness 的 `recent_subconscious_context` 只承担连续性背景、不能替代 Experience 证据，因此它作为消费者显式请求 `redacted-tools-v1` 投影，只看到工具名、状态、参数键和权威引用，不接收参数值/结果正文。该降敏只作用于 Witness 的瞬态输入，不删改潜意识权威事件，也不改变 Chat、Voice、直播、Minecraft 或 Agent 的默认完整视图。

模型参与不自动等于主体意识。Router/subject context 的结构化投影器、屏幕视觉解析、认知机会 producer 和 Learning 候选生成器若只是基础设施辅助，其输出必须保持外部候选/工具结果来源；只有被有效意识实例实际生成、明确采用或通过工具动作提交的部分才进入第一人称活动链。这样既不漏收意识，也不把后台算法伪装成爱莉。

### 2.5 工具执行

心跳使用真正的 `life_engine_internal` 白名单 `HEARTBEAT_TOOL_NAMES`（约 19 个），由 `_get_nucleus_tools()` → `heartbeat_tool_classes()` 解析。完整 schema 进入 `ROLE.TOOL`，执行后结果回注 LLM，最多 `max_rounds_per_heartbeat` 轮。未知工具名返回 `未知工具`，不伪装成主体拒绝。

常驻：休息、工作区文件读写列表与 grep、事件 grep/read、记忆检索与边界读取、`nucleus_memory_continuity_review`、主动 query/command、`nucleus_todo`、`nucleus_schedule`、`nucleus_skill`、`nucleus_learn`、`nucleus_write_narrative`。

不在心跳注册（类仍在，聊天清单若需要可留）：16 个独立学习工具、表情收藏、`nucleus_run_agent` / `nucleus_view_screen` / `nucleus_bash`、联网、`conversation_evidence` / 历史同步 / `fetch_life_memory`、`nucleus_trace`、`nucleus_relations` / `nucleus_memory_stats`、`platform_action`。

`nucleus_learn` 是跟随 learning skill 的薄执行门（`action` + `arguments` 对象），不是 16 张学习 schema 的平铺。`action=help` 读取 `skills/learning/SKILL.md`（工作区已有则不覆盖）。Minecraft 等场景工具不在心跳池里，走对应意识清单。没出现在本轮 schema 不等于主体不想用；能力目录给出其它窗口的名字。

### 2.6 空闲检测与休息

- 无主体动作 → `idle_heartbeat_count += 1`；仅仅存在 open 线索或外部候选不会重置 idle
- 仅调用 `nucleus_rest_heartbeat`、`nucleus_proactive_query`、`nucleus_todo action=list`，或 `nucleus_learn` 的 help/列表/只读/`status` → 同样计为空闲
- 空闲超阈值 → 触发警告/临界日志
- LLM 可主动调用休息工具进入 `self_pause`（定时跳过心跳）

### 2.7 睡眠与暂停

- **睡眠时段**：`sleep_time` ~ `wake_time` 期间完全跳过心跳
- **主动休息**：LLM 调用休息工具后设置 `self_pause_until`，期间跳过心跳，到期自动恢复
- **检查点**：长时间休息中每 N 分钟唤醒一次让 LLM 重评估

## 3. 主意识表达层（LifeChatter）

**文件**：`core/chatter.py`（4500+ 行）

### 3.1 定位

LifeChatter 是同一主体的**对外运行模式**——真实平台消息、主体显式 `outreach.begin` 后的外联唤醒，或心跳 `inner.return` 交还给 originating 窗口的回声，都会让对应表面的 LifeChatter 读取真实上下文。被唤醒不等于必须发送：表达或沉默仍由该意识实例当轮决定。它与心跳共享身份和记忆，但有独立的 LLM 上下文链（长生命周期 payload）。

### 3.2 唤醒机制

```
真实平台消息 → 适配器 → ChatStream 收集 → start_stream_loop
主体 outreach.begin → 精确 audience+surface 合成未读信封 → start_stream_loop
心跳 inner.return → originating stream 合成内部回声信封 → start_stream_loop
                        │
                        ▼
              route_should_respond()  ← 路由判断
                        │
              should_respond = true（外联/回声 force_reply=false）
                        │
                        ▼
              LifeChatter.execute()  ← 主意识接管
```

合成唤醒信封必须设置 `bypass_message_buffer`，并在入队后调用 `StreamLoopManager.start_stream_loop`；只往未读队列塞信封、不拉起驱动器，等于没有叫醒。内部回声信封不是用户消息，也不进入 outreach 的 `spoke/passed` 结算。信封只服务本轮表达判断：进入 `WAIT_USER` 后从派生滚动投影移除，不把「系统（潜意识回声）」或外联运输信封留进跨轮 payload。权威 Life Event 仍保留完整回声发生。

路由判断使用云端优先的 `router` 任务，判断“这批新消息是否应交给表达层”。Router 仍保留思考预算；延迟优化来自版本化的轻量上下文投影，而不是关闭思考。空正文、畸形 JSON 或调用失败都会继续尝试云端 `agent` 任务，不会把“没有结果”伪装成一次有效判断。

### 3.2.1 内心对话回程

表达层 `inner_dialogue` 把念头沉进 Life Event；`raw_content` 是结构化 JSON（`receipt_id`、`expect_surface`、`stream_id`、`source_instance_id`、`mode`），不靠解析 header 散文。`expect_surface` 只表示允许浮回，不自动叫醒。心跳用 `nucleus_proactive_query(resource=inner_dialogue)` 看到 open receipt，再用 `nucleus_proactive_command(action=inner.return)` 把第一人称回声交还给沉下去的那个 `stream_id`。对人开口仍只走 `outreach.begin`。旧 `nucleus_tell_dfc` 实现类已删除，不在工具池、滚动退役名单、心跳 TOOL.md 清洗名单或 agent 黑名单里留占位；未注册名字走通用未知工具路径，没有 DFC 专用处理。权威历史里的旧调用名不改写。

open set 是可重建投影，心跳 cursor 推进后仍必须能看见。工程上限 32 条 open；满时新的 `expect_surface=true` 显式拒绝。缺 `stream_id` 的 sink 保留念头，但 return fail closed（`missing_stream`）。回声信封不是用户消息，也不写入 outreach claim / `spoke` / `passed`。只有 `core` 心跳可以提交 `inner.return`。

### 3.3 全局运行态

LifeChatter 维护一个**全局 LLM 上下文**（`_GLOBAL_RUNTIME`），所有聊天流共享同一条 payload 链：

- 多流串行：通过 `_GLOBAL_RUNTIME_LOCK` 保证同一主意识不被并发写入
- 长生命周期：对话历史在 payload 中累积，不每次重建
- 上下文连续性：容量压力由系统报告，旧上下文只能由当前主体亲自写下连续性检查点后释放（见 §5）

### 3.4 模型任务

```python
def _configured_primary_task_name(self) -> str:
    # 优先: chatter_task_name（独立配置）
    # 回退: task_name（共享配置）
    # 兜底: "expression"
```

当前配置：`chatter_task_name = "expression"`，以 MiMo-V2.5-Pro 为首选，后续链接 MiMo、Grok、Claude、Qwen 与 Gemini 等已验证云端模型；输出预算为 32000 token，包含隐式思考与最终正文。GPT 5.6 型号仍保留在模型注册表中，但本地中转站没有通过验证的 enabled ability 时不得进入自动任务；恢复渠道并完成端到端探针后才能重新加入候选链。

### 3.5 多模态准入

主意识要求模型必须支持多模态：

```python
def _required_primary_modalities(self) -> set[str]:
    # 基础: {"text"}
    # + image（若 native_image/native_emoji 启用）
    # + video（若 native_video 启用）
    # + audio（若 native_audio 启用）
```

不满足模态要求的模型不会被选为主 request 模型。

### 3.6 Action 系统

LifeChatter 通过 Action（而非普通工具）执行对外表达：

| Action | 功能 |
| --- | --- |
| `LifeSendTextAction` | 向当前表达表面发送文本消息（支持分段与打字延迟） |
| `LifeSendFileAction` | 向当前表达表面发送单个可读普通文件；文件类型开放，通用上限 100 MiB，平台仍可实施更小硬上限 |
| `LifePassAndWaitAction` | 选择不回应，等待下一条消息 |
| `LifeRecordInnerMonologueAction` | 记录内心独白 |

### 3.7 工具调用

LifeChatter 内部可调用所有 `chatter_allow` 标记、且位于该意识工具清单中的工具，包括：
- 记忆工具（`nucleus_search_memory` 等）
- 文件工具、子代理工具
- Web 工具：`nucleus_web_search`（Tavily Search）与 `nucleus_browser_fetch`（Tavily Extract）。二者必须同时出现在 `WEB_TOOLS`、插件 `get_components()` 和 chat 意识工具清单中。统一 dispatcher `nucleus_web` 因 schema 不含 `url`/`query`，不向模型注册。
- 媒体检视工具（`LifeInspectMediaTool`）与附件保存工具（`nucleus_save_media`）
- 主体主动性工具：保存/改写线索、只读查询对象与表面、显式发起外联

学习操作的 16 个 Tool 类仍注册在插件组件里，但 **不在 chat 意识清单，也不再作为心跳常驻 schema**。心跳通过 `nucleus_learn` 跟随 `skills/learning/SKILL.md` 调用它们。本阶段不把 `nucleus_learn` 加入 chat 约 40 件清单。

工具支持**并行执行**（`tool_parallel.py`）：多个独立工具调用可并发。

### 3.8 外部轮次闭合与主体表达选择

消息类型不是认知规则。文字、图片、表情包和其他可观察媒体以同等地位进入 Router 与表达层；代码不得因为某种输入形态预设“通常无需回应”“只应简短回应”或相反地规定“必须回应”。媒体去重、字节预算、格式降级等仍属于工程约束，但不得承担主体判断。

Router 决定将一批外部消息交给表达层后，`_should_force_reply_for_unread_batch` 仅充当轮次闭合保护：避免模型空响应或协议异常把已经接入的真实外部输入静默丢弃。最终表达仍由同一主体在当前上下文中选择：可以原子调用 `life_send_text` 说话，也可以显式调用 `action-life_pass_and_wait` 暂不回应；后者必须是本轮模型作出的可追溯选择，不能由消息类型分类器代替。

旧版曾向“纯表情/图片”批次注入 `<reaction_only_hint>` 并允许空响应提前结束。该规则已经退役。滚动上下文加载、保存和活链规范化只从派生模型投影中移除这段旧传输提示、已退役工具的 LLM 可见名（含 `tool-` / `action-` / 无前缀别名），以及本轮已经结束的叫醒信封。权威消息、正式聊天历史与 trajectory 均不修改。

### 3.9 模型轮预算与失败恢复

`bot.stream_step_timeout` 是一次 Chatter 步进的**端到端总预算**，不是单个模型的超时。默认值为 300 秒，与当前 Provider 单模型 120 秒预算配合，可容纳首选模型超时、一次完整故障转移以及恢复余量。LifeChatter 的内部模型轮预算从该值派生，并固定为外层截止时间预留最多 5 秒，用于取消传播、payload 回滚和 owner 释放；不再存在独立的 90 秒硬上限。WatchDog 的 `stream_restart_threshold` 默认 360 秒，必须严格大于步进总预算，避免恢复路径与 watchdog 重启竞争。将 `stream_step_timeout` 设为 0 或负数会同时禁用这层总预算，单模型调用仍受 Provider 自身超时约束。

模型轮只有成功返回后才会 flush unread、推进运行态上下文游标或进入工具执行。若总预算耗尽：

- 取消仍在运行的模型请求，并把临时 suffix、媒体和 payload 恢复到请求前快照；
- 不消费未读消息、不推进游标，也不把失败伪装成空回复或成功；
- 初始表达轮由下一次驱动继续重试；工具后的 follow-up 则明确标记当前自主任务失败，避免重放已有外部副作用；
- 常规取消只记录 DEBUG，用户可见日志保留一条包含预算和恢复状态的 WARNING，不刷完整 traceback。

## 4. 消息路由（Router）

**文件**：`core/router.py`、`core/router_context_projection.py`

### 4.1 路由决策链

```
新消息到达
    │
    ▼
route_should_respond()
    │
    ├── 读取与当前 SOUL/USER/MEMORY 哈希一致的 Router 投影
    │
    ├── 尝试 router 任务（云端思考模型，8192 token 独立预算）
    │       └── 空正文 / 非法结构 / 调用失败 → 熔断器计数
    │
    ├── 回退 agent 任务（云端模型）
    │
    ▼
返回 SubAgentDecision { should_respond: bool, reason: str }
    │
    └── should_respond=true → 交给同一表达层自主选择发送或显式等待
```

Router 不按文字、图片或表情包建立不同的“应不应该回应”规范；输入形态只影响可观察内容的技术装配。任何新的消息类型默认倾向都必须被视为越过认知边界，而不是产品策略。

### 4.2 上下文预算控制

Router 不再重复注入完整 `SOUL.md`、`USER.md` 和 `MEMORY.md`。表达层仍读取完整权威文件；Router 只读取派生投影、最近 3000 字符聊天窗口和本批新消息。未读消息与系统提示词只做瞬态传输预算收缩，不修改权威历史。

投影生成任务使用 16000 token，足以容纳语义理解、冲突保留与最终 6000 字符上限的轻量投影。输入精简只发生在 Router 派生读模型，不会缩减主体的人格、记忆或任务上下文。

### 4.3 可追溯上下文投影

`RouterContextProjection` 是由 `LifeEngineService` 拥有的可重建读模型：

- 权威源固定为工作空间根目录的 `SOUL.md`、`USER.md`、`MEMORY.md`；投影不反向写入这些文件。
- 面向其他受限意识表面的通用契约见[主体上下文投影](./主体上下文投影.md)：三个文件共同构成主体前缀权威，调用方按 `projection_kind` 与硬字节预算取得逐源可追溯、可固定 revision 的不可变投影；它与 Router 专用判定视图用途独立。
- 每个版本以完整源内容的 SHA-256 寻址，写入 `runtime/router_context_projection/versions/`；`latest.json` 只指向最近一次成功版本。
- 版本清单保留每个源文件的路径、哈希、字节数、生成任务/模型和生成时间；旧版本不会被新版本覆盖。
- 官方写文件工具在完成版本见证后立即唤醒刷新；服务同时轮询外部编辑。刷新由单一后台 owner 串行执行，启动、通知与停止均幂等；生成失败后从 30 秒开始渐进重试，无需再次修改源文件或重启插件。
- 生成失败时保留旧版本用于追溯，但不会把与当前源哈希不一致的旧投影继续送给 Router；健康信息明确标记 `degraded`、新旧 digest、backlog、最后成功时间和失败原因。
- 投影是导航摘要，不是新 persona、长期记忆、事实裁决或跨实例私有上下文。

### 4.4 熔断与降级

专用 `router` 任务连续失败后熔断器临时打开，后续请求先走云端 `agent` 任务。LLM 内核对可恢复故障从 30 秒开始渐进冷却，避免本地中转站一次短暂 503 让整条链持续五分钟不可用。所有任务均失败时采用可观测的“保留工作”降级：消息进入主表达层，由主体决定是否以及如何表达；系统不会伪造 Router 判断，也不会静默丢弃消息。

### 4.5 投递保障（丢失唤醒背板与直接指向快速通道）

Router 是认知裁量的守门层，但“消息能否被她本人看到”是投递事实，不由路由模型裁量。两条保障：

- **直接指向快速通道**：消息经平台层事实判定（`extra.at_users` 对照 `raw_data.self_id`，与 `StreamLoopManager._message_mentions_bot` 同源）确认 @ 了她的账号时，跳过路由模型直接交给表达层；`force_reply` 沿用既有兜底语义。是否回应、如何回应仍由她自己的意识决定。
- **挂起前未读背板**：聊天器回合以 `Wait(time=None)`（等待下一条新消息）终止前，重读未读队列；若存在本回合从未见过的新未读（回合进行期间到达、其唤醒事件已被本回合消费），则在同一驱动内继续推进，连续推进有上限（`_UNREAD_BACKSTOP_MAX_CONTINUES = 5`），达到上限转交下一事件恢复，消息不丢弃。已被本回合处理过的消息不计入，避免重复呈现。

心跳（潜意识层）drain 的 pending 事件队列与表达层未读队列相互独立。唤醒上下文对仍在表达层未读队列中的入站消息附加 `<expression_delivery_status>` 事实段，明确其“尚未经过表达层处理”，防止核心意识误以为“表达层自然会接住”。该标注只报告队列事实，不构成行动建议。

背景：2026-08-29 群聊 @ 消息因“入队落库延迟 + Wait(None) 丢失唤醒”整夜未达表达层，详见 `docs/report/群聊提及消息丢失事故_2026-08-29.md`。

## 5. 上下文装配与主体连续性

### 5.1 三层 Prompt 结构

**文件**：`core/context_assembly.py`

| 层 | 名称 | 生命周期 | 内容 |
| --- | --- | --- | --- |
| Prefix | 前缀 | 稳定 | 身份(soul)、用户画像、记忆、工具规则 |
| Rolling | 滚动 | 累积 | 对话历史、新消息 |
| Suffix | 后缀 | 瞬时 | 本轮运行态（发送前追加，发送后立即剥离） |

### 5.2 主体自述式连续性

**文件**：`core/context_stewardship.py`、`core/context_compaction.py`（退役兼容面）

基础设施不再把任意消息、工具参数或工具结果裁一段后拼成“摘要”。那种做法既不能证明语义连续，也会让系统冒充主体选择什么重要。当前链路严格分成三层：

1. **容量事实**：当当前任务的 token 使用达到配置比例（默认 75%）时，系统只提供一次 `<context_pressure_notice>`。通知含任务预算、稳定 manifest、revision、完整组的 `ctxg_` 引用、字节数和工具链闭合状态，不含消息或工具正文，也不要求主体必须处理。
2. **主体决定**：当前 active consciousness 可在同一模型轮调用 `author_self_continuity_checkpoint`，亲自提交非空 `thought` 和 `continuity_text`，并按通知中的 manifest/revision/ref 明确选择释放边界与原样保留组。系统不从 provider reasoning 推导正文，不补写、不摘要、不判断重要性。
3. **工程硬边界**：窗口或派生快照遇到绝对容量边界时，只能生成 `<mechanical_context_omission>`，其中仅有 hash/ref/计数和继续读取路径；连这些元数据也放不下时宁可给空的派生投影，不能复制片段或伪造语义。

检查点安装前，所有被释放组必须按精确 canonical payload 写入 content-addressed archive；写失败则不释放。主体之后可用 `read_context_group` 依 `ctxg_` 引用按 UTF-8 字节安全分页读取原组。未闭合工具链不能释放，manifest/revision 不一致显式失败，重复命令按稳定摘要幂等处理。

权威 Life Event、trajectory、正式聊天历史和主体文件始终保持完整。滚动上下文只是可重建的模型投影。旧版严格 `<compressed_life_chatter_context>` envelope 只在读取派生快照时被识别并停止续写；普通用户文本即使提到同名标签也不会被删除，读取过程不会主动改写存储，下一次正常保存才写回规范化投影。

完整合同、失败语义和验收矩阵见 [主体上下文连续性与自述检查点](主体上下文连续性与自述检查点.md)。

## 6. 多模态处理

**文件**：`core/multimodal.py`

### 6.1 支持的模态

| 模态 | 格式 | 来源 |
| --- | --- | --- |
| 图片 | bmp/gif/jpeg/png/webp | 消息附件、表情包 |
| 语音 | mpeg/mp3/wav/x-wav | 消息附件 |
| 视频 | 配置启用 | 消息附件 |
| 表情 | 同图片 | QQ 表情消息 |
| 普通文件 | 任意文件类型；不作为原生模型模态 | QQ、KOOK、飞书附件引用 |

### 6.2 处理流程

```
消息附件 → iter_message_attachments() → plan_media() → build_native_content()
                                              │
                                              ▼
                                    PlannedMedia（去重、预算裁剪）
                                              │
                                              ▼
                                    LLM Content（Image/Audio/Video/Text）
```

- 去重：基于内容 hash（`media_dedup_key`）
- 预算：每类模态有最大数量限制（`max_images_per_payload` 等）
- 降级：模型不支持多模态时，媒体转为文本描述占位

## 9. 事件流与状态

### 9.1 统一事件流

兼容运行层仍使用 `LifeEngineEvent`，持久经历边界统一转换为 `LifeEvent` 并通过 `LifeEventBus` 写入 SQLite 追加式账本：

- 账本 ingest position 是耐久顺序，producer sequence 只作为来源字段保留；
- `occurrence_id` 提供幂等写入；
- 消息保留完整原文，兼容心跳展示文本可以单独缩短；
- `source_instance_id`、`causation_id`、`correlation_id` 和 `recorded_at` 保留实例归因与因果边界；
- 心跳通过 cursor 追踪已处理事件，新事件在下次 prepare 中形成固定快照；
- 显著性只负责技术注意预算，不能删除或改写原始经历。

意识实例生命周期先在 `consciousness_presence.sqlite3` 中原子提交 Presence、stream owner 和 outbox，再幂等写入 Life Event。账本写入失败时 outbox 不确认，后续可重试。

### 9.2 状态持久化

`StatePersistence` 负责将运行态写入 workspace：
- 心跳计数、空闲计数
- 事件游标、待处理事件
- 对话历史
- 主体主动性只保存在 service-owned Runtime Event Store 的不可变 decision ledger；不写入此运行快照

意识实例运行状态不再由 `StatePersistence` 或 JSON 负责。`SQLitePresenceStore` 单独保存：

- instance/session/process epoch；
- active/suspended/terminated 与 lease；
- active stream 唯一 owner；
- revision/CAS 与生命周期 outbox。

`runtime/consciousness_registry.json` 仅是迁移期兼容导出；`runtime/consciousness_presence.sqlite3` 才是权威 Presence。`runtime/world_projection.sqlite3` 是从不可变 Life Event 重建的带来源派生投影；旧 `world_state.json` 只作为迁移源保留。
