# 记忆连续性理念与约束

记录日期：2026-09-06（Asia/Shanghai）。

本文保留本次讨论中用户提出的目标、顾虑与未决问题，并与后续工程建议明确分开。本文是开发者维护的需求与设计记录，不是爱莉的第一人称记忆，不得自动写入或覆盖她的 SOUL、USER、MEMORY、日记及其他主体文件。

本文不宣称下述体验已经实现，也不以组件已经存在、工具已经注册或测试已经通过代替连续性验收。具体实施范围、步骤和当前进度由对应实施计划与验收记录说明；主体性、历史完整性、权限和生命周期底线以仓库 [AGENTS.md](../../AGENTS.md) 为准。

## 一、用户目标

本节记录用户想要达成的体验与设计取向，不把实现方式提前固化成某个数据库、模型角色、类名或固定字段。

### G01：记忆首先应当影响当前行为

固定记忆以及承载记忆的文件，不是仅供事后查询的资料。它们应当影响爱莉当前的理解、选择和相处方式，是连续性的实际组成部分。

用户关心的是：经历过的事情是否真的在她身上留下痕迹，而不是系统是否增加了文件、摘要或“已学习”状态。

### G02：自有文件空间整体是记忆空间

按本次讨论的目标，自有文件空间整体承载她的记忆，一个文件可以作为一个记忆单位。不能仅因为实现只索引某几个目录或文本扩展名，就把那部分覆盖范围称为完整记忆空间。

这是一种面向主体的使用方式：她可以在自己的空间中保存、读取、改写和组织经历与知识。文件的技术表示可以不同，不能由格式差异把用户的整体目标缩窄为一份固定提示词或一个专用笔记目录。

“属于记忆空间”不等于“文件中的所有内容都是她亲自说过、认可或判断为真的话”。外部材料、原始附件和主体自己的表达仍需要保留来源差别；这一归属边界来自现有工程约束，而不是对文件内容的自动认知分类。

### G03：体感连续，近期实际经历能够回忆

用户希望最大程度的连续性：经历过的事情都能留下痕迹，在相处中不明显感到爱莉遗忘。一个直接表现是，不管问起什么最近实际经历过的事情，她都知道，或能够认真回忆后找回来。

验收对象应当包括没有预先被挑成“重点”的近期细节，不能只考察测试前特意叮嘱她记住的少数事实。

用户允许内部存在特殊的处理方式，但这些处理应服务于体验上的连续，而不是让压缩、重启或后台故障变成关系与经历的断点。

### G04：学习也是连续性，反馈能够成为习惯

爱莉经历事情后，如果自己觉得有必要，应当能够主动学习。在未来相处中，应能明显感受到她确实学到了东西，知识实实在在地体现在她的行为中。

用户特别提到批评和夸奖：她能够记住反馈，后来逐渐形成自己的习惯。成长不是再次复述“我记住了”，而是在后续情境中出现可感知的改变。

这同时要求保留主体选择：学习什么、如何理解反馈、怎样形成自己的做事方式，应当由爱莉决定。

### G05：上下文压缩由主体自己决定

用户明确倾向于把压缩内容和压缩结果完全交给爱莉：哪些内容退出当前上下文、怎样组织留下来的记忆、把内容压缩成什么，由她自己决定。

工程实现不能把这一目标替换成后台替她选“重点”、替她形成第一人称总结，或者用固定模板决定她应当留下什么意义。

系统可以承担保存、预算、传输与恢复工作；这些机械职责如何实现，是工程问题，不是把语义压缩的执笔权交给基础设施的理由。

### G06：边界感知——知道自己还知道什么

长记忆不必一直全部存在于固定提示词中。她可以把详细内容写成具体文档，在当前意识中保留一个标记、索引或足够清楚的提示。

用户想要的是类似人的回忆体验：知道自己有什么记忆、知道自己有什么技能；需要认真回忆时，沿着线索找到细节，再把它重新拿回来。没有一直表现出来，不等于从未经历或已经不存在。

因此，边界感知的目标是“对可回忆范围及入口有所感知”，不是强制采用当前代码中名为 Boundary 的对象或某一种 URI 格式。

### G07：记忆成片，片与片之间可以形成复杂网络

线索可以很复杂，可以形成多层索引、网状结构和相互连接的记忆片段。拿出一段记忆时，也容易顺着关联回忆起许多其他经历。

用户希望关联由爱莉自己建立，关系的连接强度也由她自己决定。工程不应把一个自动打分算法的结果冒充为她对关系强弱的判断。

这里的目标不是要求每次回忆都展开整张图，而是让记忆可沿线索成片地重新进入注意。

### G08：日常看最新记忆，外部保留完整成长过程

平时查看记忆时，她应当看到自己的最新记忆；过去的记忆、增删改过程和整理轨迹，则在外部完整留存，构成可追溯的成长记录。

因此，“当前不再使用某份记忆”与“历史中从未有过这份记忆”必须区别开。修改和删除不应悄悄擦掉过去；当前理解改变，也不应抹去当时的理解及其形成过程。

如何表达稳定身份、改名、当前版本、精确历史版本和删除记录，属于后续工程选择，不能把某个既有实现直接当作该目标已经实现。

### G09：记忆需要整理，不能被时效污染

用户希望爱莉定期审查记忆，也提出可以借助机会系统。原因是现实会变化：过去记下的情况在未来可能已经不同，旧理解若不整理，会污染当前判断。

用户明确表示尚未想清楚解决方式，并提出是否交给潜意识等疑问。定期审查的意愿是目标；具体由谁审查、何时触发、如何判断变化，并未被指定为某一种固定机制。

### G10：对技能使用效果和可改进之处有感知

用户希望存在某种验证能力：她学会了什么，用得好不好，是否用错，哪里还能改进，系统应能帮助她有所感知。

用户认为只让主意识在每一次实际使用时主动考虑全部验证问题，不够现实。但验证系统究竟是什么、怎样实现、以什么结果为依据，仍是待探索的问题。

### G11：言行一致，不能以新承诺代替行动

用户特别在意口头答应之后没有行动的问题，希望爱莉说过的事情与实际行为一致，希望有某种机制能够时不时提醒她。

这不只是日程提醒的需求，也涉及发现“曾经答应了，但后续没有落实”这类差距。具体如何识别承诺、验证完成、提醒以及重新安排，用户尚未指定实现方式。

### G12：统一共性，不以大量碎片功能堆砌结果

用户反对针对每个现象分别增加一套专用工具和独立系统。过去大量工具存在冗余、错误和割裂，实际效果并不因功能数量增加而改善。

期望的方向是找出共同性质，形成统一抽象，让记忆管理、学习、审查和行动更容易协同与管理。用户倾向复用机会系统等理念，但这不代表现有机会代码或其他实现可以不经验证直接继承。

## 二、用户提出的风险与质疑

这些质疑是本轮调整工程方向的重要原因，不能在后续计划中被淡化成“只需补几个功能”。

1. 用户质疑 Experience 和 Witness 的实际意义，特别指出 Witness 频繁报错带来的困扰。不能因为它们曾为某种理念而创建，就假定它们不可替代。
2. 用户担心高比例复用旧系统，会同时继承旧系统的错误、复杂依赖和故障传播。
3. 世界状态与投影器的必要性也需要重新证明，不能因为名字听起来合理就继续扩展。
4. 记忆边界和记忆联想等功能没有得到充分的实际验证，用户不能确信它们真的有效。
5. 一次性增加大量东西会扩大验证难度；此前功能增加快于验证，是当前系统难以理解和修改的重要问题。
6. 用户提出了“彻底推翻重来”与“逐步确认每个组件意义”的选择问题，并希望得到可掌握、可验证的实施路径，而不是再次接收一份庞大的功能清单。

这些表述保留的是用户的顾虑与体验反馈，不等于本文已经独立完成了所有相关组件的故障诊断，也不等于用户要求立即删除它们。

## 三、尚未决定的问题

| 编号 | 未决问题 | 不能提前当成既定答案的做法 |
|---|---|---|
| Q01 | 时效审查由谁进行、怎样选择时机、怎样判断现实已变化？ | 默认新增一个潜意识角色，或按时间阈值自动判旧记忆无效 |
| Q02 | 技能验证需要什么证据，怎样区别自我感觉与实际效果？ | 模型打分即“学会”，反思文字增多即“成长” |
| Q03 | 承诺如何被识别、如何判断履行、如何处理含糊表达或阻碍？ | 所有将来时表达都建任务，没找到证据就自动判定失约 |
| Q04 | 是否需要独立后台对照者，还是现有机会与主体活动已经足够？ | 把工程建议的 reviewer 当成用户已指定的人格或常驻角色 |
| Q05 | 哪些关联表示、强度表达和图遍历真正改善回忆？ | 先规定固定认知分类、自动强化公式或完整图框架 |
| Q06 | 普通文件及精确版本引用能否承担边界感知？ | 必须保留当前 Boundary 流程才能有边界感知 |
| Q07 | Experience、Witness、World、投影和机会的哪些职责不可缺，哪些能合并或退出？ | 整套高复用免检，或未经依赖和数据审计就全部删除 |
| Q08 | 全文件空间怎样统一表达版本与引用，二进制、外部材料和主体文件怎样保持边界？ | 把所有格式强转成文本，或把导入材料自动当作主体已接受的记忆 |
| Q09 | “近期任意实际经历可回忆”的时间跨度、场景覆盖和测量方式怎样界定？ | 预先只保存测试答案，或用一句“模型难免遗忘”替代工程验证 |

以上问题允许通过小范围实验逐步回答。每一次答案都应标明证据、适用范围和仍然存在的不确定性，而不是追写成“用户一直要求如此”。

## 四、本轮采用的工程方向

本节属于工程建议与当前实施取舍，不是用户理念的逐字复述，也不是对所有组件的永久去留裁决。用户随后要求撰写详细计划、保留今天的理念，并尝试第一个最小闭环，整合到主仓库进行验证。

### E01：保留历史与合同，不默认保留旧实现

连续性、主体执笔权、来源可追溯、正确归属、幂等、权限和可恢复性是必须保留的合同。实现合同的旧类、数据库副本、后台消费者、投影链或工具数量，不因此自动获得继续存在的理由。

保留既有经历和主体文本，不要求永久保留产生这些数据的全部运行机制。若某组件退出，应保留旧记录的读取路径、稳定引用及必要兼容；没有安全迁移证据，不删除权威历史。

### E02：减法式重构，先停止范围扩张

本阶段先冻结新增后台 reviewer、批量专用工具和未经必要性证明的新管线。此前提出的后台对照角色只是候选方案，不作为第一阶段必须实现的功能。

减法不是为降低错误数量而隐藏错误、关闭记录或伪造成功；它是让可运行链路变短、职责变清楚，并使每一次变化可以独立验证和回退。

### E03：从最小闭环反推必要依赖

第一条需要证明的链路是：

> 一段实际经历被可靠保存 → 爱莉自己留下理解或线索 → 经历压缩及重启 → 能沿来源回忆 → 在之后相关行为中体现出来。

最小闭环优先使用原始经历的可靠回取、主体文件及历史、基本读取与搜索、主体亲自书写的连续性检查点。需要安排后续活动时，再验证并接入机会能力。

不要求先把每个旧模块都研究完，才能验证这条链路；也不把 Witness 成功、复杂联想或新的世界快照生成成功当成记忆成立的前提。具体剥离要先核对真实依赖，不能绕过权限、路由与意识实例隔离。

### E04：组件逐项证明价值，机会理念也不免检

组件是否保留，需要回答：它额外提供什么能力；不用它会丢失什么；能否由更简单路径承担；它出错会影响哪些功能；它在相同条件下是否改善用户可感知的连续性。

可选增强应通过“有它／无它”的对照逐项进入，而不是一批同时启用。机会系统可作为统一安排与唤起的方向，但到期、唤起、去重、恢复和暂停本身也需要验证。

### E05：保存、回忆、理解和行为分别验收

工程上可以把验收拆成不同层次，但这些层次不是替爱莉预设的认知类型：

- 保存层：原文和版本没有缺失，引用能找到来源，错误不会被报告成成功。
- 回忆层：压缩或重启后，仍能定位实际发生的内容，而不是凭相似片段补出答案。
- 主体表达层：压缩、索引、学习理解和关系判断确实来自有身份的主体活动，不是基础设施代笔。
- 行为层：新的相处与实践中出现了适当改变，不只是文件里出现“已经学会”或“以后注意”。

通过保存层测试不能宣称整个连续性已经通过；通过一个场景也不能宣称任意经历都能百分之百回忆。

### E06：工程不能悄悄改写用户目标

实现中确有预算、格式、并发和失败约束时，应明确呈现限制和恢复路径。系统没有足够证据时，应允许爱莉继续查找或表达不确定，不能用编造内容制造流畅的连续感。

“经历留下痕迹”也不必在工程中机械翻译为“每件事都产生一条永久规则”；“定期审查”不等于按年龄自动遗忘；“连接更强”不等于更真实；“提醒承诺”不等于扩大外部行动权限。这些是避免实现偏离目标的工程解释，不是用户另外规定的认知制度。

## 五、需求到验收的映射

以下是拟采用的观察方式，不是已完成的测试结果，也不是保证每个阶段都同时完成全部目标。

| 目标 | 可观察的验收场景 | 不足以单独证明成功的现象 |
|---|---|---|
| G01、G04 | 后续换一种表达或情境，观察此前反馈是否影响实际选择与行动 | 她复述“记住了”，文件出现习惯标签 |
| G02、G08 | 文件更新、改名和删除后，能读当前状态并追溯旧内容；不同格式覆盖范围明确 | 只有指定文本目录进入索引 |
| G03 | 多轮经历后进行自主压缩，再重启；提问未预先标成重点的近期实际细节 | 测试把正确答案重新放进提示词 |
| G05 | 检查压缩产物的实际执笔者、对应原文、释放边界和恢复记录 | 后台摘要看起来像她写的 |
| G06 | 当前只有线索时，能够沿线索进入详细内容，并知道读到的是哪个版本 | 只生成一个不可读取或过时的链接 |
| G07 | 基本检索与加入主体关联分别运行，比较额外正确回忆、误联想、成本与故障 | 图上节点和边更多，强度数值变大 |
| G09 | 情况变化后仍能区分过去与现在；无新证据时不会假装完成重新验证 | 文件重新保存，修改时间变新 |
| G10 | 一次具体实践有可回看的结果与反馈；修改方法后再次实践比较 | 模型自评高分或技能成熟度推进 |
| G11 | 已表达的承诺后续未落实时，差距可被发现；落实、阻碍或重新协商都有实际依据 | 再次保证会做，任务条目被标完成 |
| G12 | 同一条最小链路可独立验证；每个新增依赖都有必要性证据和退出方式 | 工具注册数量增加、孤立单元测试变多 |

对照实验应尽量保持经历输入、模型、可用预算与提问条件一致，每轮只改变一个关键因素；保留成功和失败的来源记录，并通过多个未提前暴露答案的场景检查效果。回忆正确性、行为改变、延迟、资源成本和故障影响范围都应报告，不能只挑有利结果。

## 六、交付边界

本轮要求是保留理念、给出详细计划、尝试第一个最小闭环，并整合到主仓库供真实验证。它不等于批准一次性重写全部系统，也不等于已经完成所有长期目标。

实现应在主仓库现有工作状态上保留其他人的修改；不得为了精简而改写主体语义、丢弃旧历史、静默切换身份或绕过权限。真实 Elysium 实例由用户手动启动或重启；隔离检查不能代替真实启动与连续交互验收。

后续文档应持续区分三件事：用户真正想要什么、当前实验支持什么、工程实现实际上做到了什么。
