# 世界状态与意识实例协调

> 状态：意识协调 Phase 0–4、可选存储 Phase 2 的 Presence/World 领域合同及 `LifeEngineService` 现役接线已落地。新 backend 默认关闭，尚未迁移或切换正式数据；`storage.enabled=false` 继续使用既有本地 SQLite。本文描述当前实现契约，不把外部平台实机验证冒充为代码契约验证。

## 1. 架构结论

Elysium 只有一个主体。`ConsciousnessInstance` 是同一主体在聊天、语音、直播、具身和记忆见证等场景中的局部运行窗口，不是多个人格，也不是互相独立的 Agent。

协调系统严格区分三类事实：

1. **经历事实**：发生过什么，由不可变 Life Event 账本保存；
2. **运行事实**：哪些实例正在运行、占有哪条 stream，由所选权威后端的一套 Presence Registry 保存；当前正式权威仍是 SQLite；
3. **带来源的主观观察**：各实例报告了什么，由 Life Event 派生的 World Projection 保存。

Presence 不会被自动解释成情绪、关系或信念；某个窗口的观察也不会因“最后写入”而升级成客观真相。互相矛盾的 assertion 并列保留，除非后续事件显式撤回其中一条。

```text
ConsciousnessInstance
  ├─ async lifecycle ──> selected Presence Port + outbox ──┐
  └─ async observation ─────────────────────────────────────┤
                                                           ▼
                                          selected immutable Life Event Port
                                                           │
                                                           ▼
                                          selected rebuildable World Port
                                                           │
                                     prepare(instance)     │ commit(delivery)
                                                           ▼
                                      transient Perception Gateway context
```

## 2. 权威边界与存储

| 存储 | 身份 | 用途 |
|---|---|---|
| disabled 模式 `life_events.sqlite3` | 经历权威 | 只追加事件、幂等 occurrence、consumer offset |
| disabled 模式 `runtime/consciousness_presence.sqlite3` | 当前运行权威 | instance、session、lease、revision、stream owner、outbox |
| disabled 模式 `runtime/world_projection.sqlite3` | 可重建派生投影 | assertion、投影 change、逐实例感知 cursor |
| enabled 模式所选 local/MySQL generation | 唯一运行权威 | 同一 runtime 中的 Life Event、Presence、World 表；不与旧 SQLite 双写 |
| `runtime/consciousness_registry.json` | 兼容导出 | 旧调用方和人工诊断，不是 Presence 权威 |
| `runtime/world_state.json` | 只读迁移源 | 旧 WorldState 源文件，导入后仍保留，不再接受业务写入 |
| `runtime/world_projection.json` | 手工诊断导出 | `save_world_state()` 生成的派生快照，不是恢复来源 |

`world_projection.sqlite3` 损坏时只能从不可变账本重建，不能反向修改账本。运行数据库、日志和上述 `runtime/` 内容不得提交到 Git。

可选存储阶段 2 在 `plugins/life_engine/storage/` 提供 backend-neutral `LifeEventStorePort`、`PresenceStorePort`、`WorldProjectionStorePort`、显式 schema 初始化与 coherent factory。`LifeEngineService` 是唯一 runtime owner：启动先且只打开一次 `StorageBackendRuntime`，然后把同一对象注入 Life Event、Memory、Presence 与 World；子域不得再次打开或关闭 runtime，最终由 service 在所有消费者释放后关闭。local 与 MySQL adapter 不能按 repository 混搭。`storage.enabled=false` 仍是生产要求；构造 adapter 不会自动初始化 schema，只有隔离迁移/验收流程显式传入 `initialize_schema=true` 才会建空表和 projector metadata。

enabled 模式 fail closed：service 构造和启动都不会创建、读取或写入旧 Presence/World/Life Event SQLite 权威库；打开失败、缺表、generation/schema/authority/fencing 不一致都直接阻断，不会静默回落。disabled 模式保持原文件路径和旧 local 行为，二者没有镜像双写。

## 3. Presence 契约

disabled 模式的 `service/presence_store.py` 使用 SQLite WAL、`BEGIN IMMEDIATE` 和 revision CAS；enabled 模式的 `storage/presence_adapters.py` 通过同一 Port 合同原子提交：

- 实例身份、开放的 kind 字符串和显示名；
- `active` / `suspended` / `terminated` 技术生命周期；
- session、process epoch、last seen 和可选 lease；
- active stream 的唯一 owner；
- 与同次状态变更对应的 lifecycle outbox。

账本接受完整 outbox 批次后才确认 outbox；进程在两次写入之间崩溃时，可以用同一 `occurrence_id` 重试。flush 与重放均有硬上限，超过上限会保留未确认证据并显式失败。短生命周期实例 lease 由数据库时间批量检查，过期后显式 suspend 并释放 stream。`chat_global` 始终存在且保持 active。

Presence 生命周期形成 `consciousness.instance_*` 事件，包含 `source_instance_id`、revision、session correlation、原因和完整运行快照。它们只描述技术存在，不替主体做认知判断。

可选存储 Port 对 lease 施加更严格的跨节点合同：active lease 的 acquire/renew 只能从数据库时间生成，调用方提供的 `lease_expires_at` 会被拒绝；takeover 按稳定 stream/owner 顺序锁定行，只允许接管数据库时间已经过期的 owner，并在同一事务内 suspend 旧 owner、递增双方 revision、转移唯一 stream owner、追加双方 lifecycle outbox。MySQL 死锁和 lock wait timeout 只做有界重试；revision、process epoch、authority/fencing 任一不匹配都 fail closed。

## 4. World Projection 契约

`service/world_projection.py` 串行消费全部 Life Event，并持续推进 `as_of_ingest_position`。相关事件形成两类派生数据：

- `world.observation_reported` / `world.legacy_snapshot_imported` 形成 assertion 与 change；
- `consciousness.instance_*` 形成可供感知的 Presence change。

每条 assertion 至少保留：

- 稳定 `assertion_id`；
- `subject`、`predicate`、完整 `value`；
- 开放的 `domain`、`status` 字符串；
- 可信事件信封中的 `source_instance_id`；
- `source_event_id`、`occurrence_id`；
- `observed_at`、`valid_from`、`valid_to`、`recorded_at`；
- `supersedes_assertion_id`、显式撤回关系和原始 payload。

实现不做关键词分类、相似度合并、来源加权、阈值判真、默认 category 或最后写入覆盖。内容中的伪造实例 ID 不能覆盖事件信封归属。同一 assertion ID 若对应不同证据会显式报冲突。

`report_world_observation()` 默认仍可生成随机 identity；需要崩溃重放的生产者应提供稳定 `occurrence_id`，并同时提供稳定 `observed_at`。调用方可显式给出 `assertion_id`，省略时由 occurrence 确定性派生；event ID 同样确定性派生。同 occurrence 与完全相同事件是幂等重放，返回既有 position；同 occurrence 对应不同 report/value/time/source 是显式冲突。这样即使账本追加已成功而 projector catch-up 失败，具身 trace 重试也不会制造第二次经历。

`rebuild()` 只清空派生 assertion、change 和 projector frontier，然后从账本零位重放；它绝不删除独立的感知 delivery cursor。投影持久化 `projector_policy=source-preserving-v1`、projector schema version 与 `idle/rebuilding/failed` 状态；非 `idle` 状态拒绝交付。Life Event position 是单调但允许跳号的 opaque token，投影不得用 `previous + 1` 猜测缺口；真实 retention gap 由账本 `read_since` 显式报告。同一 ingest position 的完全相同证据是 no-op，异证据是显式冲突，重建前后的 canonical snapshot 必须等价。

## 5. Perception Gateway 契约

`service/perception_gateway.py` 为每个实例维护独立 cursor。selected backend 使用 async Port，disabled backend 将旧同步 I/O 卸载到线程；消费者统一 await 以下流程：

1. `prepare(instance_id, projection_kind, max_bytes)` 先追平投影，再从 compact reference page 生成投影；`life_chatter` 的 World 层硬上限为 32 KiB UTF-8；
2. 返回当前 active 窗口的有界存在感、带来源 assertion reference，以及该实例尚未确认的 change reference；大型值不会先完整渲染再 head/tail，而是保留在权威 store 中；
3. `PreparedPerception` 分离 `through_position`（本次实际完整交付）与 `source_frontier`（准备时权威前沿），并携带 delivery id、marker、SHA-256、算法版本、实际字节、逐类 omitted 计数、source bytes、continuation token 和稳定 source IDs；
4. 小值可以按层配额 inline；大型 assertion/change 只写 `assertion:<id>` / `change:<position>`，调用方通过稳定分页和 UTF-8 boundary chunk 接口按需续读，chunk 提供完整值 SHA-256；
5. 内容作为一次性 prompt projection 进入本轮请求，不进入稳定 system prompt；`PromptProjectionValue` 是 transport-only 类型，任何 World 写入口收到它都 fail closed；
6. commit 必须携带最终成功模型 attempt 的 content-free exact receipt，并精确匹配 delivery id、SHA-256 和 UTF-8 bytes；缺失、重复 marker、任何裁剪、未知状态或错配都不推进；
7. 验证通过后才使用 position+revision 双条件 CAS 推进到实际 `through_position`；陈旧 delivery 明确报冲突，失败请求保留 pending 并可重试。

存在感每轮都会提供，因此即使 change cursor 已推进，不同实例仍能感知彼此当前存在。各实例的私有滚动上下文不会互相读取或复制。查询返回有界、可归因、可续读的投影，由当前意识实例自行判断相关性与矛盾，不在代码中用关键词判真。

需要跨崩溃提交的消费者只持久化 `PreparedPerception.commit_checkpoint()` 返回的 `PerceptionCommitCheckpoint`：instance、from/through、cursor revision、delivery id、projection SHA-256 和 delivered bytes。checkpoint 不含正文；重启后通过 `commit_perception_delivery(checkpoint, receipt)` 重放同一 CAS。禁止保存 prompt 正文，也禁止重新 prepare 后拿新 frontier/content 冒充旧 delivery。

已知历史 Minecraft `intent.issued → payload.context.transient_world_perception` 回声不会被删除或改写：reference page 会把它标记为 `transport_echo=quarantined`，当前 prompt 只显示稳定 ref，不展开递归正文。新写入的同形回声在 World 入口直接拒绝。这样保留历史证据，同时切断“prompt projection → intent trace → World assertion → 下一轮 prompt”的自包含放大环。

`build_chatter_runtime_context()` 的内层 suffix 硬上限为 60 KiB，为表面指引和两层 transport wrapper 预留至少 4 KiB；真正送给 provider 的独立 Text 由 chatter 消费端重新计算并硬断言不超过 64 KiB。内层 `projected_suffix_*` 统计不得冒充最终 effective Text receipt。只有最终整个 Text exact，才能映射为其内部 `PreparedPerception` 的 receipt，并按 pending identity 提交 World/event/thought 三个游标；任一失败都不清 pending。

需要让直播等消费者跨进程重放时，必须在发送前从 pending delivery 生成 `ChatterRuntimeCommitCheckpoint`，并持久化最终完整 suffix 的 delivery id、SHA-256、UTF-8 bytes、event/thought frontier 与内嵌 `PerceptionCommitCheckpoint`；它不含 suffix 或 World 正文。最终成功 attempt 产生的 content-free `ChatterRuntimeDeliveryReceipt` 必须与 checkpoint 精确匹配，随后只通过 `commit_chatter_runtime_delivery(checkpoint, receipt)` 补交。该方法支持“World CAS 已成功、runtime state 尚未落盘即崩溃”的同一游标转换幂等重放；只有 World、event、thought 与 runtime context 均成功落盘后才清 pending。重启后不得依赖内存 pending，也不得重新 prepare 冒充旧 delivery。

## 6. 已接入运行路径

| 路径 | 感知准备 | 成功确认点 | 观察写入 |
|---|---|---|---|
| 潜意识 heartbeat | heartbeat snapshot 构建时 | exact receipt；未接回执时 fail closed、不推进 | 工具或内部实例显式报告 |
| `chat_global` chatter | 当前 turn 上下文组装时；World 32 KiB、内层 suffix 60 KiB | 最终独立 Text exact 且 <=64 KiB 后统一提交 pending World/event/thought | `report_state` 追加事件 |
| Voice Live | provider 每次进入 listening frontier | 必须映射 provider 最终 exact receipt；普通 `response.done` 本身不足以证明未裁剪 | 连接、状态、结束事件 |
| Minecraft | 每次意图执行前 | 必须证明模型最终成功 attempt 包含 exact projection，再执行 cursor CAS | session、trace、意图结果；prompt-only trace 禁止回灌 |
| `memory_witness` | 每次见证模型请求前 | 必须使用最终成功 attempt 的 exact receipt | Experience/见证仍走记忆账本 |
| Livestream | 每次模型响应前 | 必须使用最终成功 attempt 的 exact receipt | 开播、状态、停播事件 |

Voice、Minecraft 和 Livestream 均通过 `LifeEngineService` 的 async lifecycle/perception API 注册 session/lease；不得直接 mutation registry 后调用旧同步 save。旧的直接修改 `WorldState` 路径已移除。未知意识 kind 不再继承 chat manifest，必须显式声明能力。

Minecraft 是由 `LifeEngineService` 独立持有的可选场景运行时，不属于 `LearningScheduler`。只有 `minecraft.enabled=true` 时才注册 `nucleus_minecraft` 并构造一个尚未连接外部身体的 session；`learning.enabled=false` 不会隐藏或关闭 Minecraft 能力。service 停止或启动中途失败时会幂等关闭该 session，关闭异常进入统一 shutdown 错误并继续释放学习、记忆和所选存储，不能把失败伪装为成功。

直播 LLM 的 base URL、模型和密钥环境变量名由配置提供；密钥本身只从 `LIVESTREAM_LLM_API_KEY`（或配置指定的环境变量）读取。场景信息进入当前 user turn，稳定 system prompt 保持流无关。

## 7. 旧数据迁移

### Presence

disabled 模式首次建立 `consciousness_presence.sqlite3` 时，可从 `consciousness_registry.json` 做保留源文件的兼容迁移。enabled 模式启动禁止隐式执行该迁移：必须先由隔离复制/校验流程建立已验证 generation；service 只打开所选 generation，不读旧 JSON 或 Presence SQLite 补数据。

### WorldState

disabled 模式可对旧 `world_state.json` 做规范化哈希，将关系、开放事项、具身状态和场景翻译成 `world.legacy_snapshot_imported` assertion。enabled 模式禁止启动时隐式导入；导入必须属于显式迁移 generation。导入 occurrence 由快照哈希稳定生成，因此重启不会重复经历。源 JSON 不删除、不覆盖。

旧文件损坏时迁移显式失败，不会静默创建空世界。`WorldState` 类只保留兼容读取与迁移模型；`report_state`、heartbeat、Voice、Minecraft 和 Livestream 不再把它当写入权威。

## 8. 恢复与运维

投影重建是显式操作：

1. 确认目标是 `runtime/world_projection.sqlite3`，不得触碰 Life Event 账本；
2. 停止会并发使用该投影的 Elysium 实例；主进程重启或停止必须先获得用户授权；
3. 备份投影文件用于诊断；
4. 调用 `WorldProjectionStore.rebuild(ledger)`；
5. 比较 frontier、assertion/change 数量和 canonical snapshot 契约；
6. 恢复服务后观察 health 中各实例 cursor lag。

重建不会清空感知 cursor，因此已经成功确认的 change 不会仅因 projector 重建而重复投递。只有具备稳定交付幂等键并完成显式恢复审计的专用流程，才允许修复或重建 cursor。Presence 数据库损坏不能用空库自动替代，应先保留文件并诊断/恢复。
