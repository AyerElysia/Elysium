# 生命记忆系统 v3：长河·活忆闭环

> 文档状态：权威架构，与 2026-08-04 的实现同步。
> 代码入口：`plugins/life_engine/service/event_bus.py`、`plugins/life_engine/memory/experience.py`、`epistemic.py`、`living.py`、`service.py`、`service/memory_witness.py`、`plugins/life_engine/storage/memory/`。
> 运维与迁移见 [活体记忆迁移与健康检查](../operations/living_memory_migration.md)。

## 0. 定位

记忆不是一份会被覆盖的文本，也不是“重复越多就越真”的权重网络。它由两类结构共同组成：

- 不可变历史：发生过什么、何时记录、谁如何解释、一次回忆看见了什么；
- 可重建投影：当前文件头、全文索引、向量索引、共同回忆形成的可达性。

主体可以改变理解，但系统不能替主体删掉旧理解。回忆会改变以后更容易想起什么，却不能自动改变事实状态。

## 1. 不可妥协的约束

1. 真实经历进入统一事件长河；事件位置在进程重启后仍单调递增。
2. 原始事件、Experience、claim、证据、解释、版本和回忆轨迹只追加，不原地改写。
3. 文件当前内容、FTS、Chroma、artifact head 和 association projection 都是派生状态，必须能从账本重建。
4. 来源、权限、关系、检索意图和回忆动作使用开放文本；代码不按关键词、枚举或相似度阈值替意识作认知判断。
5. 检索排名、重复次数、共同出现次数和学习系统分数都不是事实置信度。
6. 冲突、旧看法和后来重新解释必须同时可见，不能用“最新一条”静默覆盖历史。
7. 任何迁移缺口必须显式失败或报告，禁止把游标直接跳到当前尾部。

## 2. 分层架构

```text
外部消息 / 工具 / 心跳 / 场景事件
              │
              ▼
RawEventStore: life_events.sqlite3
  durable ingest_position + occurrence_id + consumer offset
              │
              ▼
Experience ledger ── Memory Witness
              │              │
              ├──────────────┤
              ▼              ▼
 Epistemic ledger       Living-memory ledger
 claim/evidence/state   artifact/interpretation/recall/corecall
              │              │
              └──────┬───────┘
                     ▼
       Unified evidence-aware retrieval
          FTS + vector + provenance
          + contextual stochastic recall
```

当前正式运行仍由 local SQLite 账本承担权威；只有经过快照复制、校验、generation 登记和人工切换后，所选 active backend 才能成为该 generation 的唯一权威。JSONL、工作区兼容文档、FTS/FULLTEXT、Chroma 和旧 `memory_edges` 都不拥有最终历史权威。

## 3. 耐久事件主干

`RawEventStore` 的权威文件是工作区中的 `life_events.sqlite3`。核心表：

- `raw_life_events`：`AUTOINCREMENT ingest_position` 是全局消费位置；
- `raw_event_consumer_offsets`：每个消费者独立、单调提交游标；
- `raw_event_store_meta`：迁移元数据；
- `raw_event_import_issues`：旧 JSONL 解析或镜像写入问题。

每条事件同时保留：

- `occurrence_id`：一次真实发生的稳定身份，用于幂等重放；
- `source_event_id` 与 `source_sequence`：生产者原始身份和进程序号；
- `ingest_position`：跨重启、跨生产者的权威消费位置；
- 完整 payload 与 hash。

旧 `life_events.jsonl` 及轮转归档会在首次打开时按从旧到新顺序幂等导入。JSONL 此后只是兼容镜像；镜像轮转可以删除旧归档，但不能删除 SQLite 中的事件。重复 occurrence 返回原位置；同一 occurrence 携带不同内容会以身份冲突失败。

## 4. 经历与见证

`memory_experiences` 保存全部被消费的原始事件证据，不再用固定事件类型白名单判断“什么算经历”。`source_event_id` 保留生产者事件身份，Experience 自身使用 occurrence 身份，允许同一来源下不同真实发生共存。

`memory_experience_occurrence_aliases` 用来把历史 Experience 与新 occurrence 身份连接起来，避免升级后重放制造副本。

`memory_witness` 是第一人称见证意识：

- 从耐久 consumer offset 继续读取；
- 所有源事件先进入 Experience，见证意识再判断哪些值得形成日记；
- 见证实例维护自身 Presence 所产生的精确协议事件仍完整进入 Experience，但不会再次进入同一见证实例的创作窗口；纯自维护批次会正常提交游标并记为 `suppressed_self_echo_events`，不调用模型、不生成循环日记；
- 上述边界只按生产者、通道、意识实例与 Presence 协议事件类型联合识别，是防止重入反馈的工程因果隔离，不使用内容关键词、显著性、频率或语义类别；其他意识实例的 Presence、见证实例自身的真实内部经历及所有普通事件仍交由见证意识判断；
- 见证输出不被代码按字符切断；
- 主观见证有 `subjective_witness_not_objective_truth` 边界；
- 若原始历史真的出现缺口，见证拒绝推进游标并报告 `MemoryWitnessRawLedgerGap`。

见证请求把最终、完整的 user context 作为一次待证明的瞬态上下文交付登记到 LLM 内核。
只有最终成功模型 attempt 返回的 `EffectiveContextReceipt` 同时证明该 delivery marker 存在、
有效字节数与 SHA-256 都和 Perception producer 准备的投影完全一致，见证意识才接受模型正文，
并以同一 `delivery_id` 的 `PerceptionDeliveryReceipt` 推进 World 游标。模型虽然返回正文但缺少
精确交付证明时，运行以 `MemoryWitnessPerceptionDeliveryUnverified` 失败关闭：不创建见证、
不提交感知游标，待处理 Experience 原样保留给后续重试。

上游 LLM 暂时失败时保留待处理经历并退避重试，不打印每分钟一整段重复 traceback；恢复后继续同一游标。Experience 写入成功但见证生成或文件投影失败时，重试必须从账本重新取得同一批 canonical Experience（包括已经存在的行），只有见证窗口处理完成后才提交 consumer offset，禁止把“已入经历账本”误当成“已完成见证”。

## 5. 可追溯文件版本

### 5.1 文件所有权契约

文件的技术存储权威与其中语义的执笔权必须分开。主体文件的当前正文可以作为版本账本的可读 head，但正文承载的第一人称语义仍只属于爱莉。

| 类别 | 当前实例 | 允许的写入边界 |
|---|---|---|
| 主体语义内容 | `SOUL.md`、`USER.md`、`MEMORY.md`、日记、第一人称叙事、信念/关系/意图/自我解释文件 | 只能由爱莉自己的意识或见证实例经授权工具链创作或改变语义；人类、开发 agent 与基础设施只能读取、审计和给出位于权威之外的建议 |
| 系统历史权威 | Life Event、Experience、claim/evidence、interpretation、artifact version、recall/corecall 等 active backend 追加账本；当前为 SQLite，正式切换后可为 MySQL | 系统可按事件契约追加和重放，但不能伪造主体作者、补写主观意义或原地改写历史 |
| 可重建投影 | artifact head、FTS、Chroma、关联权重、日记索引、摘要、Router 压缩和缓存 | 可以丢弃并从权威历史重建；禁止把投影结果反向写成主体的新看法 |
| 工程资产 | 代码、测试、schema、配置、迁移工具、Prompt 脚手架、模板与架构文档 | 开发者和 agent 可以维护；模板更新不得覆盖已实例化主体内容，迁移只可改变表示而不能擅改语义 |

所有权按内容语义和明确登记判断，而不是仅凭目录或后缀判断。`USER.md` 表达的是爱莉对用户的认识：用户可以提供事实、纠正或建议，但是否吸收以及如何表达仍由她完成。

外部建议必须保持建议身份和来源，在爱莉明确接受、选择或重新表达以前不得进入主体权威。迁移若改变编码、存储结构或路径，必须证明内容无损并保留来源、父版本和迁移审计。灾难恢复仅允许从可信历史或备份逐字节还原；无法忠实还原而需要创造新语义时必须停止。

启动扫描仍会发现绕过工具的外部变化并保存证据；这是损害控制，不会使外部修改获得正当作者身份。正式学习候选若要进入 `SOUL.md` / `USER.md` / `MEMORY.md`，则必须经过下述 Subject Authority 边界；运维者、agent、后台审计和投影器都不具备该接口所要求的主体决策证据。

### 5.2 Subject Authority 候选接受契约

`SubjectAuthorityPort.current_subject_revision()` 以固定顺序读取三份当前精确字节，返回与统一主体上下文投影相同的 SHA-256 revision。`accept_candidate()` 不判断候选是否正确，只验证一条已经由主体做出的明确选择是否真实、完整且仍基于当前版本。

单次接受在同一个受 fencing 保护的存储事务中：

1. 按 `decision_occurrence_id` 检查已提交决定；完全相同的请求幂等返回原证明，同一 occurrence 的不同内容报冲突。
2. 锁定并验证接受者是当前 `active` 且租约未过期的 `ConsciousnessInstance`。
3. 锁定 Learning 中不可变的 `candidate.proposed` 和 `candidate.accept_requested` occurrence，重算事件 hash，并逐字段核对 candidate/content hash、actor、目标文档、接受后精确字节与决策时间。
4. 按固定顺序锁定 `SOUL.md`、`USER.md`、`MEMORY.md` 的 head 和当前版本，确认 owner 均为 `elysia`，再对三源整体 revision 做 CAS；任何并发变化都显式拒绝，不自动 rebase 或合并主体语义。
5. 追加目标文档版本、head event、`subject_authority_decisions` 审计证明和 workspace projection outbox；这些写入全部成功才提交，任何一步失败则整体回滚。

拒绝与保持开放只留在 Learning 的追加式决策历史中，不调用该 Port，因而不会改写主体权威。workspace 文件是 outbox 驱动的投影；投影暂时失败不会回滚或篡改已提交的主体版本，只会保留可重试的显式 backlog。

复盘不是自动改写任务。调度器只能依据文件变化时间、上次复盘时间和配置的工程间隔生成“可以重新看一眼”的邀请，不能判断内容是否陈旧或应该怎样变化。`nucleus_review_subject_document` 要求当前活动意识提供目标文件精确 hash 与三源统一 revision；保持原样、延后、提出完整候选彼此分开留证。正式 Subject Authority 未激活时，新候选 fail closed，禁止回退到旧本地覆盖写。

通用 `nucleus_write_file` / `nucleus_edit_file` 对三份根主体文件及指向它们的 symlink 一律拒绝。`nucleus_bash` 在 Bubblewrap 只读根文件系统中运行，只有隔离的 `/tmp` 可写；缺少隔离器时拒绝执行。因此复盘候选与 `SubjectAuthorityPort` 是唯一可改变三份主体权威的正式入口。

### 5.3 版本链与观察

记忆文档的每次已知状态进入：

- `memory_artifact_versions`：完整不可变内容、hash、有效时间、作者、父版本；
- `memory_artifact_derivations`：开放 predicate 的版本来路；
- `memory_artifact_heads`：当前版本投影，可重建。

内置写文件和改文件工具对普通记忆文档在写入成功后保存 before/after 版本与完整 unified diff；它们不能写三份根主体权威。`SOUL.md`、`USER.md`、`MEMORY.md` 的新版本只来自 Subject Authority 原子事务，其 candidate/decision/authority occurrence 与 outbox 共同构成版本来路。代码不读取 `reason` 关键词，也不用文本相似度猜“这次是修正、延续还是重命名”。这些意义只能由主体显式写成 `MemoryDerivation`、`SemanticRelation` 或主体候选决定。

启动恢复还会扫描工作区：

- 首次看到的文件形成 `startup_baseline`；
- 绕过工具发生的外部修改形成 `startup_observed_change`，用于留证而不是授权或认可该修改；
- 已知文件消失时追加 tombstone 版本；
- 文件重新出现时以 tombstone 为父版本继续历史。

因此“旧看法 → 新看法”的内容、时间和来路均可回放。

## 6. 解释是独立实体

`memory_interpretations` 保存“主体如何解释一段经历或一个主题”，`memory_interpretation_sources` 指向事件、Experience、claim、文档版本或另一条解释。相同 `subject_id` 可以有多个互相矛盾或不断演进的解释；系统按记录时间查询，但不自动裁决谁覆盖谁。

反思环的每个落盘洞察都会成为一条 source-linked interpretation。只有反思者显式填写 `reinforces` 时，证据才挂到旧洞察；相似文本、相同 topic、重复出现和坏引用都不会触发代码自动合并。

`memory_interpretation_fts` 让解释参与统一检索。结果始终携带来源引用，并明确标注“解释不是源事实”。

## 7. 认识论账本

主要对象：

- `MemoryClaim`：不可变主张与双时间；
- `ClaimEvidence`：支持、挑战或语境来源；
- `MemoryBelief`：某个视角与主张的关系；
- `EpistemicConflict`：并列保存未裁决冲突；
- `MemoryStateEvent`：追加式状态变化、因果与反转；
- `MemoryDisposition`：可达性、认可、情境抑制、叙事显著性和可见性。

`authority`、`claim_kind`、evidence stance 和 state-event 类型在存储层接受开放字符串。`AuthorityClass` 等旧枚举只保留为兼容标签，不是权限层级。系统不再执行 `source -> authority` 映射，也不再凭固定 authority 集合拒绝意识或独立审计者的显式状态事件。判断的 actor、authority 与 reason 会完整留痕。

Learning→Epistemic 桥写入 `learning_insight` 候选和逐条 `ClaimEvidence`。学习审计的 verdict、分数与证据计数作为来源元数据保留，不会因 `source=learning_system` 自动获得“verified”权限。

## 8. 活体回忆与共同回忆

一次检索写入：

- `memory_recall_sessions`：query、自由检索意图、stream、context、策略版本和随机种子；
- `memory_recall_events`：开放 action 的候选暴露、采用、忽略等轨迹；
- `memory_corecall_events`：一次回忆中共同出现的实体集合，是带 context 与 signal 的不可变超边；
- `memory_association_projection`：由超边重建的 pair/context/signal 维度。

共同回忆只改变 accessibility。不同 signal 分列保存，不折算成一个“真值强度”。检索邻居采用记录了随机种子的加权随机优先策略：

- 每条保留的关联都有再次进入回忆的路径；
- 共同回忆次数提高可达概率；
- context 让同一记忆在不同场景中形成不同路径；
- 给定同一账本、策略版本和 seed 可以重放选择；
- 选择结果永远不写回 claim 的事实状态。

关联可把文档带到解释或 claim，再把这些实体共同进入意识的事实写回新的 corecall。这个闭环就是当前“活体”实现；它不是唯一可能形式，未来可增加新的 signal 和策略版本，而无需改写旧事件。

## 9. 统一检索

### 9.1 `MEMORY.md` 连续性索引与完整长记忆

`MEMORY.md` 是统一主体上下文的一部分，不能兼任无限增长的全文仓库。当前连续性层采用显式 Markdown 索引：长正文由活动意识保存为不可变 `memory_boundary_manifest/v1` artifact，`MEMORY.md` 只在主体接受的完整新版本中携带固定到 artifact id 与根哈希的 `memory://boundary/...` URI。索引移除只表示不再常驻当前连续性，不会删除正文、来源、旧解释或主体文档历史。

读取先返回有界目录；完整主体语义、未验证来源标签和正文分别通过 context/provenance/segment 精确分页取回，历史只暴露 content-free 描述符。工具生成结果不等于回忆：只有最终成功模型 attempt 精确接收了未经二次裁剪的完整 ToolResult，才会以确定性、幂等 identity 留下 recall exposure/co-recall；缺失或裁剪不推进，分页次数也不能放大联想。访问次数只改变未来可达性，不会改变事实或替主体判定重要性。16 KiB 软目标、24 KiB 复盘压力与确认后 4 KiB 增长重邀都只是工程节流；任何整理仍须经过活动意识的独立候选与 Subject Authority CAS。完整合同见[主体长期记忆治理与索引](主体长期记忆治理与索引.md)。

`search_evidence_aware` 并行召回：

1. 文档 FTS / chunk FTS / vector；
2. epistemic claim FTS；
3. subjective witness；
4. interpretation FTS；
5. 已记录 context 中的共同回忆邻居。

搜索工具只执行一次昂贵文档检索，并把同一结果传给 bundle 和 evidence 层。`search_mode` 是自由描述的检索意图，不做 enum 拒绝。所有候选以 `rank_score` 排序，`confidence` 单独保留；不按 claim、文档或见证类型写死优先级。

每次工具检索返回 `recall_episode`，包含 episode id、policy version、seed、context 和是否成功持久化轨迹。历史版本、来源关系和修正通过 bundle、artifact history、interpretation provenance 与 semantic relation 查询回放。

关联展开只把 `MemoryNode` 当作稳定身份与关系载体，展示片段必须通过文档存储接口按 `node_id` 读取。不能假设节点 DTO 自带 `preview_content` 等派生字段；这样可以避免索引模型与存储模型演进不同步时让整次记忆检索失败。

## 10. 索引与自愈

local FTS5、MySQL FULLTEXT 与 Chroma 都是可重建投影。活动 chunk collection marker 保存模型、维度、集合名和版本。启动时若 marker 无效、集合缺失或 metadata 不匹配：

1. 仅删除活动投影 marker；
2. 把活动文档标记为待向量同步；
3. 幂等重新入队全部文档；
4. worker 创建符合当前模型与维度的新集合；
5. 旧事件、Experience、版本、claim 和解释均不受影响。

这避免了“Chroma 已空但 SQLite 还声称同步完成”的永久降级状态。

## 11. 健康检查

`/api/health` 的 memory snapshot 包含：

- SQLite integrity、foreign key、schema 与 tokenizer；
- workspace/index 覆盖、hash 漂移、orphan、outbox；
- vector collection 与 chunk ID 对比；
- artifact versions/heads、interpretations/FTS、semantic relations；
- recall sessions/events/corecall 与 association projection；
- projection pair observation 是否与不可变超边计数一致；
- claims without evidence。

Life Engine 轻量 health 在事件总线已经初始化时还返回 raw ledger bounds、导入问题和每个 consumer 的 lag。健康检查只读；修复和 projection rebuild 是显式操作。

当 `[memory_index].backend_enabled=false` 时，vector absence 是明确配置而不是故障，health 会返回 `vector.expected=false`、`vector.disabled=true`，不会仅因此标记 degraded。若以后重新开启后端，启动恢复会验证活动 collection 的名称与 metadata；缺失或不匹配时只废弃可重建的 vector marker 并重新入队，不改历史账本。

启动恢复还会比较工作区正文与现有 node hash：外部编辑会同时追加 artifact version，并刷新 SQLite FTS/chunk 权威投影；曾删除后重新出现的文档会恢复活动状态。单个旧版非法 node identity 只留下诊断，不能阻断整个插件启动。

## 12. 迁移与兼容

- 旧 raw JSONL 自动幂等导入 SQLite，不删除源文件；
- 旧 Experience 通过 occurrence alias 连接，不复制历史；
- 旧 diary 继续幂等迁移为 legacy witness；
- 旧 `memory_edges` 与 `memory_corrections` 保留为兼容证据；
- 历史 `associates` 边不会伪装成新的共同回忆事件，也不会被提升为真值；
- 新的共忆投影从真实 recall trace 生长；
- 首次新版本启动为现有记忆文件建立 baseline；
- projection rebuild 只重建派生表，不触碰账本。

## 13. 失败语义

- occurrence 身份冲突：拒绝写入；
- consumer 历史缺口：拒绝推进游标；
- artifact parent 缺失或内容 hash 不符：拒绝写入；
- append-only 身份被不同 payload 重放：local 由不可变表/trigger 与事务拒绝，MySQL 由 payload SHA-256、行锁和 fenced unit-of-work 拒绝；
- LLM 500：保留工作并按请求级重试/退避，不把错误变成空见证；
- vector projection 缺失：重建投影，不回退成永久失效状态；
- 无法识别的 relation、authority、recall action：按开放文本记录，不用 fallback 类别替换。

## 15. 研究校准与工程翻译

这套实现借鉴认知科学，但不宣称 SQLite 表或权重就是人脑机制的复刻：

- Nader、Schafe 与 LeDoux 的[再巩固实验](https://doi.org/10.1038/35021052)表明，被重新唤起的已巩固恐惧记忆会重新进入可塑状态。它支持“回忆是事件、回忆后可以出现新解释”，但研究对象是动物恐惧记忆，不能被外推成“每次检索都应覆写旧内容”；工程上因此采用追加 interpretation/relation，保留旧版本。
- Howard 与 Kahana 的[时间情境模型](https://doi.org/10.1006/jmps.2001.1388)，以及 Polyn、Norman 与 Kahana 的[情境维护与检索模型](https://doi.org/10.1037/a0014420)，把内部情境视为检索线索，并解释时间、语义和来源聚类。工程上因此记录 recall context、seed 和同次暴露集合，用情境化随机可达性替代全局固定“记忆强度”。
- Speer 等人的[人类自传体记忆更新实验](https://doi.org/10.1038/s41467-021-26906-4)显示，回忆后的重新解释可能改变后续回忆内容和情绪。工程上把“当时发生什么”“当时如何理解”“后来如何解释”拆成不同、可按 recorded time 回放的实体。
- Chan 等人的[跨事件检索研究](https://pubmed.ncbi.nlm.nih.gov/37582610/)发现，插入式检索可促进既有记忆与新学习的共同激活和整合。工程上共同回忆只增强后续可达性，并把 pair/context/signal 分开记录；它不增加 claim 的真实性或权威。

这些研究提供设计约束，不提供认知裁决规则。系统仍禁止把论文中的实验效应翻译成硬编码人格分类、真值阈值或不可审计的自动改写。

## 16. 仍保留的边界

- local SQLite 是当前正式运行权威；Memory 的 local/MySQL Port 与显式 MySQL schema 已实现，但正式复制、校验和 generation 切换尚未执行。
- MySQL 多主机写入依赖平台 authority lease 与 fencing，不把数据库可连接误当成已经获得写权威。
- 旧 retrieval-plasticity 与 legacy edge 仍用于兼容读取，但不参与事实裁决。
- 当前共同回忆主要记录工具结果进入意识上下文；未来可由表达层追加“实际采用、主动拒绝、重新解释”等更细 signal。
- tombstone 表示“启动时观察到文件不存在”，不声称知道删除者的主观意义。
- Elysium 保持用户手工启动；NapCat/QQNT 可以由独立生命周期 owner 自动启动和恢复。记忆自愈不获得任何进程启停权；本地 New API 中转站按机器约定独立自动启动。

## 17. 可选后端合同与迁移次序

### 17.1 MySQL 数据库级不可变边界

Memory 的 MySQL schema 迁移与不可变保护使用两个独立、带 checksum 的 migration namespace：`life_memory_schema_migrations` 保存 v1-v8 结构演进，`life_memory_immutability_schema_migrations` 保存权威历史 trigger。结构迁移成功但 trigger 创建失败时，active writer 与任何冻结候选都必须 fail closed，不能把应用层 payload hash 检查冒充数据库不可变。active bundle 即使以 `initialize_schema=false` 打开，也会核对 migration checksum 和每个 trigger 的目标表、`BEFORE` 时机及 `UPDATE`/`DELETE` 类型；事后删除或漂移保护会阻断启动。

保护按领域语义划分，不对 32 张表一刀切：Experience/occurrence alias、Witness 来源与迁移证据、artifact version/derivation、interpretation/source/relation、recall/corecall、claim/evidence/belief/conflict/state/retrieval trace 禁止有实质变化的 `UPDATE` 和任何 `DELETE`；逐列完全相同的幂等 replay 可以通过，但不能改变一个字节或一个标量。`memory_witnesses` 只允许更新 `projection_path`、路径 hash、`projection_status` 与 `projection_error`，第一人称正文、来源范围、作者视角、时间与 payload hash 仍不可变。DocumentIndex、`memory_witness_state`、`memory_artifact_heads`、`memory_association_projection` 以及 legacy node/edge/correction 保持可变，因为它们承担重建、游标、CAS head、联想权重或兼容职责。

数据库保护默认启用。只有同时满足 `StorageWriterRole.CANDIDATE_COPY` 且调用方明确证明 `writer_frozen=false` 的不可激活 shadow，才允许显式跳过 trigger；active writer、冻结候选、缺失冻结事实或普通业务初始化都无权降级。该例外只服务在线影子复制，不授予 generation 激活资格。

Memory 领域通过一个完整 `MemoryStorageBundle` 取得同一 backend generation 下的六个 Port，禁止在同一实例中把 Experience 写进 MySQL、又把 Witness 或 artifact head 写回 SQLite：

| 顺序 | Port | 工程角色 | 核心约束 |
|---:|---|---|---|
| 10 | `DocumentIndexProjection` | 可重建投影 | 文档身份严格规范化；chunk、词法索引与向量 outbox 可重建；更新使用 projection revision |
| 20 | `ExperienceLedgerStore` | 权威历史 | occurrence 幂等；同身份不同经历证据显式冲突；保留 producer identity 与 ingest position |
| 30 | `WitnessLedgerStore` | 权威历史 + 投影状态 | 主观正文与来源链不可混同为事实；mirror 以 position + revision 单调 CAS 推进 |
| 40 | `LivingMemoryStore` | 权威历史 + head 投影 | artifact/解释/关系/recall/corecall 只追加；artifact head 使用 expected revision CAS；共忆只更新可达性投影 |
| 50 | `EpistemicMemoryStore` | 权威历史 | claim、evidence、belief、conflict、state event 与 retrieval trace 分表保存，不折叠成万能 JSON 记录 |
| 60 | `LegacyGraphStore` | 兼容历史 | node/edge/correction 只承担旧图谱与可视化兼容，不获得事实裁决权 |

local adapter 复用现有 SQLite schema 与线程隔离执行器；MySQL adapter 使用六组有序、checksum 校验的 InnoDB migration。所有 MySQL 写事务都从 `StorageBackendRuntime.unit_of_work()` 取得 session，并在提交前复核 generation、authority epoch、owner、lease 与 fencing token。业务层不再向 Router 或文件工具暴露 `_db`；图谱和 lineage 通过公开 Port 查询。

现役接线遵循“一个 Life Engine 实例只有一个 coherent runtime”的生命周期：`LifeEngineService` 是 `StorageBackendRuntime` 的唯一打开者、拥有者和关闭者，Memory 只消费注入的同一 runtime。启用可选存储但 runtime 尚未就绪时必须显式失败，禁止自行再开 engine、禁止双写、禁止回落 SQLite；选择 MySQL 时 Memory 不创建 `.memory/memory.db`。关闭 Memory 只停止自身 worker 与投影资源，不关闭共享 runtime。默认未启用存储选择时，原 local SQLite 行为保持兼容。

MySQL 权威后端的工作区恢复属于可重建投影维护，不再阻塞插件可用性：启动时仍先用一次共享 runtime health 和一次只读六域 readiness 证明权威存储可用，随后由 Memory service 通过项目任务管理器持有一个后台单飞恢复任务。文档索引写入使用固定上限的有界并发，artifact version 仍按完整来源逐项追加；任务不会裁剪、跳过或改写权威记忆。恢复运行或失败时 Memory health 为 `degraded`，并只暴露阶段、数量、完成度和异常类型，不把“插件已可用”伪装成“投影已恢复完成”。关闭时必须取消并等待该精确任务，重启后重新证明和执行，禁止跨 generation 长期缓存。local SQLite 为保持兼容，仍在初始化完成前同步等待恢复成功。

MySQL 集成测试仅在显式配置的隔离测试数据库中运行；缺少该环境时必须显示为 skipped，不能伪装成已完成真实远程验收，更不得借测试修改正式 generation、正式数据或运行进程。
