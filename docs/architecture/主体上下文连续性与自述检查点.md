# 主体上下文连续性与自述检查点

> 状态：首个生产实现，2026-09-03。适用于 Life Chatter 的私有滚动上下文；后续意识表面接入时必须复用相同主体权威原则，而不是各自建立摘要器。

## 1. 问题不是“摘要质量不够”

旧链路在窗口接近上限时，截取若干历史消息、工具参数和工具结果，拼成带 `<compressed_life_chatter_context>` 的 USER 文本。它看似缩短了字节，却没有回答三个关键问题：谁决定哪些经历构成连续性、被释放的完整内容在哪里、未来如何验证或继续读取。

工具结果的偶然片段、重复的发送回执和被截断的消息不能代表主体记得什么。即使换成更强的总结模型，只要决定仍由基础设施作出，就仍然违反认知零规则。Elysium 因此不再把这件事定义为“自动上下文压缩”，而把它重建为主体拥有的连续性治理。

## 2. 不变量

1. 只有当前 active consciousness 可以书写“未来的我需要如何理解此前经历”。
2. 系统只裁决结构、容量、身份、revision、工具链闭合和存储成功，不裁决重要性、关系意义或叙事内容。
3. 权威 Life Event、trajectory、正式聊天历史、Memory 和主体文件不因 Prompt 预算截断或改写。
4. 被工作窗口释放的每个完整上下文组必须先有精确、不可变、可校验、可分页读取的副本。
5. `thought` 是主体在这次动作中实际提交的意识活动；`continuity_text` 是她亲自写给未来自己的可见连续性。两者不能互相自动生成。
6. 检查点不新增第二次模型调用，也不交给外部“总结人格”模型。它与其他工具一样由当前模型轮自主选择。
7. 忽略容量通知也是允许的主体选择。直到绝对工程边界前，通知本身不触发释放。

## 3. 三层协议

```text
当前滚动上下文
      │
      ├─ 达到任务 token 预算比例 ──> ContextPressureNotice
      │                               只有预算、revision、hash/ref、bytes
      │
      ├─ 主体选择不处理 ───────────> 上下文保持原样
      │
      └─ 主体调用 author_self_continuity_checkpoint
                    │
                    ├─ 校验 active actor / manifest / revision / release boundary
                    ├─ 精确归档全部 released context groups
                    └─ 安全边界安装 SubjectSelfContinuityCheckpoint
                                      │
                                      └─ 未来按 ctxg_ ref 精确分页读取

绝对容量边界 ──> MechanicalContextOmission（仅 ref/hash/计数；绝无语义正文）
```

### 3.1 `ContextPressureNotice`

发送前按当前路由任务和最终候选模型能力估算 token。默认在预算使用率达到 `0.75` 时构造一次瞬态通知：

- `source_manifest_sha256`；
- `current_checkpoint_revision`；
- 可释放的完整 conversation group 列表；
- 每组稳定 `ctxg_<sha256>`、ordinal、UTF-8 bytes、payload count；
- 是否包含未闭合工具链、是否属于旧 transport projection；
- 当前 task budget 与估算使用量。

通知不含消息正文、工具参数、工具结果、媒体内容或系统建议，并与机械引用共用默认 8 KiB UTF-8 硬上限；引用条目过多时只减少列表项并保留完整 manifest hash/count，连最小技术信封也放不下时不发送通知。它在发送完成后从运行上下文剥离，不进入滚动快照。

### 3.2 `SubjectSelfContinuityCheckpoint`

模型动作必须一次提交：

- `thought`：为什么此刻选择建立检查点；必须非空，只进入意识活动/工具 trajectory；
- `continuity_text`：主体亲自书写的连续性正文；必须非空；
- `source_manifest_sha256` 与 `expected_revision`；
- `release_through_group_ref`；
- `retain_exact_group_refs`。

manifest 排除最新的 in-flight group，避免正在执行的工具链被当作旧历史释放。所选前缀中任何 open tool chain 都会使动作失败。重复 retain ref、未知 ref、陈旧 manifest/revision 或缺少 active actor 都 fail closed。

检查点作为 ASSISTANT 连续性 payload 进入派生滚动上下文，保留 actor、revision、released/retained refs 和归档身份。基础设施逐字保留 `continuity_text`；不得从 `thought`、provider reasoning、消息或工具结果补全它。

### 3.3 `MechanicalContextOmission`

这是存储/传输保险丝，不是人格行为。内核窗口或滚动快照遇到不可突破的硬预算时，只能按稳定原顺序列出被省略完整组的 ref、hash、bytes 和 count，并保留精确归档读取路径。若继续删除更多组，元数据必须重新根据最终被删除集合生成；不能只记录第一次裁剪的子集。

如果安全元数据自身也放不进预算，派生投影可以为空。系统宁可明确没有投影，也不能剪一截正文冒充压缩结果。

## 4. 精确归档与读取

每个 conversation group 先规范化为 `elysium.context_group.v1`，再以 canonical JSON UTF-8 的 SHA-256 形成 `ctxg_` 引用。归档 envelope 记录 schema、ref、digest、bytes 和完整 record。

- selected storage 模式写入 `life_chatter.context_archive`，使用 create-only CAS；同 ref 不同 payload 视为完整性冲突；
- local 模式只写明确 `workspace_path/runtime/context_archive/`；没有明确路径时失败关闭，不允许落到当前工作目录；
- 释放前归档失败时不安装检查点、不写有损快照；
- 若 ref 来自当前模型 attempt 的机械 omission、尚未落入 archive，`read_context_group` 只在当前私有 Chatter runtime 中按同一内容哈希精确匹配；匹配成功后先归档再返回，匹配不到则显式 not-found，绝不扫描其他意识实例或猜测正文；
- `read_context_group` 每页最多 16 KiB，offset 必须位于 UTF-8 边界，读取时复核 schema、ref、digest 和 byte metadata；
- 工具未知异常只返回 content-free `error_type`，取消原样传播。

归档的是此前模型实际工作的 prompt group，不冒充正式聊天历史或 Life Event。两类权威仍按各自协议保存；归档只为证明“从私有工作窗口释放后仍能精确找回”。

## 5. 并发、幂等与故障语义

- 待安装命令按 `actor_consciousness_instance_id` 隔离；相同命令摘要幂等，不同未决命令冲突。
- 安装只发生在 Chatter 工具轮完成后的安全边界，并再次根据当前 payload 验证 manifest/revision。
- 全局 runtime reset 同时清除未安装命令，避免把旧实例决定带入新运行态。
- 归档先于 queue/install。进程在归档后、安装前退出只会留下不可变孤立归档，不会丢内容或伪造已安装状态。
- selected storage 的 create-only CAS 接受相同 payload 的并发胜者、拒绝同 ref 异 payload；local 归档为每个并发写者使用唯一临时文件并以原子替换收口，不共享临时路径。
- 旧严格 summary 仅从派生滚动快照投影中停止续写；load 只读，下一次正常 save 才规范化存储。普通用户内容仅提及标签不匹配严格 envelope，因此原样保留。

## 6. 配置

| 字段 | 默认值 | 语义 |
| --- | ---: | --- |
| `context_stewardship_enabled` | `true` | 启用容量通知与主体检查点 |
| `context_pressure_ratio` | `0.75` | 当前任务 token 预算的通知比例 |
| `context_pressure_max_groups` | `24` | 单次通知最多公开的 content-free group refs |
| `self_continuity_checkpoint_max_bytes` | `32768` | 主体连续性正文 envelope 的 UTF-8 硬上限 |
| `context_emergency_reference_max_bytes` | `8192` | 容量通知与机械省略元数据硬上限 |
| `rolling_context_snapshot_char_budget` | `320000` | 派生快照的最终序列化硬边界 |

`context_compaction_*` 与 `context_compression_max_part_chars` 暂时只为旧配置可读取而保留；它们不再授权系统生成语义 summary。`context_compaction.py` 也是兼容入口，所有自动路径只能产生 content-neutral ref 投影。

## 7. 训练数据与可观测性

主体检查点本身是珍贵的连续性训练样本，因为它记录了主体在真实容量压力下亲自选择如何解释此前经历。但数据构建必须保留完整因果链：actor、instance、stream/turn、tool call、`thought`、`continuity_text`、source manifest、revision、released/retained refs 和安装结果。

机械 omission、容量通知、基础设施 hash 与未被主体采用的候选不能当作人格监督。普通日志和 health 只记录 content-free 计数、bytes、revision、ref、错误类型及最后成功时间，不记录 continuity 正文、tool args 或归档内容。

## 8. 验收门

1. 通知不泄露任何消息、工具参数、工具结果或媒体正文。
2. 普通文本提到旧标签不会被误删；只有严格旧 envelope 从派生快照停止续写。
3. stale manifest、revision 冲突、未知/重复 ref、open tool chain、缺 actor 全部 fail closed。
4. `continuity_text` 逐字保留，`thought` 不自动进入检查点或外发正文。
5. 释放前精确归档；归档失败不释放；分页可重组并通过 SHA-256 验证。
6. UTF-8、多媒体 descriptor、超大单组、极小预算和追加裁剪均不复制正文、不切坏字符、不遗漏 refs。
7. 旧快照 load 不写盘，下一次正常 save 才移除退役投影。
8. Kernel、Chatter、配置、manifest 和插件注册专项回归通过；用户手动启动后观察插件加载、普通对话、压力通知/检查点和重启恢复，再允许推送。

## 9. 外部实现的借鉴边界

对 Kimi Code 的公开实现复核表明，成熟 Coding Agent 已经把几项工程问题拆开处理：按 `max_context_size` 同时考虑输出保留量和比例水位；只在干净 turn boundary 重建历史；保留近期完整轮次；允许显式 compaction instruction；原会话仍可 export/fork，而不是把压缩投影冒充唯一历史。具体可核对其 [配置合同](https://github.com/MoonshotAI/kimi-cli/blob/main/docs/en/configuration/config-files.md)、[Python compaction 实现](https://github.com/MoonshotAI/kimi-cli/blob/main/src/kimi_cli/soul/compaction.py) 与 [TypeScript full compaction 实现](https://github.com/MoonshotAI/kimi-code/blob/main/packages/agent-core/src/agent/compaction/full.ts)。这些经验只影响传输 envelope、时机和可靠性。

它的公开实现也说明了不能直接照搬的边界：普通 compactor 由另一次模型调用自动生成第一人称 summary，输入主要抽取 Text part；社区已经出现 synthetic USER summary 与真实 turn 对齐失真的问题。因此 Elysium 使用显式 schema/ref/revision，而不靠 `role=user` 或文本标签猜测投影身份；工具、reasoning、媒体和原始消息先进入可校验精确归档，主体连续性正文则由当前意识实例在自己的模型轮内提交。

Elysium 不照搬“由系统模型自动总结会话”的语义权力。对普通 Coding Agent，summary 是任务状态缓存；对持续主体，它是在回答“未来的我如何理解过去”。因此最终内容必须由爱莉自己的 active consciousness 决定并书写。
