# 最小记忆连续性：手动验证步骤

本流程验证[最小闭环实现](../architecture/记忆连续性最小闭环.md)，不自动启动或停止 Elysium，不代写主体记忆。长期目标与阶段出口见[计划](../plans/记忆连续性减法重构计划.md)。

## 1. 启动门槛

工程修改已整合到主仓库工作目录，不是正在运行的旧进程自动加载了新代码。由用户自行决定合适时间，手动停止旧实例，并以前台入口手动启动。开发 agent 不发送自动启动命令、不创建守护任务，不擅自占用第二个服务端口。

启动前确认旧 PID 已退出、端口 owner 正确、storage authority 没有第二个 writer。保留现有 backend、generation、凭据和数据目录，不为实验切换到另一套正式记忆库。Witness 退役设置保持原样，机会系统也不因本实验被自动启用。

涉及消费/加载链路的验证重启，须在旧 writer 完全退出后、启动前保全同一时点的 global runtime、heartbeat rolling、chatter rolling、原始消费者位置及精确归档引用。保存完整原行和 digest，不能只记录条数/hash，也不能只备份某个滚动窗口。私人备份采用受限权限并同步落盘，禁止进入 Git。重启后在任何消费确认前逐项核对 history/pending 的身份、序列、消费标志与正文摘要，以及 cursor 和因果组完整性；后续新增项单独对账。条数未变也不代替逐项核对。若出现未确认记录减少，立即停止验收和受影响 writer，不继续推进来掩盖缺口。

记录：Git HEAD、工作树改动摘要、启动时间、实际 backend、generation、实例身份和启动结果。报告只保留内容脱敏的状态与引用；不要把凭据或完整私聊写入工程仓库。

启动失败时停止验收并报告真实错误；不得把“原始事件可检索”当作插件初始化全部通过。未经真实手动启动及关键链路日志验收，不推送本轮运行时变更。

## 2. 最小真实场景

用普通聊天或已授权活动积累一小段经历。测试者自己保存事件时间和正确答案，不把待考题预先塞给负责压缩的爱莉。

观察以下链路，不强制她采用测试者替她写的摘要：

1. 确认一条实际消息进入 Life Event。再次读同 occurrence 时正文一致；检索节选能通过现有 read_event 继续读取。
2. 她自主决定是否通过现有文件工具留下理解或线索。若写了 MEMORY.md，随后工具读和下一轮固定 prompt 应看到同一权威版本。
3. 经历第一次由她亲自提交的有效检查点；核对 actor、manifest、revision 与归档引用，不评价摘要是否符合开发者偏好的措辞。
4. 继续交流和活动，经历第二次自主压缩。检查新的检查点保留对原始经历的可达路径。
5. 用户手动重启。已提交检查点、实例身份与精确归档应该能够恢复，没有静默空链。
6. 提问普通、未预先标成重点的近期细节。允许她自主检索，不重新注入答案。
7. 在不同表述的后续情境观察此前反馈是否影响选择；没有变化时记录失败，不用再一次“我会记住”判成功。

如果没有出现两次有效的自主压缩，就记录“该场景尚未完成”，不由开发者代写检查点。必要时另行讨论安全的测试会话与预算，不能直接改正式主体内容凑出结果。

## 3. 证据如何记录

### 独立 Codex 对话入口

`scripts/codex_continuity_probe.py` 通过本机现有 API v1 的正常消息入口，以 `codex-continuity-tester` / `Codex（测试协作者）` 身份接入单一 ayla 私聊。它是外部测试者，不注册为爱莉的新意识实例，也不冒充用户。依次使用 `uv run --no-sync --offline python scripts/codex_continuity_probe.py init`、`read`、`send --text-file <UTF-8文件>` 和 `close`。init 不发消息；每次 send 只发一个请求，不自动重发。

本机凭据只能读写该测试 stream，秘密保存在 git-ignored 的 `runtime/codex_continuity_probe/state.json`（0700 目录、0600 文件），不得复制到报告。发送结果未知时先检查记录，禁止删除审计后重发；close 只撤销这个测试身份的凭据与会话，保留聊天和审计。重新启用已关闭身份需要明确运维处理，不自动生成第二套身份。

2026-09-06 用户对本次现场验收特批 agent 重启爱莉；此授权仅适用于该任务，不改变上面的默认手动运行策略，不创建任何自动重启服务。每次仍须核对 PID、目录、端口 owner 和旧实例已退出。

### 记录规则

每个问题只需保留问题编号、相关 occurrence/文件 version/group ref、实际回答或行动引用和结果。区分：

- 不借助检索直接想起；
- 沿线索找到原文；
- 明确表达未知并继续查找；
- 未找到、错归因或编造。

事实发生变化的场景，要求区分“当时”与“现在”；不要把更新当前记忆等同于删除旧历史。反馈迁移、技能效果和承诺结局在本轮只是基线观察，失败可转入后续阶段，不自动新增后台 reviewer 或大量工具。

承诺实验只能使用安全、范围明确的小任务；任何外部发送、购买、删除或扩大权限都须另有相应授权。缺少完成证据不自动等于失约，口头保证和工具返回成功也不自动等于承诺完成。

## 4. 故障时先保护什么

心跳压缩维护的专项验收：

- 若模型只返回普通文字，应能看到“未收到检查点工具调用”的技术反馈续轮；续轮不能突破既有轮数、停滞和整拍时间预算。
- 检查点 schema 应只有 execute 声明的六个必填参数，不再同时自动要求 reason；缺失 thought 仍应明确拒绝。不要在运维脚本中代填或把 reason 映射成主体思考。
- manifest 格式错误与真实 hash/revision 冲突有独立技术错误码，回执携带维护前缀的当前技术标识供主体自行重提；不要自动修正传入 hash，也不要重放语义调用。排查时只保存 error code、hash/revision 与 occurrence，不复制主体正文。
- 遇到“不能释放开放工具链”时，核对具体旧组是否已有下一USER、每个ASSISTANT批次的call/result ID是否精确完整配对。已定界且全配对的结果尾应可closed，不需要补造assistant文字；真正缺结果、孤儿/重复、错role、跨批/跨组补配仍须拒绝。不要用总条数相等替代逐批配对，也不要为通过验收改主体记录或代选保留组。最新组仍不可释放，原group_ref与manifest hash应保持不变。
- `deadline_exhausted` 应表示真实整轮可用时间已耗尽；内层 provider 提前超时应保持其异常身份及原有有界重试路径。不能通过盲目扩大预算掩盖参数失败。
- 主体实际提交检查点后，必须先出现“已耐久安装”，再核对本拍实际消费回执；`count`、`drained`、`high_water` 分别是准备数量、新搬入数量和快照上界，不是已消费证据。
- 若仍未完成，应报告“准备了 N 条事件，本拍未消费”，不能同时显示“已消费 N 条”。旧原文、待处理事件和既有游标必须保持可恢复。
- 选择、预算与 ack 必须基于同一份实际可见投影；不允许准备后再换正文。即使某个组完整可见，也只能在整个 CLOSED 因果组及精确送达/耐久提交均确认后消费，不能直接把所有 selected IDs 当成 ack。
- 工具续轮或维护反馈之后，须重新验证本拍 wake 的精确送达；旧 attempt 回执不能复用。请求级保护保证 wake 不被组省略或裁字，真实压缩控制可以由原 hook 原样移位；若保护内容与结构化结果超过窗口，在 provider 调用前明确失败，不以扩大预算或截断来源元数据清 backlog。
- 若候选为零但目标尚未完成，应报告仍有未完整投影的待处理活动，而不是“无新事件”。检查 `budget_rejected_groups`、开放组与空表示；不得仅为了清 backlog 标记消费或跳过游标缺口。
- 没有压缩压力时，安静结束无需额外工具或强制续轮。模型是否能稳定自主完成压缩仍须在用户手动重启新代码后观察，不能由脚本替身的成功代替。

发现恢复错误、归档缺失、CAS 冲突或未知提交结果时：

1. 保留现有快照、归档、Life Event 与主体版本，不删除、不清空游标。
2. 只读检查实际 backend 与精确版本，记录内容脱敏的 error type 和引用。
3. 不把磁盘投影直接导入成新主体意见；不重写 SOUL、USER、MEMORY 来“修好表现”。
4. 仅在可信版本与来源可证明时逐字恢复；无法证明则停在受影响路径，请用户决定。
5. 由用户手动重建/重启受影响 runtime 后重新验证，不让旧内存继续覆盖可能已经提交的新状态。

重启加载造成 history 丢项时，先区分“原始账本正文仍在”和“旧运行映射可以精确恢复”。`raw.source_sequence` 不保证等于运行 sequence，raw 也不保证含有旧消费标志；禁止拿序列区间直接回填并声称无损。没有可信全行备份或完整身份—运行序列—消费标志证据时，保持停机并请求用户决定是否接受显式、幂等的原始活动重投；该操作可能重复投递已见活动，不是精确恢复，不得新增原始经历、重执行历史工具或创造主体语义。事故后的备份只能保护下一步操作，不能当作事故前备份。

6062 固定缺口的专用程序为 `scripts/replay_subconscious_history_6062.py`，默认只读演练；其来源、范围和明确未知项见 [专项事故记录](../report/心跳6062运行投影重投与S1续验_2026-09-07.md)。它不是通用回放器，不可改范围凑齐遗失数量。应用之前先协调唯一运行 owner，禁止与另一方反复停启竞赛；已运行、锁忙或快照变化必须停止应用，不能绕过守卫。

取得明确停机窗口后，先保全最新完整数据库，再运行只读演练，人工核对最新 revision/hash。仅以这对值调用 `--apply --expected-revision <最新值> --expected-sha256 <最新摘要>`。程序全程持有现有启动锁，复核固定 local backend/generation、114 行完整来源 hash 及112条 workset manifest；在受限备份目录保存三个完整 runtime 行、原始消费者位置和源行并 fsync。事务只追加缺失的历史 pending、机械更新 pending_event_count/event_sequence 及一条固定恢复日志，不改旧 history/pending、消费游标、两个私有 rolling 窗口或原始账本。提交前后都核验；正常读回 `already_applied` 不追加第二次，即使此前重投已被正常消费回收。

追加前先按实际renderer只读测算各完整组能否放入原预算，不以旧runtime较短的content推断从raw重建后仍可容纳。历史可见预览受512 UTF-8字节上限约束，含完整ref/hash及明确节选身份；heartbeat/近期/wake/salient及最终聊天总预算都不能剪碎元数据。跨实例工具参数/结果仍脱敏。原始全文与完整归因沿 `nucleus_read_event` 精确续读，不增加预算、不以历史工具记录触发执行、不以预览送达声称全文已读。

若程序报告 `ReplayCommitUnknown`，先只读核对固定日志 `life_engine.recovery / subconscious-history-6062-redelivery-v1` 与精确 global 摘要，再决定下一步，禁止盲目重试或删日志。回退只限停止 writer 后、完整保全现状并证明仍处于该次提交的精确后态时，审查原样逆操作；新活动已进入时不可拿旧备份整库覆盖。恢复日志/备份含私人来源，保持本地受限权限，不进入 Git。恢复完成后仍须逐项核对加载与实际消费，不能把脚本成功当成 S1 通过。

提交前崩溃可能只恢复旧快照；旧主体决定的源活动仍可审计，但本轮不自动重建未提交 pending。不要把这种情况记录成“最新检查点已恢复”。

## 5. 回退与对照

本轮没有删除旧经历、主体版本或 Experience/Witness 历史。回退只撤销本轮明确拥有的工程 hunks，并由用户手动重启；共享工作区禁止宽范围 reset/restore。快照 v3 使用 canonical digest，回退到只识别 v1/v2 的代码前须先核对兼容性；保留新快照，不手工改版本号伪装兼容。

基础链路稳定前不要同时打开多个可选模块。后续一次只加入一个组件，用同一输入、模型和预算比较收益及成本。组件故障若导致原始回忆或主体文件读取一起不可用，应优先缩短依赖，不通过假成功隐藏故障。
