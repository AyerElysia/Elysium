# 消息附件引用持久化补验

2026-09-09（北京时间）。状态：局部工程合同通过；已完成正式附件列核实、再次授权重启与完整记忆恢复。原测试流已接收一条新普通邀请，但模型服务连接失败，主体端到端使用仍未验收。

## 目的与根因

审计发现 `Message.attachments` 只存在于运行时对象。`StreamManager.add_message`、`add_sent_message_to_history` 原先只把 `message.content` 写入 `messages.content`，`_db_message_to_runtime` 也没有重建附件；进程重启后媒体的稳定引用、hash 和来源消息身份因此丢失。原始媒体字节不应复制到聊天消息表，本修复只保存描述符。

## 实施

- `Messages` 增加可空 `media_attachments` TEXT 列，使用现有非破坏性 schema sync，可对旧表做幂等 `ADD COLUMN`。
- 接收和发送路径分别写入版本化 JSON：`{"version":1,"attachments":[...]}`。描述符沿用 `MediaAttachment.to_descriptor()`，不包含原始 bytes；正文序列化格式保持不变。
- 历史重建读取该列并用 `MediaAttachment.from_descriptor()` 恢复有序、可重复的 descriptor-only 引用。`SQL NULL` 仅表示旧行没有记录附件；非空损坏、未知版本和非法描述符显式失败，不伪造成空附件。
- 延迟正文查询仍可以只加载 `[Content deferred]`；附件引用从独立列恢复，不触发正文读取。恢复对象经 `Message.to_dict/from_dict` 仍保留引用。

## 可复核验证

新增 `test/core/managers/test_stream_manager_attachment_persistence.py`，使用短合成 PNG、WAV、MP4 和不透明文件字节及临时 SQLite：

- 五类 segment 的 descriptor round-trip，确认顺序、重复项、hash、MIME、来源和 resource_id 保留，正文、base64 和原始 bytes 不进入附件列；
- 旧表幂等升级（第一次新增 1 列，第二次新增 0 列），旧正文保持逐字节不变；
- 关闭临时引擎、创建新引擎/新 session 后，普通和 `raiseload` 延迟正文路径都恢复相同附件描述符；
- 接收与发送重复调用不产生第二行；数据库写入失败时不先发布 unread/volatile 状态，修复后可用同一消息身份重试；
- 受管原件经 `ManagedMediaService` 解析为附件后写入消息历史，关闭并重开消息 session 与媒体 store，再用保存的同一 `media_id` 回取原件，字节与 hash 一致；重建后的消息再经 `build_chat_message_event` 进入 Life Event 事实投影，附件 descriptor 的 `resource_id` 保持一致。这验证跨域引用到事实投影的局部链，不把两个域合并成一个权限边界；
- 非空损坏 JSON、未知版本、额外字段和非法 descriptor 均显式报错，错误文本不回显合成私密标记；
- SQLite/MySQL 方言的新增列定义均为可空 `TEXT`。
- 在已有 Life Event 临时账本的两个本地存储实现中，消息事实写入、重开读取和 occurrence 重放均保留同一附件 descriptor；该文件全量 11 项通过。
