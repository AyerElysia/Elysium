# 跨平台普通附件能力收口（2026-08-18）

## 1. 问题与结论

此前“看起来支持文件”和“主体真正能够取得、保存并发送文件”不是同一件事：

- QQ 普通文件只有名称、大小和 ID，正文没有进入本地受控存储；
- KOOK 已下载正文，但使用可碰撞文件名落盘，缺少内容哈希、硬字节上限和稳定引用；
- 飞书事件保留了 `file_key`，入站下载器却只处理图片与语音；标准出站链也没有普通文件上传与发送；
- `LifeSendFileAction` 有实现，但未注册到插件组件和 chat manifest；文档因此早于真实能力；
- `nucleus_save_media` 把普通文件路径误当 Base64，无法消费适配器已经下载的附件。

本轮把这些断点收口为一个统一合同：平台负责取得正文并生成内容寻址引用，Life Engine 负责由主体显式保存、读取或发送。附件类型不成为回应、保存或转发规则。

## 2. 生产合同

### 2.1 入站物化

- QQ、KOOK、飞书把成功取得的正文原子写入 `data/received_files/<platform>/`。
- 路径由 SHA-256 与安全化文件名共同构成；重复内容幂等复用，已存在但校验不一致的目标会被原子修复。
- 单个入站附件硬上限为 200 MiB。取消立即传播；下载失败、超限或协议缺失只返回 `materialized=false` 元数据，不伪装成功。
- 统一消息携带 `path`、`storage_key`、`sha256`、`size` 和文件名，不携带正文或 Base64。错误日志只记录错误类型和不可逆诊断标识，不记录正文、下载 URL 或凭据。

### 2.2 主体保存与读取

- `nucleus_save_media` 新增普通 `file` 分支，只接受合法 Base64 或 `data/received_files` 下的受控本地引用。
- 保存目标必须位于 Life Engine workspace；写入采用临时文件与原子替换，并返回 SHA-256。
- 远程 URL 不会被保存工具暗中下载；需要网络下载时继续使用已有 `nucleus_download` 能力。
- 普通文件不是原生多模态内容。正文只有在主体显式使用有界文件读取工具时才进入当前认知上下文。

### 2.3 主体发送

- `action-life_send_file` 正式注册为 chat 能力并进入插件 manifest。
- 发送单个可读普通文件，文件类型不设扩展名白名单；目录、通配符、不可读文件和通用 100 MiB 上限显式拒绝。
- QQ 与 KOOK 复用已有文件出站协议；飞书新增文件上传、私聊/群聊发送与引用回复。
- 飞书依据[开放平台上传文件合同](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/file/create)拒绝空文件并限制为 30 MiB；发送使用 `msg_type=file` 和上传所得 `file_key`。

## 3. 认知边界

“能取得文件”只是一项技术能力，不代表系统替主体决定要阅读、保存、回复或转发。平台、扩展名和消息类型不得生成认知倾向；同一主体根据当前经历和意图显式选择工具。失败也不得被改写成主体拒绝或忽略。
