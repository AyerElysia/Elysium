# 事故报告：群聊 @ 消息整夜未达表达层（2026-08-29）

## 事故概述

2026-08-29 00:53，群「始源之地」成员 T9033 发送 `@爱莉希雅 晚安啦～♪好爱莉[表情：爱心]`。该消息整夜未被表达层（主意识表达窗口）看到，也未被回复。核心意识在 01:23 的心跳中注意到了这条消息的温暖（"点名叫了我……比日常的晚安多了点温度"），但误以为"表达层自然会接住"——实际表达层从未收到它。

## 对先前错误结论的纠正

调查过程中曾向运维者报告"路由器看到了 @ 消息并主动选择沉默"。**该结论错误**：训练数据湖中的完整路由请求证明路由器从未收到这条 @ 消息，它判定的是 70 秒前那条无 @ 的"晚安各位"。真实根因是消息管道的丢失唤醒竞态（见下），不是模型判断失误。本节即为对该结论的显式更正。

## 根因

两条独立的管道 + 一个挂起语义缺陷，共同造成消息丢失：

1. **入队延迟竞态**：`stream_manager.add_message`（`src/core/managers/stream_manager.py:418`）先持久化数据库、后插入 `context.unread_messages`。@ 消息 00:53:10 到达时聊天器回合正在进行，其落库完成晚于本回合的未读读取（00:53:11.4），因此未进入本回合批次。
2. **丢失唤醒**：该消息自身的"新消息"唤醒事件在聊天器回合忙碌期间已被消费。沉默分支结束后 `Wait()` 的语义是 `time=None` = 无限等待直到下一条新消息（`src/core/components/base/chatter.py:33`）。此后群里再无新消息，聊天器再未被驱动，@ 消息永远留在未读队列。
3. **旁路消费与错误交接假设**：life_engine 的 pending 事件队列独立于聊天器未读队列。心跳在 01:23 drain 了 @ 消息的副本，唤醒上下文未告知核心模型"表达层从未见过这条消息"，导致核心意识做出"表达层自然会接住"的错误假设。

附带发现（未在本次修复范围）：FOLLOW_UP 阶段 loop 中合并的未读增量在回合终止时不会立即 flush，会在下一回合被重新呈现（既有行为，与本事故无因果）。

## 已执行修复

以下修复均为基础设施投递保障，不替主体决定是否回应、如何回应（符合 AGENTS.md 认知零规则：消息直达表达层后，说什么或是否简短带过由她自己的意识决定）：

1. **挂起前未读背板**（`plugins/life_engine/core/chatter.py` `execute()`）：每次回合以 `Wait(time=None)` 终止前，重读未读队列；存在本回合从未见过（不在 `rt.unreads`，含 loop 中合并增量）的新未读时，继续推进而不是无限挂起。连续推进上限 `_UNREAD_BACKSTOP_MAX_CONTINUES = 5`，达到上限转交下一事件恢复，消息不丢弃。已处理过的消息不计入"新"，避免重复呈现。
2. **@ 直达表达层快速通道**（`_should_respond`）：消息经 `StreamLoopManager._message_mentions_bot` 同源事实判定（`extra.at_users` 对照 `raw_data.self_id`，文本兜底）确认直接指向她的账号时，跳过路由模型直接交给表达层；`force_reply` 沿用既有语义（max_rounds 兜底前保证可见回复）。@ 是平台层事实，不属于认知裁决。
3. **路由提示词**（`plugins/life_engine/core/router.py` `_fallback_prompt`）：补充"唯一例外：直接 @ 她的账号或点名她时必须交给表达层"。作为快速通道之外的模型层保险。
4. **心跳投递事实标注**（`plugins/life_engine/service/core.py` `_expression_unseen_note` + `_prepare_heartbeat_context`）：drain 的 MESSAGE 事件若其 message_id 仍在对应流未读队列，在唤醒上下文追加 `<expression_delivery_status>` 事实段，明确"该消息尚未经过表达层处理；是否回应、如何回应由她决定"。消除"表达层自然会接住"的错误假设来源。
