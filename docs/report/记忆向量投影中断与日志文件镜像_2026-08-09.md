
## 4. 为什么 health 说了 11.25 天的 `ok`

`memory_index_jobs` 是**生产者/消费者不对称**的：

- 生产者 `_enqueue_index_job_in_transaction` 在写事务内**无条件**入队；
- 消费者 loop 由 `[memory_index].enabled` 单独控制（`service/core.py:8158`）；
- 旧 `issue_count` 只累加 `processing` + `failed`，**不含 `pending`**。

于是后端关闭 → 消费者从未创建 → 生产者继续入队 → 积压只落在 `pending` → health 恒等于 `ok`。

而 FTS 完全不受影响：`_replace_chunk_fts` 在同一个写事务里同步写入，所以**文本检索一直是完整的**。这就是积压能长期静默的原因——检索还能用，只有 health 能暴露它。

当日实测：

```

oldest pending age      11.25 天
last_completed_at       1785606127.238
stale_reason_counts     {'SupersededContent': 304}
```

修复：`memory/health.py` 现在报 `degraded` / `backlog_status=disabled_backlog`，并给出 owner、backlog、last success、可读 reason，满足 §8。详见 `docs/architecture/生命记忆系统.md` §11.1。

## 5. 今天 06:24 的重新入队不是 bug

1966 条 pending 的 `updated_at` 全是今天，但 `created_at` 最早保留到 7-29。原因：SQLite 后端在 init 阶段同步跑 `_run_startup_recovery_owned`（`memory/service.py:572`），`_reconcile_document` 的 `not node.embedding_synced` 分支在两秒内重新入队（06:24:42 n=1208、06:24:43 n=703）。

它是安全的：

- `job_id = f"{node_id}:{content_hash}"` 是确定性的，重复入队幂等；
- UPDATE 分支保留 `created_at`，只重置 `status` / `index_revision` / `updated_at` / `error`；
- 429 个已同步节点未被触碰；
- 积压有界：1966 pending ↔ 1967 个 `embedding_synced=0` 的活文件节点，0 孤儿、0 指向被取代 hash、0 指向已删除节点。

## 6. 恢复：决策与执行

### 6.1 两条路

| 路径 | 代价 | 风险 |
| --- | --- | --- |
| A. 恢复被挪走的 store | 字节级拷贝，秒级 | 需先证明它可开、且与权威指针匹配 |
| B. 接受全量重嵌 | ~1966 文档 × `batch_size=4` / `interval_seconds=60` ≈ 8 小时 embedding 调用 | 走 `invalidate_vector_projection()`，会**DELETE 权威指针行**并重新入队约 2400 文档 |

**选 A。** 理由不只是成本：B 的爆炸半径严格更大，而字节级恢复正是 §4.1 明确许可的灾难恢复形式（byte-identical restore + 审计痕迹）。

### 6.2 执行（stamp `20260809-1539`）

```
data/life_engine_workspace/.memory/
├── chroma/                            ← cp -a 恢复的审计过的 store（在役）
├── chroma.broken-20260802-1010/       ← 源，保持原封不动（审计基线）
└── chroma.empty-20260809-1539/        ← 被让位的空 store，保留待查
```

三份都在。没有删除任何东西。

### 7.1 更正：4215 不是向量数

先前我说过"4215 条向量仍然完整"，**这是错的**：

- **4215** 是 hnswlib 的 element **槽位**数。hnswlib 从不收缩，删除只打 tombstone，槽位一直留着。
- **759** 才是活向量数。

这条更正改变的是这次恢复的"价值量级"，不改变结论：429 个 `embedding_synced=1` 文档 ↔ 759 条 chunk 向量，说明 `memory.db` 与被挪走的目录是**配对的一对**，恢复因此是有效的。

### 7.2 live 与基线的 sqlite 字节差异（预期）

`chroma.sqlite3` 的 sha256 两边不同（live `4724e755…` / 基线 `5257d059…`），大小同为 25292800。原因是只读打开时 SQLite 把 WAL checkpoint 回了主文件——**页面搬家，不是内容变化**：两边的 collections / segments / collection_metadata / 计数（859 embeddings、533 queue）逐项相同，`quick_check` 均 `ok`。真正承载向量的 10 个 HNSW 文件字节完全一致。

### 7.3 审计痕迹：我自己留下的持有者

验证期间我的一个探针进程（`/tmp/verify_live.py`）在 `collection.count()` 里阻塞了约 38 分钟并一直持有 live store，正是它把 live `chroma.sqlite3` 的 mtime 推到了 16:01。已终止；现在无任何持有者，`quick_check` 仍为 `ok`。

`count()` 会加载 4215 槽位的 HNSW，很慢；后续核对**应直接只读查询 SQLite**，不要走 `count()`。

## 8. 日志系统：真实故障是"从来没有文件 sink"

SQLite sink 一直正常：`logs.db` 当日 106979 行、今天 4019 行、最新一条 15:22:58。

缺失的是文件侧，而且是四处彼此印证的"死配置"：

- `_global_config["log_dir"]` 被声明，**从未被读取**；
- `bot.py` 的 `self.log_dir` 只有赋值，**没有读者**；
- `initialize_logger_system()` 从来没收到过它（而 `main.py:82` 早就传了 `log_dir="logs"`）；
- `_strip_rich_markup` 的 docstring 宣称"仅用于文件日志输出"，而它唯一的调用点喂的是 DB sink。

后果：Elysium 由人手启动，控制台写到 pty（当日为 `/dev/pts/3`），**会话一结束那份输出就不存在了**。`logs/elysium.log` 是早期 nohup 的遗留产物，不由任何机制维护。

修复：在 `LogStore` **已有的 writer 线程内**增加按日期滚动的纯文本镜像（不新增线程，句柄与 SQLite 连接同一个 owner，符合 §7 单一 owner）。两个 sink 互不牵连，任一侧失败只增加自己的失败计数。详见 `docs/architecture/日志系统.md` §3.7。
