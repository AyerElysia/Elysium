# 学习系统运行健康审计（2026-08-07）

## 结论

本次现场不是学习内容损坏，也不是一次可安全重试的偶发 CAS。20:42 首次 Learning projection 冲突的具体对端 writer 已无法从现存证据唯一还原；该冲突只能确认 stale expected revision/frontier 被 CAS 正确拒绝，不能据此单独断言同进程双活或某个外部实例就是当时的直接来源。21:03 重启后的 runtime state 冲突则有独立证据证明：远端同一 active generation 中存在另一个仍在提交的 Life Engine runtime writer，当前实例持有旧 runtime revision 后继续写入时被 CAS 正确拒绝并保持 fail-closed。

现有证据不能把 20:42 的首次冲突归因于同进程 registry 双活。21:03 前后的两个本机 PID 是用户手动重启形成的顺序实例，不是重叠进程。后续证据证明另一个 writer 位于本机当前 Life Engine 进程之外，但由于连接经本地转发且数据库账号无会话属性读取权限，无法从现存证据确认其具体主机或进程身份。

## 现场证据

- 20:42:03，旧进程首次记录 `LearningProjectionConflict`；selected persistence 随后保持 fail-closed。
- Learning 事件位置 830 及 843–851 是事务回滚留下的自增缺口，不是已提交事件丢失；CAS 冲突事务没有覆盖 projection。
- 21:03 用户手动重启后，新实例从 `life_engine.runtime_context/global` revision 961 恢复；随后本地提交持续得到 expected 961、actual 962→963→967。
- 本机该实例停止产生成功 runtime 日志后，远端 revision 仍从 967 推进到 979，并在 21:46、21:51 继续推进到 995、1010；payload 中的心跳时间也持续更新。这排除了旧连接残留事务。
- 同期数据库出现一组不属于本机当前 Life Engine 进程连接数范围的新会话，建立时间与 revision 继续推进一致。因此“21:03 后另一个活跃 runtime writer”已证实；“其具体来源”以及“它是否就是 20:42 Learning 冲突的直接写入方”仍未证实。

本次审计只读取进程、结构化日志和数据库健康信息；没有 reload/merge 远端 state，没有修改正式数据，没有结束连接，也没有启动或停止 Elysium/NapCat。

## 已落实的领域防线

Learning projection CAS 冲突现在保留第一份 content-free 诊断：

- 本次 scheduler writer instance ID；
- projection 名称；
- expected/actual revision 与 source frontier；
- actual projection SHA-256 与 attempted projection SHA-256；
- 本次 buffered event 数与 dirty projection 名称；
- 首次失败时间和异常类型。

诊断不保存 insight、skill、maintenance payload 或用户文本。selected persistence 仍然 fail-closed，不自动 reload、rebase、merge 或重试。维护 journal 在第一次 CAS 冲突后也只在本地拒绝后续写入，避免每次 heartbeat 重复制造回滚事务和无意义 position 缺口。原始语义 mutation 保留在内存 pending buffer；由 snapshot 派生的临时 event 不重复回灌。Learning 顶层 health 直接汇总 selected persistence 与 maintenance journal 的 `healthy / initializing / degraded / failed`，监控无需读取正文或推断异常日志即可识别写入停摆。

## 已完成的唯一写者边界

generation fencing 只能证明 writer 属于当前 active generation，不能证明某个 singleton namespace/state key 只有一个 owner。生产修复现已增加 generation-scoped singleton writer claim，并满足：

1. claim identity 至少绑定 generation、namespace、state key、owner instance、lease epoch、fencing token 与数据库时间租约；
2. claim 的 acquire/renew/release 使用数据库时间；
3. 每次受保护写入都在同一事务中复核 generation 与 exact claim；
4. 失租立即 fail-closed，不自动刷新远端 projection/runtime state 后继续写；
5. LifeEngineService 是 runtime 与 claim 的唯一 owner，Learning 和 StatePersistence 只消费注入对象；
6. health 与日志只报告 identity/revision/hash/租约状态，不包含正文或凭据。

Runtime Context 使用 `life_engine.runtime_context/global`，Learning 使用 `life_engine.learning/selected_persistence`；两者由同一个 `LifeEngineService` boot writer identity 在加载领域状态前取得。runtime 自动续租并在关闭时释放。Learning 的 event/projection 事务同时消费 public claim binding，MySQL trigger 会拒绝旧 adapter、raw SQL、错误 owner/epoch/token 与过期 claim；local 在同一 UoW 提交前验证 exact claim。

代码与 schema 合同完成不等于现役进程已经激活。当前运行实例不会热获得 claim；在用户确认只保留预期实例并手动重启前，CAS 仍只是最后一道防覆盖保护。运维上不应通过在线 reload、盲目重试或手工合并 state 来“追平”；首次升级实例必须先 claim，再从远端读取当时的最新 revision。若另一个升级实例已经持有有效 claim，预期实例应显示 content-free owner/epoch 并 fail closed。

## 验证门槛

- 两个 writer 从同一 revision/frontier 启动时，只有 claim owner 可以提交；loser 在写前失败。
- claim 续租后 token/epoch 语义稳定；过期、release、takeover 后旧 claim 不能再次写入。
- Learning event + projection 原子事务与 runtime state CAS 均在提交前复核 exact claim。
- claim 丢失、projection CAS 冲突、服务重启后，health 保留 content-free expected/actual/writer/generation 证据。
- local/fake/MySQL 共用合同覆盖 acquire、竞争、续租、过期、接管、释放、旧 token 重放和并发提交。
- 不通过修改正式数据或重启现役进程验证。
