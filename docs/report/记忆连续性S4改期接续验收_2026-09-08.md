## 3. 根因与最小修复

代码路径为 `plugins/life_engine/storage/opportunity_adapters.py` 的 `SQLOpportunityStore._cancel_invalid_pending` 与 `materialize_due`。

1. `opportunity.schedule`／`opportunity.snooze` 对已有登记执行 CONFIGURE/CAS，登记 revision 增长，并保存新 `first_due_at`。
2. 原实现清理旧 pending 时，将 activation 的 `registration_revision` 提前写成新登记 revision，同时清空 `next_due_at`。未发布 pending 和已发布未 seen 两个分支均有此问题。
3. 后续扫描只在 activation revision 与登记不同、且没有 pending 时按新 `first_due_at` 接续。原实现已经写成相同 revision，使这个恢复分支永远不执行，扫描返回空却不报告失败。
4. 修复在清理时保留旧的已应用 revision；新时间到了之后，由已有 materialize 事务应用新 revision 与新到期时间。

原有 `due_index + 1`、唯一约束、事务、CAS、数据库时钟、singleton scheduler claim 和状态门保持不变。provider 停用时的零 revision 恢复哨兵保持不变。旧 occurrence 不删除，已发布 publication／Life Event 不改写；只允许将尚未发布的 outbox 明确取消。旧 seen 回执不能消费新 pending。

最初隔离阶段只有 SQLite 实测和 MySQL 分支审查；后续已在第 13 节的获准停机窗口，用新建私有 MySQL 8.0 服务真实验证同一 adapter 的两处改期分支及既有 actor／scheduler／receipt 合同。双后端证据不代表正式 MySQL 切换或其全部故障交错已经验证；本次正式后端仍为原 local selected SQLite。

## 7. 正式接入与主体决定边界

统一机会接入不是单条提醒开关。按现有实现，需要先准备 schema，再写耐久 managed marker；之后旧固定心跳、生命定时器及相关旧自动能力链退出。仅把配置改回 false 不能撤销 marker 回退旧调度；能力安装、初始安排、workflow 选择也不能由运维准备冒充主体决定。

正式切换决定归用户。最初受控重启授权未被当作全局切换授权；在收到明确风险说明后，用户进一步要求继续未闭环工作、自动推进并验证所有相关工作，允许修正工程阻碍及替换不可用配置模型。本次按该新授权执行 [切换手册](../operations/opportunity-runtime-cutover.md)，仍先核对旧安排清单、新鲜保全与恢复能力，不自动认领旧承诺或替她安装默认流程。主体可拒绝或推迟真实实验。

主体安排、首次到期、exact receipt、经事实校准后的改期、真实进程恢复、第二次到期与 exact receipt，以及主体关闭和已投递反馈均已取得，见第 11–14 节。该单条受邀链证明本次可靠接续，不证明未提示的时间理解、时效审查、技能学习或承诺履行的普遍收益；正式样本也不替代最初 pending／未 seen 失败交错的隔离合同。

继续实施时已修正 self_awaken 操作 schema 的“新建／revision 0”说明与 CONFIGURE 的矛盾：只允许正整数旧登记 revision，明确首次登记走 opportunity.open。原生执行入口拒绝 0、负数、bool、字符串及小数；管理协议、能力手册与测试同步，不引入自动 upsert 或恢复关闭登记。
