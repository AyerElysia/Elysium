**日期**: 2026-08-02
**范围**: 全系统异步处理审查
**基线**: `14f1d7e`

---

## 触发事件

05:52 系统冻结。最后一条日志是 `life_chatter 记录纯文本独白，继续 loop`，之后事件循环再无进展。

定位到 `chatter.py:_save_rolling_context_snapshot()`：它是 `async def`，内部却直接做 `tmp_path.write_text(...)` 和 `os.replace(...)`。这个函数在每轮 life_chatter 循环都会调用，是高频路径。

顺带解释了一个一直没想明白的现象——**为什么 90s 的 `wait_for` 没有触发**：`asyncio.wait_for` 依赖事件循环自己去推进定时器。协程内部做同步阻塞时卡住的是循环本身，超时机制和被超时的代码一起死了。超时保护对同步阻塞是完全无效的。

从这个点展开做了全系统审查。以下按严重度排列。

## P0-1 记忆层 SQLite 全局串行

**新增**: `plugins/life_engine/memory/sqlite_runtime.py`
**改动**: `memory/` 下 `decay.py` `edges.py` `health.py` `lineage.py` `nodes.py` `router.py` `worker.py`

原状：每次读写都在解释器**默认 executor** 上跑裸连接，没有 WAL，没有 busy_timeout。并发一上来就退化成全局串行，且一旦锁等待就直接吃满默认池。

改为统一的 `run_db` 入口：

- WAL + `synchronous=NORMAL` + `busy_timeout=10000` + `mmap_size=256MB`
- 独立有界线程池（`ELYSIUM_MEMORY_DB_WORKERS`，默认 4），不再和别人抢默认 executor
- 写连接与 `query_only=ON` 只读连接分离
- 只读连接按**代际（generation）**做线程本地复用；`bind_reader_pool()` 换库时递增代际并主动关闭旧句柄——旧句柄不关会一直钉住 WAL，磁盘只涨不回收

## P0-2 调度器同步回调泄漏默认 executor

**新增**: `src/kernel/concurrency/blocking.py`
**改动**: `src/kernel/scheduler/core.py`

原写法：

```python
await asyncio.wait_for(asyncio.to_thread(cb), timeout=timeout)
```

问题不是超时不生效，是**超时后线程杀不掉**。`wait_for` 取消的只是那个 awaitable，被调用方仍然占着 worker 直到自己返回。而 `to_thread` 派发的是全进程共用的默认 executor，适配器读文件、媒体解码、向量检索用的是同一个池子。于是一个卡死的定时任务不是局部故障，是全进程 `to_thread` 的故障。而且这个泄漏在任何指标里都看不见。

`BlockingPool` 分开处理这两件事：

- 每个子系统持有自己的有界池，故障半径收敛在子系统内
- 超时后不再假装收回：线程被登记为"已放弃"，出现在 `get_statistics()["sync_callback_pool"]` 里，最终返回时补一条带真实时长的日志。`abandoned_live > 0` 就是"调度看起来卡住了"的第一观察点
- 区分两种超时。`future.cancel()` 为真是唯一可靠的"调用绝不会执行"的证据（只在还排在队列里时成功），此时抛 `BlockingCallNotStarted`，说明**池子已经满了**；为假才是调用本身跑太久。两者混在一起，排查会一直停在错误的调用上

超时判定也从调用方下沉到了 `_run_callback` 内部：协程回调能被 `wait_for` 真正取消，同步回调不能，两者的收尾方式不同，在外面套一层统一的 `wait_for` 会把线程泄漏掩盖成一次普通超时。

## 顺带修掉一个 kernel DB 真 bug

**`src/kernel/db/core/engine.py`**

原来用 `engine.begin()` 下发 PRAGMA。`begin()` 只配置**连接池里的一条**连接，其余连接完全没拿到这些设置——WAL、busy_timeout 看着"配了"，实际大部分连接没有。

改为 `event.listens_for(engine.sync_engine, "connect")`，每条新连接都生效。每条语句独立 try/except 保持降级不崩；失败语句用 `reported` 集合保证只告警一次，否则每建一条连接刷一遍日志。

## 过程中自己引入又修掉的问题

如实记录，因为其中两个的性质值得警惕：

1. `file_tools.py` / `download_tools.py` 用了 `asyncio.to_thread` 却**没有 import asyncio**。直接炸了 2 个用例，其余位置被一层宽 `except Exception` 吞成 `(False, ...)` **静默掩盖**。这是宽异常捕获的典型代价。已修，`ruff --select F821` 确认干净。
2. `_save_rolling_context_snapshot` 从 `def` 改 `async def` 后，6 处测试桩仍是 `lambda _response: None`，报 `TypeError: object NoneType can't be used in 'await'`。已换成协程桩。
3. 发现一个**没报错但已经变空转**的用例：`test_..._snapshot_save_failure_does_not_mutate_runtime` 是 `def` + 未 await 的调用，测试一直"通过"却什么都没执行。改成 `async def` + `await` 后才真正生效。sync→async 迁移会静默产生这类真空测试，值得单独一条检查项。

## 未解决 / 已挂账

**1. 一次未能复现的全量挂起。** 早期某次全量跑超过 12 分钟不动，py-spy 定位到 worker 卡在 `test_memory_search_v2.py:164` 的同步 `db.execute`。该文件单跑正常（`-n0`，17 passed / 2.08s），属 `--dist loadfile` 下的跨文件交互——同一 worker 进程连续跑多个文件，模块级全局状态会串。它发生在上面那个 `import asyncio` 缺失还在树上的窗口内，此后 10 次全量跑没有再现。**未 root cause，因此不声称已修复。**

**2. `test/kernel/test_scheduler.py::TestScheduler` 有既有的墙钟 flaky，非本次引入。** 本次 10 次跑出现 2 次抖动（`test_pause_resume_task`）。为排除是调度器改动导致，在 HEAD 上另跑 6 次全量：同样抖了 1 次（`test_recurring_task`）。两个用例同类——异步回调 + 0.5s 周期 + 1.5~3.5s `asyncio.sleep` 断言窗口，而调度器检查间隔是 1s，8 路并行下必然偶发。且它们用的是**异步**回调，走不到本次新增的线程池。建议改成事件驱动等待而非睡固定时长，属独立改动，本次未动。

## 后续检查点

- `async def` 内不得直接调用 `Path.read_*/write_*`、`open().read/write()`、`subprocess.run/call`、`time.sleep()`
- 阻塞调用一律走 `BlockingPool` 或 `asyncio.create_subprocess_*`；**新增子系统应开自己的池，不要回到默认 executor**
- 给同步回调加超时时，先问一句"超时之后那个线程去哪了"
- sync→async 迁移后，检查测试桩是否也改成了协程，以及调用点是否真的 await 了
