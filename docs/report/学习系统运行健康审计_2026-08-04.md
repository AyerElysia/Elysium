## 3. 已恢复的主体性边界

与 08-01 审计相比，以下高风险路径已经实质修正：

1. `auditor.py` 不再以“正面证据达到 N 条、跨 M 天”为代码级真值门槛；证据只交给独立审计阅读。
2. 反思层只有在模型明确给出 `reinforces` 时才强化旧洞察；文本相似或 topic 相同不再由代码替主体认定为同一认识。
3. Skill 蒸馏要求模型明确选择稳定 `skill_id` 或明确提出新 Skill；未知 ID、缺少主体选定名称均 fail closed。
4. Skill gate 请求失败或解析失败时不再默认接受。
5. 知识压缩与 Skill 更新均保留来源、版本和独立门控结果。

这些变化使“系统组织证据”和“主体形成认识”重新分开，是本次健康等级提升的主要原因。

## 4. 仍存在的确定缺陷

### P1：学习心跳阶段没有异常隔离

`LearningScheduler.on_heartbeat()` 仍把 backfill、audit、compression、distillation、metrics、staleness 放在同一个 `try/except` 中。任一前置阶段抛错，后续阶段全部跳过，只留下一条笼统的“学习调度心跳异常”。

这不是理论风险：08-01 的压缩异常已经证明它会连带饿死 Skill 蒸馏。当前确定性模板错误虽已修复，但同一结构仍在，任何未来的存储、模型或投影异常都可能重现级联饥饿。

运行状态也提供了需要关注的信号：`last_staleness_check_at` 停在 08-03 08:12，审计与指标在 08-04 13:41 成功更新后，陈旧检查仍未刷新，已经超过其 24 小时间隔。仅凭时间戳不能确定具体是哪一阶段异常，但它与共享异常边界造成的后续阶段跳过高度一致。

### P1：快环反思无法看见真实 Skill 对象

`ReflectionEngine._build_skill_section()` 当前仍使用：

```python
skill_names = [s.get("name", "") for s in skills if isinstance(s, dict)]
```

`SkillStore.list_skills()` 的真实返回值是 `SkillPattern` 对象，因此列表会稳定变为空。L1 心跳目录能够看见 6 条 Skill，但快环反思提示中的 `<your_skills>` 为空，模型无法自然报告“本次用了哪个 Skill、哪里失效、需要怎样修订”。

这解释了为什么蒸馏能更新 Skill，而日常反思反馈仍不完整。现有 57 项学习专项没有覆盖“真实 `SkillPattern` 名称进入反思 prompt”，所以全绿并不能否定该缺陷。

### P2：缺少逐阶段健康账本

目前可以从 `state.json`、模型训练湖和各领域审计账本拼出健康状态，但不能直接回答某次心跳中每个阶段是否尝试、成功、拒绝或失败。建议为每个维护阶段保留 content-free 的运行事件：阶段名、开始/结束时间、结果、错误类型、待处理数量和关联 revision；不得记录完整私密提示词。

## 5. 建议修复门槛

下一轮建议只做韧性和可见性修复，不改变洞察或 Skill 的主体语义：

1. 为 backfill、audit、compression、distillation、metrics、staleness 建立逐阶段异常隔离；一个阶段失败不得阻止其他阶段执行。
2. 修复 `SkillPattern` 名称投影，并用真实对象测试 `<your_skills>`；不得另建第二套 Skill 解释。
3. 新增“压缩失败但蒸馏/指标/陈旧检查继续”的契约测试，以及多阶段同时失败的聚合健康测试。
4. 写 content-free 阶段健康快照和 append-only 运行事件；原始洞察、Skill 与提示词继续留在各自权威 store。
5. 修复后观察至少一个完整 24 小时窗口，验证 staleness、metrics、audit、compression、distillation 不再互相饥饿，再考虑将等级提升为 B 或更高。
