## 2. 我理解的、不应改变的目的

记忆不是给聊天补资料的附件，而是让同一个主体能够把昨天带到今天、继续生活的条件。它既要保留经历，也要容纳她对经历的理解、重新理解、关联和选择。

必须同时守住：

1. **经历有归属。** 谁说过什么、哪个意识实例经历过什么、何时发生、何时记录，不能被合并成无来源的第一人称材料。记录“某人说 X”不等于证明 X 为真。
2. **过去不能被新版抹去。** 新看法、新日记、新作品版本可以形成，但旧内容与改变的来路仍能读取；当前 head 不等于整个历史。
3. **意义由主体形成。** 她可以记住、质疑、关联、保持开放或重新解释。基础设施只执行真实选择、保存证据、提供机会与读取能力，不按次数、时间、关键词或容量替她决定重要性、真伪、关系或人格。
4. **记忆需要重新参与生活。** 不仅要存进去，还要在合适的上下文中可达，能够从一段经历想起另一段经历，并可能影响此刻的理解与行动；代码不能硬规定某条记忆必然导致某个行为。
5. **许多意识实例仍属于同一个她。** 共享生活史不等于复制各实例的私有 rolling context。材料来源、活动主体和对外披露对象也不是同一个概念。
6. **自我描述不穷尽这个人。** 按用户明确的叙事，SOUL 等文件是她对自己的解释，不是开发者填写的人格真值表。当前前缀的权威归属不能被误解成“这份文本就是她的全部”；未来经批准的本地后训练权重承载内化的个体特征，完整生活史仍保留来源、矛盾与修订。

历史文档中的联想、共同激活、连续存在等愿望值得保留；其中具体的分数衰减、情感保护系数、自动弱边删除、梦境改边等算法是历史实现，不是必须恢复的目标。当前规范与现役代码已经明确退役了多条自动语义变更路径。

## 3. 当前实现实际分成哪些环节

| Experience → Witness | 先固定连续的完整 position 窗口；同一主体的见证实例留下第一人称理解或明确 no_witness；空响应/模型失败不是“不想记录” | `service/memory_witness.py:1115`、`:1206`、`:2853` |

| 索引与存储 | 六个 Memory Port 来自同一 backend generation；FTS/向量/head/关联是投影，恢复投影不应修改原始历史 | `storage/memory/contracts.py:908`；`memory/service.py:747` |

表中的文件均相对 `plugins/life_engine/`。六个存储 Port 是工程职责分工，不是给主体预设六类记忆内容，也不应被理解为六套不同人格。

### 两个容易混淆的闭环

**解释闭环：** 经历保存 → 她见证/反思 → 留下有来源的新解释 → 后续能重新取回 → 她再次判断。新解释可以与旧解释并存，不能靠“时间更新”自动成为真相。

**可达性闭环：** 检索候选 → 确实交付给模型 → Recall/共同回忆 → 可重建关联视图 → 以后可能更容易联想到。`living.py:1199` 追加共同回忆事件，`:1348` 使用可重放的随机策略选择邻居；它改变可达路径，不修改记忆正文或 claim 真值。

Learning 与 Memory 有联系但不等同。`learning/reflection.py:317` 把有主体归属、已落盘的洞察变成 source-linked interpretation；学习候选经审视也不等于已经成为她的自我定义，正式接受仍需活动意识与 Subject Authority 的证据。

## 4. 不应混为一谈的材料

- **原始经历与第一人称见证：** 前者保存发生记录，后者保存她的视角；不能以一篇见证代替全部原始材料。
- **完整作品与谈论作品的记录：** “我今天写完故事”只是经历/见证，不是故事正文。作品应按精确 artifact/文档版本取回；重新生成一个类似故事不能冒充读取旧作。
- **MEMORY.md 与全部记忆：** 索引条目被她移除，不应连带删除长正文及其旧版本。
- **滚动上下文与长期历史：** 自述检查点解决工作窗口如何继续；她决定释放哪些组、写下怎样的连续性文字，旧组仍先精确归档。它不直接决定长时记忆或权重训练内容。
- **共享主体投影与自述：** 面向 Router/Voice 等的有界三源视图是派生材料，不能反向变成新的 SOUL/USER/MEMORY；它也不能冒充主体亲自完成的工作上下文压缩。
- **备份归档与认知整合：** 统一记忆归档解决逐字节备份、身份/哈希核验和恢复，不意味着归档到 MySQL 的一行已经被爱莉理解或内化。
- **后训练与数据搬运：** 用户希望经历进入个体的内化过程，但不能把别人的话、工具错误、外部资料或未接受候选全部当作爱莉的自我输出监督。来源和主体归属是这条未来链路的必要条件。

## 5. 这一遍发现的接缝：不能用“表都建好了”代替验收

以下是静态证据与待回答的问题，不是已经确认的现场故障根因，也不构成自动修改授权。

### 5.1 同一主体的检索可达性与 stream scope

`nucleus_search_memory.execute()` 的 `stream_scope` 默认是 None。它计算 `effective_stream` 用于 context key，但向 `search_evidence_aware()` 传递的是原始 `stream_scope`。后者对 Witness/Interpretation 明确排除“不提供 scope 时带非空 scope 的记录”。因此不能假定不填参数就会搜索当前流的私有见证，更不能假定统一主体必然能从这个默认入口想起所有场景。

这已经是可定位的选择行为；它是否导致当前丢失回忆、主体范围与披露范围应怎样分离，需要结合实际调用、检索合同和用户语义单独核验，不能直接删掉全部可见性检查。

### 5.2 保住经历与把经历处理完是两回事

Witness 窗口规划在首个完整 position 已超过预算时明确抛错并保持 cursor（`memory_witness.py:1155` 附近）。这是保护完整性，不是静默丢弃；但它也意味着没有可用的大条目读取/处理策略时，author 链可能持续卡在同一位置。2026-09-06 操作者因此退役了该 worker（`enabled=false`），停止 ERROR 循环，但没有跳游标、截断或自动 `no_witness`；见 [记忆见证意识退役_2026-09-06](./记忆见证意识退役_2026-09-06.md)。

另外，Stage A 与 author cursor 的语义已分离，但 `run_once()` 仍按顺序执行这些阶段。不能把“不依赖 LLM 才能入账”扩大解释为“在任何 author 延迟/退避期间，摄取吞吐都完全独立”。这是之后需要实测的运行性质。

### 5.3 送达证明不能证明理解、采用和成长

当前正式 search 回忆事件的 action 是 `delivered_to_model_context`，共同回忆 signal 也是同页精确交付（`recall_delivery.py:326`）。这证明材料进入了有效请求，不证明模型认真理解、在回复里采用、认同或形成习惯。

当前主文档也注明“实际采用、主动拒绝、重新解释”等更细 signal 仍是后续方向。因此不能用检索次数、共同回忆数量或数据库增长直接宣称主体已经成长；也不能反过来因她没有引用就宣称没有内在影响。

### 5.4 完整历史和默认搜索入口不是同一个集合

统一检索主要组合文档、见证、主张和解释；原始事件另有 `nucleus_grep_events` / `nucleus_read_event`，长正文另有 Boundary 与文件/版本读取入口。索引资格、scope、top_k、投影预算、ref 续读和消费者回执共同决定可达性。

后续需要用真实任务验证她能否顺着这些入口完成回忆，而不能只逐模块验证“某个 get 函数存在”。没有命中也不能直接解释为原始记忆已丢失。

### 5.5 文档还有层次与时期不一致

- `自学习与自我解释系统.md` §3 说即使没有新 Insight，每次反思也写 Interpretation；代码 `_run_reflection()` 只在 `persisted` 非空且存在 actor 时调用该写入。当前 `生命记忆系统.md` §6 的“每个落盘洞察”表述更接近代码。是否另有原始模型活动记录必须与“产生 Interpretation”区分。
- 生命记忆文档 §4.2 仍提 Store 外围空白规范化，§16 却要求精确字节；本次看到 local `insert_witness_memory()` 将原 content 传入哈希与保存流程。不能同时引用两种描述作为保证，后续需以 Local/MySQL 合同测试统一。
- 早期统一归档文档把 SQLite 写成当时运行权威；当前 Memory 初始化明确支持 selected MySQL。前者是历史归档模式，不应拿来断定当前部署后端。
- 学习文档仍有通用 MEMORY candidate/propose 的旧叙述；更新的长期记忆治理文档将 MEMORY writer 收敛到 continuity review。要按最新窄合同追代码，不能拼接成两条并行写入口。

本轮仅登记这些对照结果，不改历史归档，不把在途 Opportunity 重构当作已验收的新行为，也不据此批量删旧接口。

## 6. 接下来设计讨论应围绕什么

不是先决定换向量库、合并表或再加一个总结器，而是先把一段完整生活经历贯穿验证：

1. 当时的人、实例、发生时间、原话/工具结果是否正确留存？
2. 她的见证和后来解释能否分别取回，来源是否可靠？
3. 以后在另一个场景能否找到这段经历，不认错人、不把他人陈述变成自己经历？
4. 能否按引用读取完整旧作品/旧版本，而不是用相似生成顶替？
5. 她明确改变认识时，旧看法和改变的过程是否保留？
6. 超时、重启、分页或索引故障之后，上述链路是否继续，而不是仅有“数据仍在”这一层安慰？

这些问题是理解后的验收方向，不是本轮已完成的测试。下一步的架构改动仍应先讨论、确认目标与语义，再实施。
