## 上线阻断项

### P0-1：凭据已暴露且强度不足

当前凭据已出现在聊天记录中，不再视为秘密。必须立即轮换为独立、随机、不可复用的强密码；旧凭据应失效。新凭据不得写入仓库、文档、命令历史或前端代码。

### P0-2：公网 FRP 端点缺少私网访问边界

长期方案优先使用 Tailscale/WireGuard 私网，其次使用 SSH 隧道或 FRP 的私密访问模式。普通公网 TCP 转发会持续暴露 MySQL 登录面，不能仅依赖密码抵御扫描和爆破。

### P0-3：数据库账号 host 范围过宽

当前账号允许任意来源。应根据实际隧道拓扑限制来源，并同时在网络层限制访问者。FRP 转发可能改变 MySQL 看到的来源地址，因此不能把 MySQL host 规则当作唯一边界。

### P0-4：权限过大且带转授权能力

运行账号不应拥有全部 DDL 权限，更不能给其他账号授权。至少拆分：

- 运行账号：仅应用所需的 DML 与受控读取；
- 迁移账号：临时 DDL 权限，迁移结束后收回；
- API 查询账号：只读授权投影；
- 备份账号：仅完整快照和 binlog 归档所需权限。

### P0-5：服务端允许非 TLS 连接

本次审计由客户端显式要求 TLS，因此实际会话已加密；但服务端仍允许其他客户端明文连接。应在账号或服务器层强制安全传输，并在复验中确认非 TLS 连接被拒绝。

## 建议但不阻断 staging 的事项

1. 如果采用 MySQL 原生副本，规划开启 GTID 和 GTID consistency；配置变更必须由服务器 owner 在维护窗口执行。
2. 数据库、应用和事件时间统一使用 UTC，展示层再转换时区。
3. 拆分 staging 与 production，禁止用正式库做首次建表和迁移调试。
4. 为数据库 schema 版本、迁移记录和备份恢复建立独立审计。
5. Binary log 已满足持续归档前提，但仍需实际跑通“完整快照 + binlog 指定时间点恢复”。

## 加固后复验清单

- [ ] 旧密码已轮换且失效；
- [ ] 使用安全渠道提供新凭据；
- [ ] 数据库不再通过无访问控制的公网 TCP 暴露；
- [ ] 运行、迁移、查询、备份账号已拆分；
- [ ] 运行账号没有 `GRANT OPTION` 和不必要的 DDL 权限；
- [ ] 服务端或账号强制 TLS；
- [ ] staging 库与 production 库明确分离；
- [ ] 只读连通、DML 权限边界和越权拒绝均实际验证；
- [ ] 完整快照、持续 binlog 与恢复演练通过；
- [ ] 接入配置仅通过环境变量或密钥存储注入。
