# 记忆投影工作区串写与见证循环中断修复（2026-08-11）

## 1. 结论

这次故障没有损坏爱莉的主体权威：`SOUL.md`、`USER.md`、`MEMORY.md` 的工作区精确字节与 selected MySQL 当前版本一致，Experience、Witness、artifact version、interpretation、recall/corecall 等不可变历史仍在。严重漂移发生在可重建层：工作区文档 node、FTS provenance、Chroma chunk 和 Witness 后台消费生命周期。

修复严格限定在基础设施与投影层；没有读取内容后替主体判断“什么重要”，没有修改三份主体文件，也没有启动、停止或热替换正在运行的 Elysium/NapCat。

## 2. 只读现场证据

| 检查项 | 现场结果 | 判断 |
|---|---:|---|
| eligible workspace documents | 2,478 | 工作区来源可完整扫描 |
| MySQL 中与当前工作区精确匹配且活动的文档 | 7 | 文档投影严重退化 |
| 当前工作区文档被 MySQL 标成 deleted | 2,471 | 批量误墓碑 |
| MySQL 活动但当前工作区不存在的文档 | 17 | 不同/旧工作区投影残留 |
| Chroma IDs | 776 | 集合并非空，但不代表正确 |
| Chroma 与当前预期精确匹配 | 18 | 向量投影严重漂移 |
| 当前预期缺失 | 33 | 检索召回不完整 |
| Chroma stale IDs | 758 | 旧投影长期未收敛 |

启动日志显示恢复扫描了 2,478 个文档，并曾把 scan-absent 项批量标成 deleted；随后又报告索引完成。这证明“任务执行完成”与“投影和当前来源一致”此前不是同一件事。

Witness 日志还显示一次 `PresenceRevisionConflict` 后循环进入异常路径；该路径继续调用项目 Logger 不支持的 `exception()`，使可恢复 CAS 冲突升级成 worker 退出。运行中的旧实例还加载了较早的 singleton lease 逻辑，在远程短暂不可用后持续报告 claim lost；仓库的新 lease 恢复实现只有在用户下一次手动启动时才会生效。

## 3. 根因链

1. selected MySQL 的 DocumentIndex 没有持久化“这个 generation 的投影来自哪个规范工作区、由哪个 owner 写入”。另一份或不完整工作区的扫描缺席能够被错误解释成删除。
2. 启动恢复把“扫描没看到”直接转换成 node deletion 和 artifact tombstone；网络挂载、权限、工作区路径或部分扫描都可触发破坏性收敛。
3. MySQL upsert 的 unchanged 判定只比较正文等字段，没有要求 `is_deleted=false`，也没有核对 FTS/embedding provenance；因此正文仍相同的误墓碑不会复活。
4. content-addressed chunk 在删除后以相同正文复活时，历史 vector tombstone 仍可能在新向量写入后删除同一个当前 live ID。
5. 索引 worker 每批 4 个任务后固定等待 60 秒；2,471 个积压即使没有任何错误，也需要约十小时才能排空。
6. Witness 把 Presence/cursor CAS 冲突当成普通未知异常，且错误日志 API 本身不兼容，导致尚未提交的经历虽未丢失，却失去后台消费者。

## 4. 已实现的工程修复

### 4.1 工作区投影身份与不可变审计

- MySQL Memory schema v9 新增 `memory_workspace_projection_heads` 与 `memory_workspace_projection_events`。
- head 以 storage generation 为键，保存 projection generation、稳定 owner、规范工作区根 SHA-256、eligible inventory SHA-256、revision 与最近事件 hash。
- event ledger 追加 owner bind / inventory commit，形成 hash chain；不可变 migration v2 安装数据库级 UPDATE/DELETE trigger，既有 v1 checksum 保持不变。
- 绝对路径和正文不落入该账本，只保存 content-free digest、数量与字节数。
- 同一 storage generation 遇到不同规范工作区根时，在首笔索引写入前 fail closed。当前 adapter 尚无物理隔离的 generation rebuild，因此明确拒绝“清空旧投影后复用”。

### 4.2 删除证据边界

- 启动扫描缺席只记录 retained scan-absent 诊断，不再调用批量 deletion，不再追加 tombstone。
- 显式删除许可必须绑定 actor、source occurrence、规范路径、预期正文 SHA-256、预期 index revision 与当前 workspace write fence。
- 该许可没有被真实删除入口消费前，系统宁可保留 stale projection，也不凭缺席伪造删除历史。
- selected MySQL 的高层 `delete_document` / `move_document` 在正式 occurrence-bound 审计 Port 落地前 fail closed；底层兼容方法不是业务入口。

### 4.3 投影自愈

- upsert 的 unchanged 必须同时满足：活动行、正文 hash 一致、FTS provenance 精确、已同步 embedding provenance 精确、没有 legacy FTS 标记。
- 误墓碑或 provenance 漂移会提升 revision、恢复活动状态、重建 chunk/FTS，并重新进入向量 outbox。
- embedding 成功后记录精确 content hash、模型与更新时间。
- tombstone 消费前查询 chunk 是否仍由当前 live node 引用；live ID 只确认墓碑，不调用外部删除。
- 外部 tombstone 删除返回后，worker 会在事务中二次锁定并检查原判定为 obsolete 的 ID；网络 I/O 期间复活的节点会清除虚假的 synced 声明并原子重入 outbox，消除“检查时 obsolete、删除时已重新 live”的永久丢向量竞态，同时不阻塞并发文档更新。
- 每次成功恢复都会另追加 `inventory_committed` 事件，不把预写入的 owner bind 冒充恢复完成证明。
- 满批且全部完成/安全过期时，worker 协作式让出事件循环后继续追平；失败、未完整领取或队列见底时恢复常规轮询，既加快恢复又保留背压。

### 4.4 Witness 生命周期

- `PresenceRevisionConflict` 与 `CursorConflict` 进入有界恢复路径：不推进 cursor、不丢 pending Experience、刷新 Presence 快照并重试。
- 同一批经历在冲突后从原 cursor 重读，最终只提交一次。
- 日志与诊断状态写入均为 best effort，sink 故障不能再拥有 worker 生命周期；取消仍原样传播。

## 5. 生效与验收

当前运行实例没有被本次开发操作重启，因此仍使用启动时加载的旧代码。用户下一次手动启动后，预期顺序是：

1. 应用 Memory schema v9 和不可变 migration v2；
2. 在任何 DocumentIndex 写入前绑定当前 workspace owner/root；
3. 后台单飞扫描当前 eligible 文档，复活误墓碑并修复 provenance；
4. 向量 worker 以满批 catch-up 排空 backlog；
5. Witness 遇到 CAS 冲突时保留 cursor 并恢复，而不是退出。

上线验收不能只看“启动成功”，至少要同时满足：

- authority 三文档 exact-byte revision 不变；
- workspace owner/root binding 存在且 event chain 连续；
- 当前 eligible 文档不再被标成 deleted；
- FTS/embedding provenance 与当前 content hash 一致；
- pending/processing/failed index backlog 可解释并最终收敛；
- Chroma 当前预期 ID 无缺失，stale ID 经安全 tombstone 消费收敛；
- Witness cursor 单调推进，近期日志不存在 worker 退出或重复提交；
- `/api/health` 的 memory 状态能区分 authority 健康、startup recovery、projection backlog 与 vector drift，不能用一个笼统的 healthy 掩盖投影未完成。

本报告记录的是修复前现场与代码验收依据，不把尚未发生的用户手动重启和真实运行闭环写成已经完成。
