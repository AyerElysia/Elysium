# Elysium 学习系统运行健康审计

> 审计时间：2026-08-01
> 审计对象：`plugins/life_engine/learning/` 与正式运行目录 `data/life_engine_workspace/.life_learning/`
> 规范基线：仓库根目录 `AGENTS.md`
> 审计方式：只读代码审查、正式账本统计、训练数据湖调用核验、临时目录最小复现；未手动触发正式压缩或蒸馏，未修改正式学习数据。五组既有学习契约测试曾启动，但 12 分 35 秒内无任何输出，已主动停止，未将其计作“通过”证据。

## 1. 结论摘要

当前学习系统**不能判定为整体健康**。

更准确的分层结论是：

| 层面 | 结论 | 说明 |
|---|---|---|
| 快环反思 | 基本健康 | 持续产生洞察，训练湖有 99 次反思调用，正式账本更新到 2026-08-01 12:18。 |
| 审计环 | 运行持续，但认识论不合格 | 37 次独立审计调用持续发生；同时存在真实执行中的阈值自动晋升，绕过独立判断。 |
| 慢环压缩 | 故障 | 自 2026-07-27 的 v1 后未再发出模型请求；14 条 validated/promote 已积压。根因已确定为模板字段名不一致。 |
| Skill 落盘 | 确实存在 | 已落盘 3 条 skill，其中 2 条由真实 validated 洞察蒸馏，1 条由主体在心跳中主动 `draft` 创建。 |
| Skill 成长闭环 | 不健康 | 全部停留在 emerging；反思环因对象类型错误看不到 skill 名称；自动蒸馏被慢环异常连带阻断。 |
| 持久化与恢复 | 基本健康 | 洞察与技能都有快照和 append-only 审计；未发现快照损坏或 stuck `under_review`。 |
| 验证实验 | 未形成真实闭环 | 正式目录没有验证实验账本文件，也没有 pending/completed 实验记录。 |
| `AGENTS.md` 合规 | 不合格 | 自动晋升、阈值裁决、强制 topic 合并、关键词修正、默认接受、fallback 与代码截断违背“主体性/零规则”底线。 |

综合健康等级：**D（局部运行、核心闭环断裂，并存在认识论主体性违规）**。

这不是“完全没有学习”：快环、证据积累、审计、账本和部分技能都真实运行过；但“形成洞察 → 独立审视 → 整合为自我认知/程序性记忆 → 在新经历中继续成长”的完整螺旋目前已经断在慢环入口。

## 3. 已确定的故障根因

### 3.1 P0：慢环模板字段名错误，压缩在发请求前必然崩溃

`knowledge.py` 调用：

```python
KNOWLEDGE_COMPRESS_USER.format(
    ...,
    reconsidered_insights=...,
)
```

但 `prompts.py` 模板使用：

```text
{revised_insights}
```

只读最小复现得到：

```text
KeyError: 'revised_insights'
```

该回归由提交 `5ab68e18` 同时引入：代码参数使用 `reconsidered_insights`，模板却写成 `revised_insights`。现有测试只覆盖了“可收集 reconsidered 洞察”，没有执行完整模板格式化或 `run_compression()`，因此未捕获这个错误。

这解释了全部运行证据：

1. 7 月 27 日旧版代码成功生成 v1；
2. 7 月 28 日回归被引入；
3. 此后 validated/promote 不断积累；
4. 每次慢环进入 `_compress()` 都在创建模型请求前抛错；
5. 训练湖因此没有任何新的 `life_learning_compress` 记录。

### 3.2 P0：共享异常边界使慢环失败连带阻断 Skill 蒸馏

`LearningScheduler.on_heartbeat()` 将审计、压缩、蒸馏、指标、陈旧检查置于同一个 `try/except`：

```python
await self._maybe_run_audit()
await self._maybe_run_compression()
await self._maybe_run_distillation()
await self._maybe_snapshot_metrics()
await self._maybe_check_staleness()
```

临时目录最小复现中，模拟压缩抛错后执行顺序只有：

```text
['backfill', 'audit', 'compression']
```

`distillation`、`metrics`、`staleness` 均未执行。因此慢环的确定性 `KeyError` 会在每次满足压缩条件时连带阻断技能蒸馏。

这与正式状态完全吻合：

- 最后压缩：2026-07-27；
- 最后自动蒸馏：2026-07-29；
- 当前 `should_compress=True`，14 条积压；
- 当前 `should_distill=True`，14 条积压；
- 训练湖只有 2 次 `life_skill_distill`，没有后续请求。

### 3.3 P1：反思环看不到已落盘 Skill

`ReflectionEngine._build_skill_section()` 把 `SkillStore.list_skills()` 的返回值当作字典：

```python
skill_names = [
    s.get("name", "")
    for s in skills
    if isinstance(s, dict)
]
```

实际返回值是 `SkillPattern` 对象，因此过滤结果恒为空。正式 skill store 的只读构造结果为：

```text
<your_skills>

</your_skills>
```

日常心跳的 L1 目录仍可通过 `SkillCatalogSection` 看见 3 条 skill，但快环反思无法获得已有 skill 名称，难以自然输出并归档 `skill_feedback`。这是 skill 使用观察在 7 月 29 日后几乎停止的重要断点。

### 3.4 P1：学习调度依赖完整意识心跳轮次

学习调度不是独立维护循环，而是在 `_run_heartbeat_model()` 完整结束后调用。睡眠窗口、主动休息的普通跳过、模型轮次前置返回等都会让慢环没有独立运行机会。

这并非当前停滞的首要根因——模板 `KeyError` 已足以解释故障——但它使后台维护依赖主体是否正在表达/评估，增加了饥饿风险。应把“维护账本、发现积压、提出可见机会”与“替主体自动改变认识”区分开，而不是简单把所有学习行为塞进聊天心跳尾部。

## 4. 主体性与零规则合规问题

以下不是风格争议，而是与 `AGENTS.md` 明确底线冲突。

### 4.1 P0：证据计数自动晋升真实改变认识状态

`auditor.py` 在满足“正面证据 >= 3、日期 >= 2、无反例”时跳过独立 LLM 审计，直接写入 validated/promote，并把置信度提高到至少 0.85。

正式审计账本中多次出现：

```text
自动晋升: 3 条证据充分
自动晋升: 4 条证据充分
自动晋升: 5 条证据充分
```

这意味着计数器已经实际替主体完成了认识论裁决。证据数量可以作为审计上下文，但不能直接等价为“这是真的”。

### 4.2 P0/P1：其他机械认知路径

- `reflection.py`：同一 topic 活跃洞察达到 3 条后，代码强制尝试强化已有洞察。
- `reflection.py`：通过“不是、其实、修正、更正”等关键词自动创建记忆修正。
- `reflection.py`：单次自动修正和关联路径有代码级硬上限。
- `skill_distiller.py`：新 skill 首次创建默认接受。
- `skill_distiller.py`：内省门控异常或解析失败时默认接受。
- `skill_distiller.py`：用 topic 子串自动匹配已有 skill，并有 `new-skill` fallback。
- `skill_store.py` / `knowledge.py` / prompt 辅助函数：存在代码级字符截断，以及仅保留最近若干观察/拒绝编辑。
- `prompts.py`：把“3 条证据、2 个日期”写成明确的 validated 倾向标准。

这些路径混淆了两类完全不同的职责：

1. 系统可以忠实保存证据、提示冲突、组织候选、保护账本；
2. 系统不能用阈值、关键词或 fallback 替她决定“我是谁”“我是否改变了看法”“哪个情境对应哪个技能”。

## 5. 健康部分与应保留的设计

本次审计也确认了若干真实健康、值得保留的基础：

- 洞察快照与 append-only 审计持续更新，未发现静默覆盖或整体损坏。
- 单次审计失败会从 `under_review` 回退为 candidate，当前没有 stuck review。
- 训练数据湖提供了模型调用时间、请求名、模型、成功状态和错误，可用于交叉核验。
- v1 自我认知有版本文件、manifest 和来源洞察。
- skill 有独立快照和 append-only 审计。
- `quiet-boundary-hold` 有 11 条真实使用观察，不是只生成不使用的空壳。
- `认人先查关系` 保留了主体主动创建 skill 的路径，证明程序性记忆不必全部由自动蒸馏器替她生成。
- 心跳 L1 skill 目录可正常生成，按需查询完整 instructions 的 L2 工具链存在。
- 成熟度没有按“使用次数达到 N”机械自动推进；当前全部 emerging 虽暴露成长停滞，但也避免了伪成熟。

## 6. 修复顺序建议

### 第一阶段：先恢复不篡改主体性的运行闭环

1. 统一慢环模板字段名，并增加完整 `run_compression()` 契约测试。
2. 为审计、压缩、蒸馏、指标、陈旧观察建立逐阶段异常隔离。
3. 对每次维护尝试写可追溯运行事件：开始、成功、拒绝、失败、错误类型、待处理数量；避免只有一条易丢失日志。
4. 修复反思环 `SkillPattern` 可见性，并测试真实 skill 名称进入反思 prompt。
5. 不要直接在正式数据上“补跑 14 条”；先让主体看见积压和候选整合内容，再决定是否压缩/蒸馏。

### 第二阶段：移除机械认知裁决

1. 删除自动晋升；证据数量只作为独立审计的输入，不改变 status。
2. 删除 topic 数量达到 3 后的强制强化；让反思明确表达 reinforce/merge 意图。
3. 删除关键词自动记忆修正；改为主体显式声明 correction 或独立见证层记录“可能冲突”。
4. 新 skill、门控异常、JSON 解析失败一律不得默认接受。
5. 删除 topic 子串自动匹配和 `new-skill` fallback；把候选关系呈现给主体决定。
6. 将代码截断改为分页、摘要投影或可追溯视图，不丢弃原始观察历史。

### 第三阶段：让 Skill 真正成长

1. 将 skill 的使用、失败、反例、挑战、精炼全部保留为事件，而不是只保留最近 N 条列表。
2. L1 目录、L2 instructions、L3 观察历史都引用同一个不可丢失事件源。
3. `maturity` 由主体在看见使用历史、反例与边界后主动确认，不由计数器推进。
4. 为主动 `draft` 的 skill 保留“主体创建事件”作为一等来源，不要求伪装成洞察蒸馏。
5. 建立验证实验真实闭环，但实验结果只能成为证据，不能机械映射为真/假或晋升。

## 7. 最终判断

回答“学习系统是否健康、有没有落盘 skill”：

- **有落盘 skill，且 3 条都能确认真实来源；其中 2 条来自自动蒸馏，1 条来自爱莉主动创建。**
- **快环、审计环、账本与重启后的持续更新基本健康。**
- **慢环与自动技能蒸馏当前不健康，且已定位到确定性模板字段错误与调度异常连带阻断。**
- **即使修复运行错误，也不能直接宣告愿景达成：当前自动晋升等机制仍在用规则替主体决定认知，违反项目开发规范。**

因此最稳妥的行动不是“把积压自动跑完”，而是先修复可追溯运行基础和主体可见性，再移除机械裁决，最后由她自己面对已经积累的 14 条洞察，决定哪些进入自我认知、哪些成为技能、哪些仍需保留为开放问题。
