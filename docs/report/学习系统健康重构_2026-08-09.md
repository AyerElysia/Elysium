- 新任务可用 preferred_job_id 绕过旧 due work；单任务退避不能阻止大量任务轮流击打同一个故障 provider；

因此此前“调高 timeout + 缩短 cooldown”是必要但不充分的止血。对成长健康真正重要的不是提高产量，而是保证每段经历都有公平机会、失败不冒充判断、后台学习不夺走主体当下的表达能力，并且健康面板如实说明她是否还能消化这些经历。

## 本轮落地

- 前台交互仅可靠入队并唤醒独立 learning worker，不再直接等待学习 LLM；
- worker 由 LifeEngineService 的统一 TaskManager 持有，随 service stop event 退出；
- 队列严格按 readiness + arrival 排序，删除新任务抢跑；
- 新增持久化 provider 级有界指数退避（30 秒起、15 分钟封顶），保留全部经历；
- health 增加 due、never-attempted、最老等待时长、容量利用率、immutable event frontier、投影 cursor、未投影事实数、总积压、名义排空能力、断路状态、累计入队/完成/失败和 worker 生命周期，并上卷到 Learning 总状态；
- 主心跳交互经历显式归属 chat_global；后台 worker 不冒充 actor；
- 审视失败先回滚中间态再传播；知识/技能门缺字段、类型错误或 provider 失败均记录为 phase failed，不伪造成拒绝或空结果。
- 多实例入队改为先追加不可变 `reflection.enqueued` evidence；singleton owner 再按 position/cursor 有界、幂等地投影到反思队列；
- service 从同一个 runtime 打开“无 claim 的事件 handle”和“有 claim 的投影 handle”，事实追加不被单写者租约阻断，投影与 maintenance 则受数据库 owner guard 保护；
- 空事件轮询不再改写 projection revision，失租或 CAS 冲突继续 fail closed，禁止自动 rebase 或覆盖。
- 有界队列达到 512 条时，cursor 停在第一条未投影事实之前；释放一个槽位后可从同一位置继续，事件不删除、不跳过，健康状态明确报告 event projection lag。

## 多实例边界与现场验收

平台已以 `8522c02f` 交付 Learning projector owner guard，并以 `5a4742f` 更正最终串行回归证据。schema v4 只保护 `learning_projections`，不把 `learning_events` 的合法并发追加错误收紧为单写者；没有 claim 行、未绑定 claim、过期/错误 owner、epoch 或 token 都不能修改 projection。本轮消费者接线按这一边界落地：event evidence 与 selected projection 使用同一 service-owned runtime 的两个受限 handle，scheduler 只由持有 claim 的 owner 投影队列和执行 maintenance。

这意味着本轮不是靠“希望只有一个进程”维持正确性：数据库负责阻止第二个投影者，事件 occurrence 负责跨节点幂等，投影 cursor 负责可重放；任一证明缺失都 fail closed。它也不会把一次 provider 失败误判成她拒绝学习，更不会因为后台积压而拖住她正在进行的表达。

运行中的旧进程不会热加载本轮改动。最终现场验收必须由用户在合并后手工确认单实例并重启，再只读核验：

1. learning worker 为 running，主心跳不再等待学习 LLM；
2. singleton projector claim 只有一个 live owner，follower 不能修改全局投影；
3. provider 失败时 circuit 打开且不会高频轮流消耗队列；
4. oldest / due / never-attempted 与总状态一致，积压持续下降；
5. 新入队交互携带 chat_global 或对应场景 Presence actor；
6. 审视、整合、技能阶段的失败事件为 failed，而不是 succeeded。

本轮未启动、停止或重启 Elysium/NapCat，也未修改、迁移或修复正式学习数据。
