# Memory 正式库 v9 升级缺口与修复

日期：2026-08-11
状态：**正式 MySQL 技术 schema、自动化回归与用户手动启动验收均已通过；用户已明确授权正常非 force push**

## 1. 事故边界

代码基线要求：

- `MEMORY_SCHEMA_VERSION = 9`；
- `MEMORY_IMMUTABILITY_SCHEMA_VERSION = 2`；
- `memory_workspace_projection_events` 与 `memory_workspace_projection_heads` 两张 workspace projection 表；
- `memory_workspace_projection_events` 的 UPDATE/DELETE 数据库级不可变 trigger；
- 完整 Memory trigger 合同共 44 条。

正式 MySQL 在升级前只有 schema v1..v8、immutability v1 和 42 条匹配 trigger，两张 v9 表均不存在。正常业务启动固定使用 `initialize_schema=false`，只验证 migration checksum 与 trigger，不会在启动阶段自动应用技术 schema。因此“用户下次手动启动会自动补 v9/v2”的旧结论错误；如果不先升级，Life Engine/Memory 会在插件加载阶段失败关闭。

## 2. 根因

`e9e47918` 提高了 Memory 代码合同，但现有正式运维 CLI 没有独立的 Memory additive upgrade 路径。生产 adapter 正确地禁止业务启动修改 schema，运维侧却缺少相应显式命令，形成“代码只验证、无人负责安装”的断层。

该问题不是数据迁移失败、checksum 漂移或既有 trigger 漂移：升级前 v1..v8 与 immutability v1 的名称和 checksum 均匹配，42 条既有 trigger 也匹配。

## 3. 实现

`scripts/adopt_life_mysql_baseline.py` 新增独立 `upgrade-memory`：

1. 要求显式 `--confirm-memory-upgrade` 和此前不存在的 `--output` 目录；
2. 本机若仍有 Elysium `main.py` 进程则在 DDL 前失败关闭；
3. 数据库时间下仍有任何 active singleton writer claim 时在 DDL 前失败关闭；
4. 在只读一致性快照中计算既有 32 张 Memory 表逐表内容根、总根与行数；
5. 记录 active generation、authority epoch/owner/event head 与 generation manifest；
6. 分别通过 `MySQLMigrationRunner` 和正式 advisory lock 应用 Memory schema v1..v9、immutability v1..v2；
7. 以完整 body contract 核验 44 条 trigger；
8. 再次核对既有 32 张表、authority、活动 claim、本机进程和两张新表；
9. 新建 v9 表必须为空，任何既有数据或 authority 改变都失败关闭；
10. 失败只落 content-free 原因，不打印数据库凭据或业务正文。

该命令不注册或激活 generation，不修改 authority，不导入本地数据，不使用 candidate-copy，不启动或停止 Elysium。
